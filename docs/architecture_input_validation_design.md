**저장 실패 시 복원 로직 부재**:
- 토글·라디오는 저장 실패 시 원래 값으로 되돌리는 로직이 있음 (예: `general-settings-auto-trade-tab.ts:93-95`, `general-settings-display-settings-tab.ts:24`).
- 숫자 입력란(`createNumInput`/`createMoneyInput`)은 `onChange`에서 `autoSave`만 호출하고 실패 시 복원 로직 없음. 잘못된 값이 화면에 남음.
- 시간쌍 입력(`createTimePairInput`)도 저장 전에 `state.vals`를 덮어써서 실패 시 잘못된 값이 남음 (`general-settings-time-settings-tab.ts:31-33`).

**시간쌍 순서 검증 부재**:
- 자동매수/매도 시간(`createTimePairInput`)에서 시작이 종료보다 늦어도 저장됨 (예: 시작 15:00, 종료 09:00).
- `time-pair-input.ts`에 순서 검증 로직 없음.

### 1.2 목표

1. **숫자 입력란 min/max 일관적 적용**: 검증 없는 18개 입력란에 min/max 추가. 이미 검증 있는 입력란과 동일 패턴 (P23 일관성).
2. **일일 수익률 한도 상한 확장**: max:100 → max:1000. 200% 이상 수익도 허용 (사용자 결정).
3. **시간쌍 순서 검증 추가**: 시작 ≥ 종료 시 저장 막고 안내 메시지 표시 (P20 폴백 금지 — 잘못된 값 방치 금지, P21 투명성 — 사유 표시).
4. **저장 실패 시 입력값 복원**: 토글·라디오에 있는 복원 패턴을 숫자 입력란·시간쌍에 동일 적용 (P23 일관성).
5. **허용 범위 안내 라벨 추가**: 모든 숫자 입력란에 허용 범위를 작은 텍스트로 표시. 사용자가 입력 전에 범위 인지 (P21 사용자 투명성).
6. **P10/P16/P20/P21/P22/P23/P24/P25 완전 부합**.

### 1.3 비목표 (본 설계에서 다루지 않음)

- **백엔드 검증 로직 추가**: 프론트엔드 입력란 검증만. 백엔드 스키마 검증은 별도 작업 (백엔드에서 이미 일부 검증 존재 가능 — 2세션 사전조사에서 확인).
- **검색 입력란 디바운스**: `buy-target.ts` 검색 입력란. 사용 빈도 낮고 성능 영향 미미. 별도 작업 시 고려.
- **API 키·텔레그램 토큰 입력 검증**: 한글/특수문자 검증. API 키는 증권사 규격에 따라 다양하므로 프론트 검증 부적절. 백엔드 인증 실패 시 이미 에러 피드백 있음.
- **저장 시점 불일치(토글 즉시 vs 숫자 0.4초 지연)**: 디바운스는 의도적 설계(입력 중 매 저장 방지). 변경 시 데이터 정합성 위험 낮음. 별도 작업 시 고려.
- **부분 저장 가능성(saveSection 다중 필드)**: 현재 프론트에서 단일 필드 저장이 대부분. 다중 필드 저장은 API 키·텔레그램 탭만. 별도 작업 시 고려.

## 2. 설계 방향

### 2.1 핵심 설계 결정

#### 결정 1: 입력란별 min/max 값 — 단위 기준 분류

입력란 단위에 따라 4가지 패턴 적용 (P23 일관성 — 같은 단위는 같은 검증):

| 단위 | min | max | 근거 |
|---|---|---|---|
| 비율 (%) | 0 | 100 | 비율은 0~100. 음수·100 초과 불가 |
| 금액 (원) | 0 | 생략 | 사용자 결정 — 상한 없이 음수만 막기 |
| 개수 (개) | 0 | 100 | 개인 투자자 기준 합리적 상한. 음수·정수 아닌 값 막음 |
| 가산점 점수 | 0 | 100 | 가산점이므로 음수 막음. 100점 이상 비현실적 |

**예외 (사용자 결정)**:
| 입력란 | min | max | 근거 |
|---|---|---|---|
| 일일 수익률 한도 (%) | 0 | 1000 | 사용자 제안 — 200% 이상 수익도 현실적으로 가능. 기존 max:100 확장 |
| 일일 수익 한도 (원) | 0 | 생략 | 손실 한도(min:-10억, max:0)와 대칭적으로 min:0만 지정 |

**왜 이렇게**: 이미 검증 있는 입력란(매도 주문 간격, 손실 한도 등)의 패턴을 동일하게 적용. 새로운 검증 방식 도입하지 않음 (P23 일관성, P24 단순성).

#### 결정 2: 허용 범위 안내 라벨 — 기존 labelSubText 패턴 재사용

모든 숫자 입력란에 허용 범위를 작은 텍스트로 표시. 사용자가 입력하기 전에 허용 범위를 인지 (P21 사용자 투명성).

**적용 방식**: 기존 `labelSubText` 패턴 재사용 (신규 컴포넌트 생성 금지 — P23 일관성, P24 단순성).

`labelSubText`는 `createToggleLabelControlsRow`에서 이미 라벨 하단에 작은 회색 텍스트로 표시되는 패턴 (`setting-row-controls.ts:178-183`). 현재 `(수수료 포함)`, `(초, 5초 단위)` 등에 사용 중.

**허용 범위 표시 포맷 (단위별)**:

| 단위 | 표시 포맷 | 예시 |
|---|---|---|
| 비율 (%) | `0~100%` | 종목 상승률 매수차단: `0~100%` |
| 금액 (원) | `0원 이상` | 전체 일일 최대 매수 금액: `0원 이상` |
| 개수 (개) | `0~100개` | 최대 동시 보유 종목 수: `0~100개` |
| 가산점 점수 | `0~100점` | 5일 고가 돌파 가산점: `0~100점` |

**예외 표시**:
| 입력란 | 표시 | 근거 |
|---|---|---|
| 일일 수익률 한도 (%) | `0~1000%` | 결정 1 예외 — 상한 1000% |
| 일일 수익 한도 (원) | `0원 이상` | 결정 1 예외 — 상한 없음 |
| 매수/매도 주문 간격 (초) | `(초, 5초 단위)` 유지 | 이미 labelSubText 있음 — 중복 추가 금지 (P10 SSOT) |
| 업종 가산점 슬라이더/입력 3개 | `(-100%~+100%)` | 결정 1 — min:-100, max:100 (이미 검증 있음, 안내만 추가) |

**이미 labelSubText 있는 입력란 처리**:
- 매수 주문 간격: 기존 `(초, 5초 단위)` → `(초, 5초 단위, 5~300초)`로 병합 (중복 라벨 생성 금지)
- 매도 주문 간격: 기존 `(초, 5초 단위, 손절 포함)` → `(초, 5초 단위, 5~300초, 손절 포함)`로 병합
- 전체 일일 최대 매수 금액: 기존 `(수수료 포함)` → `(수수료 포함, 0원 이상)`로 병합
- 종목당 일일 최대 매수 금액: 기존 `(수수료 포함)` → `(수수료 포함, 0원 이상)`로 병합

**labelSubText 미지원 입력란 처리**:
- `createSettingRow`로 직접 렌더링하는 입력란(업종순위 설정 등)은 `labelSubText` 파라미터가 없음.
- 이 경우 `createDescText` 패턴(행 아래 별도 설명줄)로 동일하게 적용하거나, `createSettingRow`에 `labelSubText` 지원 추가.
- 2세션 사전조사에서 `createSettingRow` 시그니처 확인 후 결정.

**왜 이렇게**: 기존 `labelSubText`/`createDescText` 패턴을 재사용. 새 안내 라벨 컴포넌트 생성 금지 (P23 일관성, P24 단순성). 이미 안내 텍스트 있는 입력란은 병합하여 중복 방지 (P10 SSOT).

#### 결정 3: 시간쌍 순서 검증 — 저장 막고 안내

`createTimePairInput`의 `onTimeChange` 콜백 호출 전에 순서 검증 추가:
- 시작 시간 ≥ 종료 시간 → 콜백 호출하지 않고 사용자에게 안내 메시지 표시
- 안내 메시지: "시작 시간이 종료 시간보다 빨라야 합니다" (P21 투명성)
- 입력란 값은 사용자가 입력한 대로 두되 저장은 막음 (P20 폴백 금지 — 잘못된 값을 자동 교정하지 않음, 사용자가 직접 수정)

**왜 자동 교환(스왑) 안 함**: 사용자가 의도한 것과 다르게 동작하면 P21(사용자 투명성) 위반. 사용자가 "야간 매매를 원했는데 왜 낮에 매매되지?" 혼란 발생.

#### 결정 4: 저장 실패 시 입력값 복원 — 토글 패턴 재사용

토글·라디오에 이미 있는 복원 패턴을 숫자 입력란·시간쌍에 동일 적용:

```
// 토글 기존 패턴 (general-settings-auto-trade-tab.ts:92-95)
const res = await saveSection(...)
toastResult(res)
if (!res.ok) { state.vals.X = 원래값; toggle.setOn(원래값) }

// 숫자 입력란에 동일 패턴 적용
const 원래값 = state.vals.X
state.vals.X = 새값
const res = await saveSection(...)
toastResult(res)
if (!res.ok) { state.vals.X = 원래값; input.setValue(원래값) }
```

**왜 이렇게**: 토글 패턴을 그대로 재사용하여 새로운 복원 메커니즘 도입하지 않음 (P23 일관성, P24 단순성).

#### 결정 6: 수정 범위 — 4개 수정안 통합 진행

4개 수정안(검증 추가, 허용 범위 안내 라벨, 시간 순서, 복원 로직)은 모두 "입력란 검증·복원"이라는 공통 주제. 하나의 다단계 작업으로 통합 설계. 구현은 세션당 1단계 원칙에 따라 별도 세션에서 분할 진행(2세션 태스크 파일에서 단계 분할).

### 2.2 기각 방안

| 방안 | 기각 사유 |
|---|---|
| 백엔드에서만 검증 (프론트 미검증) | 사용자가 잘못 입력해도 프론트에서 막지 않으면 저장 시도 후 실패 메시지. 입력 단계에서 막는 것이 사용자 경험 상위 (P21) |
| 모든 입력란에 디바운스 통일 | 현재 토글 즉시·숫자 0.4초 지연은 의도적 설계. 통일 시 입력 중 매 저장 발생 또는 토글 지연 발생. 비목표로 이관 |
| 시간쌍 자동 스왑 | P21 위반 — 사용자 의도와 다르게 동작. 기각 |
| 금액 상한 10억/1억 고정 | 사용자 결정 — 상한 없이 음수만 막기. 기각 |
| 비율 상한 1000% 통일 | 수익률 한도만 1000%, 나머지 비율은 0~100이 자명(상승률·하락률·임계치 등). 예외 처리 (결정 1) |
| 신규 안내 라벨 컴포넌트 생성 | 기존 `labelSubText`/`createDescText` 패턴으로 충분. 신규 컴포넌트는 P24(단순성) 위반. 기각 |
| 입력란 placeholder에 범위 표시 | placeholder는 입력 시작하면 사라져 범위를 계속 볼 수 없음. `labelSubText`가 라벨 하단에 고정 표시되어 지속적. 기각 |

## 3. 사용자 결정 항목

### 질문 1: 3개 수정안 진행 방식
- **질문**: 3개 수정안(1: 입력란 음수·범위 제한, 2: 시간쌍 순서 검증, 3: 저장 실패 시 입력값 복원)을 어떻게 묶어 진행할까요?
- **사용자 답변**: "먼저 일반설정페이지 자동매매 탭에서 일일 수익률 한도 (%) 입력란도 100%로 한정되어 있어.. 이것도 문제인 것 같은데? 1000% 이상 수익 날 수도 있는 거 아닐까? 물론 힘든 거겠지만 현실에서 200% 이상 수익 날 수도 있는 거잖아? 추가하는 게 좋을 것 같은데."
- **반영**: 일일 수익률 한도 max:100 → max:1000 확장을 결정 1에 포함. 3개 수정안 통합 진행은 사용자가 명시적 거부하지 않았으므로 결정 4로 채택.

### 질문 2: 금액 입력란 상한
- **질문**: 금액 입력란(매수 한도, 종목당 매수 금액, 일일 수익 한도 등)의 최대값 상한을 어떻게 정할까요?
- **사용자 답변**: 상한 없이 음수만 막기
- **반영**: 결정 1 — 금액(원)은 min:0, max 생략

### 질문 3: 시간 순서 위반 처리
- **질문**: 자동매수/매도 시간에서 시작이 종료보다 늦을 때 어떻게 처리할까요?
- **사용자 답변**: 저장 막고 안내 메시지
- **반영**: 결정 3 — 저장 막고 "시작 시간이 종료 시간보다 빨라야 합니다" 안내

### 질문 4: 허용 범위 안내 라벨 추가 (사용자 추가 요청)
- **사용자 요청**: "입력란에 min~max 범위를 표시하는 작은 안내 라벨을 추가해주세요. 예: 0~100%, 0원 이상, 0~100개 등. 사용자가 입력하기 전에 허용 범위를 바로 알 수 있으면 UI/UX가 좋아질 것 같습니다. 적용 방식은 기존 createDescText 패턴을 재사용하거나, labelSubText 패턴을 응용하는 등 일관성(P23)을 유지해주세요."
- **반영**: 결정 2 — 기존 `labelSubText` 패턴 재사용. 단위별 표시 포맷 정의. 이미 안내 텍스트 있는 입력란은 병합(P10 SSOT). `labelSubText` 미지원 입력란은 `createDescText` 또는 `createSettingRow` 확장(2세션 사전조사에서 결정).

## 4. 아키텍처 원칙 부합 검토

| 원칙 | 부합 | 근거 |
|---|---|---|
| P10 (SSOT) | ✅ | 검증 값(min/max)은 입력란 생성 시점에 단일 지정. 중복 관리 없음. 허용 범위 안내 텍스트도 단일 출처에서 생성 |
| P16 (살아있는 경로) | ✅ | 검증 로직은 `createNumInput`/`createTimePairInput`의 실제 입력 이벤트 경로에 연결. dead code 아님 |
| P20 (폴백 금지) | ✅ | 시간쌍 순서 위반 시 잘못된 값을 자동 교정하지 않고 저장만 막음. 빈 값/None을 폴밭 기본값으로 덮지 않음 |
| P21 (사용자 투명성) | ✅ | 시간쌍 순서 위반 시 안내 메시지 표시. 저장 실패 시 toast 표시(기존). 허용 범위 안내 라벨로 사용자가 입력 전 범위 인지. 사용자가 "왜 저장 안 됐지?" 의문 갖지 않음 |
| P22 (데이터 정합성) | ✅ | 저장 실패 시 입력값 복원으로 프론트 값과 백엔드 값 불일치 방지 |
| P23 (일관성) | ✅ | 이미 검증 있는 입력란(매도 주문 간격, 손실 한도 등)의 패턴을 동일 적용. 토글 복원 패턴 재사용. 허용 범위 안내도 기존 `labelSubText`/`createDescText` 패턴 재사용 |
| P24 (단순성) | ✅ | 새로운 검증 프레임워크 도입 없음. 기존 `createNumInput`의 min/max 파라미터 활용. 토글 복원 패턴 재사용. 신규 안내 라벨 컴포넌트 생성 없이 기존 패턴 재사용 |
| P25 (격리된 실패) | ✅ | 개별 입력란 검증 실패가 다른 입력란·페이지에 영향 주지 않음. 저장 실패 시 해당 입력란만 복원 |

## 6. 리스크/롤백 기준

- **리스크 낮음**: 입력란 검증 추가는 사용자가 기존에 입력하던 값의 범위를 제한. 기존에 음수·범위 초과 값을 사용 중이었다면 해당 값이 입력란에 표시될 때 보정될 수 있음.
- **롤백 기준**: 검증 추가 후 기존 정상 값(0~100, 0~금액)이 입력되지 않는 경우. 즉시 롤백.
- **거래 로직 영향 없음**: 본 설계는 프론트엔드 입력란 검증만. 매매 로직 변경 없음. safe-trade 스킬 미적용.
