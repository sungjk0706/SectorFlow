## 1. 목표

1. 조사 보고서 86건 발견 사항을 코드 정밀 검증 결과 기반으로 재분류하고, 실제 의미 있는 개선만 선별 적용
2. 틱 핫패스 내 heavy work의 **연산량을 감소**시켜 틱 처리 지연 완화 (단, 매매 타이밍은 변경하지 않음)
3. 보고서 오류 항목(H-09, M-16)과 영향 미미 항목의 상태를 보고서에 정확히 갱신 — 잔존 발견 사항의 신뢰성 확보
4. 모든 변경이 매수/매도 판단 결과에 **동일성을 보장**하는지 사전 점검 (safe-trade)

### 용어 구분

- **매수 주문 체결**: 매수 주문이 실제로 성립한 사건.
- **매도 주문 체결**: 매도 주문이 실제로 성립한 사건.
- **시세 체결**: 가격·거래량 등 시장 시세가 전달된 사건. 이 문서의 01 시세 체결은 보유종목 현재가 갱신과 매도 조건 검사에 사용되는 사건이다.
- 주문 체결과 시세 체결은 별개의 사건이므로, 종류를 생략한 “체결”이라는 표현은 사용하지 않는다.

## 2. 비목표 (Not To Do)

1. **"지연 스케줄(dirty 마킹 후 배치 처리)" 방향 전면 기각** — evaluate_buy_candidates / check_sell_conditions의 실행 시점을 지연시키면 매수/매도 타이밍이 변하여 매매 결과가 달라짐 (safe-trade 위반, 상세는 §6 기각안)
2. **positions code→index 맵 도입 금지** — n≤10(최대 보유 5종목)에서 O(n) 영향 미미. 맵 도입 시 P10/P22/P16 복잡도 증가가 성능 이득보다 큼 (P24 단순성 위반)
3. **master_stocks_cache 구독 종목 set 별도 유지 금지** — 단일 순회 0.025ms, 빈도 낮음. set 도입 시 P10/P22/P16 이중 관리 위험이 이득보다 큼 (P24 위반)
4. **WS broadcast asyncio.gather 병렬화 금지(1단계)** — 단일 사용자 앱 N=1에서 이득 미미. per-client 에러 격리(P25) 이미 구현됨. 브라우저 탭 다중 사용 시나리오가 실제화되면 재검토
5. **배치 크기 500 / 단일 컨슈머 구조 변경 금지(1단계)** — 틱 폭주 시 큐 적체 가능성은 있으나, 단일 사용자 앱 트래픽에서 실제 발생 관찰 전 구조 변경은 P24 위반(불필요한 추상화)
6. **DB 쓰기 큐(maxsize=100) 구조 변경 금지** — 적체 시 생산자 블로킹은 있으나, 현재 관찰된 적체 없음. 모니터링 추가만 검토
7. **safe-trade 임계값/모드 전환 변경 없음** — 본 설계는 매매 판단 로직이 아닌 실행 경로의 연산 효율만 다룸

## 4. 채택안 + 이유

### 결정 1: 보고서 오류/영향 미미 항목 상태 갱신 (문서 작업, 코드 수정 없음)

**채택**: H-09, M-16은 보고서 상태를 "기각(실제 코드와 불일치)"로 변경. 영향 미미 군집(positions O(n) 7건, WS broadcast 2건, master_stocks_cache 5건)은 "보류(영향 미미 — 단일 사용자 앱 전제)"로 변경. 보고서 §1.2 통계와 §6 갱신 이력 갱신.

**왜**: 보고서가 "포맷 SSOT가 아니라 과거 산출물"이더라도, 잔존 발견 사항의 신뢰성은 후속 작업의 전제가 된다. 오류 항목을 방치하면 향후 에이전트가 잘못된 항목을 수정하려 시도할 수 있다(P16 살아있는 경로 — 문서도 살아있어야). 상태 갱신은 코드 수정 없이 보고서 파일만 편집하므로 safe-trade 영향 없음.

### 결정 2: M-23 per-entry copy 제거 (백엔드, 위험도 중간)

> **사전조사 결과 반영 (2026-08-02)**: 복사는 "방어적 복사"가 아님. 복사본에 추가하는 7개 필드 중 6개가 원본에 이미 존재하며, 시장 구분·NXT 여부·업종명을 구하는 함수들이 원본에서 그대로 읽어와 복사본에 다른 이름으로 옮겨 담는 중복 작업임. 복사 제거의 진짜 장애물은 원본 보호가 아니라 **화면(프론트엔드)이 기대하는 필드명과 원본 필드명이 다름** (예: 화면은 `avg_amt_5d`/`high_5d`/`market_type`, 원본은 `avg_5d_trade_amount`/`high_5d_price`/`market`).

**채택**: 복사 통째로 제거가 아닌 **필드명 불일치 해소 후 복사 축소**. 두 가지 길:
- **길 A (근본, 권장)**: 화면이 원본 필드명을 그대로 쓰도록 프론트엔드 수정 → 복사 완전 제거 가능. 화면 수정 범위 확인 필요.
- **길 B (점진)**: 화면 필드명 유지하되, 원본을 통째로 복사하지 않고 화면에 필요한 필드만 작은 그릇에 담기 → 복사 비용은 줄고 화면 호환성 유지.

**왜**: 200ms 루프에서 1337회 dict copy는 측정 가능한 오버헤드. P24(단순성 — 불필요한 복사 제거) 부합. 사전조사로 "방어적 복사" 가설이 기각되었으므로, 장애물은 필드명 불일치로 명확해짐 — 이를 해소하는 것이 근본 해결(P10 SSOT, P24 단순성). 길 선택은 화면 수정 범위 조사 후 결정.

**사전조사로 확정된 사항**:
- 복사본에 추가하는 필드 7개: 종목코드(원본 키로만 존재), 상태(원본에 이미 있음·중복), 5거래일 평균 거래대금(원본 `avg_5d_trade_amount`를 `avg_amt_5d`로 이름만 변경), 5거래일 최고가(원본 `high_5d_price`를 `high_5d`로 이름만 변경), 시장 구분(원본 `market`를 `market_type`로 이름만 변경·`get_stock_market()`이 원본에서 읽어옴), NXT 여부(원본 `nxt_enable`와 동일·`is_nxt_enabled()`가 원본에서 읽어옴), 업종명(원본 `sector`와 동일·`get_merged_sectors_batch()`가 원본에서 읽어옴).
- 결론: 7개 중 6개가 원본에 이미 존재하거나 원본에서 파생. 복사는 원본 보호가 아닌 필드명 변환용.

### 결정 3: H-06/H-07 check_sell_conditions 순회 범위 — 주문 체결 종목 한정으로 축소 (safe-trade 핵심, 위험도 높음)

> **정정 (2026-08-02 코드 기반 재조사 반영)**: 주문 체결 알림(00)에서 매도 검사 제거 시 **매도 신호 누락 없음**이 코드 기반으로 확인됨. 단, 매수 주문 체결 직후 시세 급변동 시 "즉시 반응"이 다음 01틱 수신까지 살짝 지연될 수 있음(누락 아님). 본 정정은 사용자 추가 질문 조사 결과 반영.

**채택**: `_on_fill_after_ws`가 `check_sell_conditions`에 전체 포지션이 아닌 **주문 체결된 종목의 포지션만** 전달하도록 변경. 현재 H-03(`_check_01_auto_sell`)은 이미 시세 체결이 발생한 종목 한정 매칭(`_matched = [p for p in state.positions if ... == nk_px]`)을 사용 중 — 이 패턴과 일치시킴.

**왜**:
- 주문 체결 알림(00) 틱은 특정 종목의 매수 주문 체결 또는 매도 주문 체결을 알리는 사건이다. 다른 종목의 매도 조건은 이 주문 체결과 무관 — 다른 종목의 매도 신호는 해당 종목의 01 시세 체결(가격 갱신) 경로에서 이미 `_check_01_auto_sell`이 평가 중.
- 즉, 주문 체결 알림(00)에서 전체 포지션 매도 조건을 재검사하는 것은 **중복 평가**. 주문 체결 종목만 평가해도 매도 신호 누락 없음(다른 종목은 자신의 01 시세 체결에서 평가됨).
- **매도 판단 결과 동일성 보장**: 주문 체결 종목의 매도 조건은 동일하게 평가됨. 다른 종목의 매도 조건은 제거되는 것이 아니라 **이미 다른 경로(01 시세 체결)에서 평가 중**이므로 결과 동일.
- 연산량: 전체 포지션 순회(n≤10) → 주문 체결 종목 1건. n이 작아 절대적 이득은 미미하나, 구조적 중복 제거(P24) + 매도 판단 경로 일관성(P23) 부수 효과.

**safe-trade 점검**:
- 매도 타이밍 변경: ❌ 없음. 주문 체결 종목의 매도 조건은 동일 시점에 동일하게 평가됨.
- 다른 종목 매도 신호 누락: ❌ 없음. 다른 종목은 01 시세 체결(가격 갱신) 경로에서 평가됨(`_check_01_auto_sell`). 보유종목은 200개 한도에 관계없이 우선 구독되므로 01틱 누락 시나리오 없음(`engine_ws_reg.py:108-138`).
- **"즉시 반응" 지연 (정정 반영)**: 매수 주문 체결 직후 시세 급변동으로 즉시 매도조건에 도달하는 경우, 주문 체결 알림(00) 경로가 없으면 다음 01틱 수신까지 대기해야 함. 이는 "매도 신호 누락"이 아니라 "반응 지연"이며, 01틱이 안정적으로 수신되므로 최종적으로 매도 신호는 발생함.
- 단, **사전조사 완료 (2026-08-02)**: 01 시세 체결이 주문 체결 종목 외 포지션의 가격 갱신을 충실히 전달함을 확인. 보유 종목은 구독 한도(200개)에 관계없이 항상 우선 등록(`engine_ws_reg.py:108-138`)되어 01틱 누락 시나리오 없음. 매도 판단은 각 종목이 자신의 현재가·손익률로 독립 평가. 부분 체결·전량 매도·주문 체결 종목이 보유 목록에 없는 경우 모두 안전 처리 가능. 누락 시나리오 없으므로 본 결정 유지.

### 결정 4: H-05/H-08 evaluate_buy_candidates — 지연 없이 연산량만 점검 (safe-trade, 위험도 높음)

**채택**: `evaluate_buy_candidates`의 실행 시점은 **현재와 동일하게 유지**(잔고 회복 시 즉시). "지연 스케줄" 방향은 기각(§6). 대신, `evaluate_buy_candidates` 내부 연산량이 실제로 틱 블로킹을 유발하는지 2세션에서 정량 측정 후, 필요 시에만 내부 최적화(스냅샷 비교 로직 등) 검토.

> **사전조사 결과 반영 (2026-08-02)**: `evaluate_buy_candidates`는 이미 "이전과 변한 게 없으면 평가를 건너뛰는" 스냅샷 비교 장치(`_last_global_snapshot`)를 갖추고 있음. 잔고 회복 후 매번 전체 후보를 처음부터 다시 계산하는 것이 아님. 따라서 실제 지연이 설계서 가정보다 미미할 가능성이 높음. 정량 측정 후 지연이 관찰되지 않으면 최적화 불필요(P24).

**왜**:
- `evaluate_buy_candidates`는 잔고 회복 시 매수 후보 재평가 → 매수 주문 발생 가능. 이 시점을 지연시키면 매수 타이밍이 변하여 매매 결과가 달라짐(safe-trade 최고 위험).
- 단, 함수 내부 연산량(O(buy_targets, 10~50) + 스냅샷 비교)이 실제로 틱 블로킹을 유발하는지는 정량 측정 필요. n이 작으면 최적화 불필요(P24).
- 매수 판단 결과 동일성: 내부 최적화가 판단 로직을 변경하지 않는 한 결과 동일. 2세션에서 내부 최적화 시 판단 로직 불변 점검.

**safe-trade 점검**:
- 매수 타이밍 변경: ❌ 없음(실행 시점 유지).
- 매수 판단 결과 변경: 내부 최적화 시에만 점검 필요. 2세션에서 확인.

### 결정 5: M-12 _broadcast_account DB 조회 — 관찰 대상 (위험도 중간)

**채택**: `build_positions_from_trades("real")` DB 조회가 실제로 브로드캐스트 지연을 유발하는지 2세션에서 정량 측정. 지연이 관찰되면 `buy_date` 주입만 별도 경로로 분리(브로드캐스트 본체는 `state.positions` 사용) 검토. 분리 시에도 매매 판단에 영향 없음(브로드캐스트는 UI 전송용).

> **사전조사 결과 반영 (2026-08-02)**: 설계서 전제 "매번 DB 거래내역 조회"가 실제 코드와 다름. 거래 기록은 앱 기동 시 한 번만 DB에서 불러와 메모리에 보관(`_ensure_loaded()` + `_loaded` 플래그), 이후 `build_positions_from_trades()`는 메모리에서 계산. 즉, 매번 DB를 조회하는 것이 아니라 메모리 연산. 따라서 화면 갱신 지연이 설계서 가정보다 훨씬 미미할 가능성이 높음. 정량 측정 후 지연이 관찰되지 않으면 분리 불필요(P24).

**왜**: `_broadcast_account`는 UI/WS 전송용. 매매 판단 경로가 아님. DB 조회 지연이 UI 갱신 지연만 유발(매매 영향 없음). 단, 사용자가 주문 체결 후 UI 지연을 인지하면 P21(사용자 투명성) 관점에서 개선 가치. 2세션에서 실제 지연 측정 후 결정.

### 결정 6: ~~H-01/H-02/H-04 큐 적체 모니터링 추가~~ — **기각 (위험도 낮음)**

> **기각 (2026-08-02 코드 기반 재조사 반영)**: 사용자 추가 질문 조사 결과, 큐 적체 모니터링 추가 자체가 불필요하다고 판단하여 기각.

**기각 사유**:
1. **실제 적체 발생 이력 없음**: QueueFull 예외 처리 코드는 4곳에 존재하나(방어적 프로그래밍), 실제 운영 중 발생 기록이 없음.
2. **단일 사용자 앱에서 큐 꽉 찰 가능성 매우 낮음**: tick_queue(maxsize=20000), broadcast_queue(maxsize=2000). 초당 1000틱이 들어와도 20초간 버퍼링 가능.
3. **매매 판단에 직접 영향 없음**: 큐 적체는 UI 전송용 경로. 매매 판단 경로가 아님.
4. **P21(사용자 투명성) 필수 아님**: 큐 적체는 "중요한 의사결정"이 아니므로 사용자 투명성 원칙의 엄격 적용 대상 아님.
5. **관찰된 문제 없는 모니터링 추가는 P24 위반 가능성**: 실제 적체 발생 전 모니터링 코드를 추가하는 것은 불필요한 추상화.
6. **장중 테스트로 충분**: 필요 시 디버그 엔드포인트(`/api/debug/queue-status`)만 추가하여 장중 테스트 시에만 사용하는 방식이 더 적합. 단, 이것도 본 설계서 범위 외이며 별도 요청 시 진행.

**대안**: 큐 적체 문제가 실제로 관찰되면 그 시점에 별도 설계서에서 다룸. 현재는 관찰된 문제가 없으므로 아무것도 하지 않음.
