# 설계서: 수익 카드 실현손익 전용화 + 당월 차트 비거래일 제거

> 상태: 작성 완료 (사용자 승인 대기)
> 작성일: 2026-07-30
> 관련 원칙: P10(SSOT), P20(폴백 금지), P21(사용자 투명성), P22(데이터 정합성), P23(일관성), P24(단순성)
> 관련 파일: `frontend/src/pages/profit-shared.ts`, `profit-detail-mount.ts`, `profit-math.ts`, `profit-detail-display.ts`, `profit-math.test.ts`, `canvas-profit-chart.ts`
> 관련 이전 설계: `docs/architecture_profit_cards_refactor_design.md` (수익 카드 4종 리팩토링 — 본 설계의 선행 작업)

## 1. 배경 및 목표

### 1.1 현재 상태 (문제)

앱 기동 테스트에서 수익현황/수익상세 페이지의 3가지 결함 발견:

1. **당일 손익 카드에 평가손익 합산** (핵심 원칙 위반)
   - `profit-shared.ts` `updateSummaryCards` 230줄: `dayPnl = realizedToday + evalPnl`
   - 보유종목 평가손익(`computeHoldingsSummary.evalPnl`)을 당일 실현손익에 합산
   - 미체결/평가손익(예: 300원)이 당일 카드에 표시되어 사용자 혼란
   - 당일 드릴다운 모달(`buildTodayDrilldownContent`)에도 "평가 손익 (현재 보유 — 최근 체결 기준)" 섹션으로 동일 평가손익 표시

2. **당월 차트 비거래일(빈 날짜) 표시** (가독성 저하)
   - 백엔드 `get_daily_summary`(trade_history.py 618-621줄)가 `use_date_range` 경로에서 주말/공휴일 포함 모든 달력일 생성
   - `buildChartFromDailySummary`가 `sell_count=0` → `pnl=null` → 빈 막대로 표시
   - 당월 카드 클릭 시 거래 없는 날이 빈 막대로 차트 가독성 저하

3. **빈 데이터 안내 라벨 불일치** (P23 일관성 위반)
   - 차트: "거래 내역이 없습니다"
   - 당일 드릴다운: "매도 내역이 없습니다." / "보유 종목이 없습니다."
   - 5거래일/당월 드릴다운: "5거래일 거래 내역이 없습니다." / "당월 거래 내역이 없습니다."
   - 누적 드릴다운: "거래 내역이 없습니다." / "입금 이력이 없습니다."

### 1.2 목표

1. 수익현황/수익상세의 모든 손익 카드/통계에서 평가손익 완전 배제, 오직 체결 완료된 실현손익만 표시
2. 당일 카드 = 오늘 매도 완료된 sellHistory의 실현손익 합계만 표시
3. 당일 드릴다운 모달에서 평가 영역 제거 (실현 영역만 표시)
4. 당월 차트에서 비거래일(매수·매도 모두 0인 날) 제외, 실제 거래 데이터 있는 거래일만 x축 표시
5. 빈 데이터 안내 라벨을 "거래 내역이 없습니다"로 통일 (입금 이력은 별개 개념이므로 유지)

### 1.3 비목표 (다루지 않는 것)

- **계좌현황 평가 3행 유지**: 보유 종목 평가금액/평가손익/평가수익률은 계좌현황 섹션에서 유지 (사용자 결정 — 핵심 원칙의 예외 영역)
- **보유종목 페이지 평가 유지**: `sell-position.ts`의 평가 계산은 유지 (핵심 원칙의 예외 영역)
- **공휴일 캘린더 동기화**: 백엔드 휴장일 캘린더를 프론트에 동기화하는 작업은 별도 후순위 (HANDOVER 미해결 문제)
- **백엔드 dailySummary 비거래일 생성 로직 수정**: 백엔드가 아닌 프론트 `buildChartFromDailySummary`에서 필터링 (P24 단순성 — 백엔드 의존 최소화)

## 2. 설계 방향

### 2.1 핵심 설계 결정

**결정 1: 당일 카드 평가손익 합산 제거**
- `updateSummaryCards` 당일 카드 계산식: `dayPnl = realizedToday + evalPnl` → `dayPnl = realizedToday`
- 사유: 핵심 원칙("모든 손익 카드는 실현손익만") 준수. 평가손익은 계좌현황/보유종목 페이지에서만 표시.
- 분모(`dayBaseAsset`)는 실현손익 기준으로 유지 (rate 계산에 사용).

**결정 2: 당일 카드 서브 텍스트 "최근 체결 기준" 라벨 제거**
- 평가손익이 제거되었으므로 "최근 체결 기준" 라벨 불필요 (실현손익은 체결 완료된 값).
- `profit-detail-mount.ts` `openSubText` 인수 `'최근 체결 기준'` → `''`로 변경.
- 개장 전 "개장 전" 라벨은 유지 (F-3-c).

**결정 3: buildTodayDrilldown 평가 영역 제거**
- `TodayDrilldownResult` 타입에서 `evalRows`/`evalTotal` 필드 제거 → `realizedRows`/`realizedTotal`만 반환.
- 사유: 당일 드릴다운 모달도 핵심 원칙 준수 (실현 영역만 표시).
- `computePositionValuation`/`computeHoldingsSummary`는 계좌현황·보유종목 페이지에서 계속 사용 (제거 아님).

**결정 4: buildTodayDrilldownContent 평가 섹션 제거**
- "평가 손익 (현재 보유 — 최근 체결 기준)" 섹션 제거.
- "당일 총 손익" 행 제거 (실현 합계만 표시하므로 중복).
- 실현 영역만 표시: "실현 손익 (오늘 매도)" + "실현 합계".

**결정 5: buildChartFromDailySummary 비거래일 필터링**
- `sell_count=0 && buy_count=0`인 행을 배열에서 제외 (filter 추가).
- 매수만 있거나 매도만 있는 날은 유지 (거래 데이터 존재).
- 사유: 백엔드 휴장일 캘린더 의존 없이 P24 단순성 부합. 공휴일 건너뛰기는 HANDOVER 후순위 항목이므로 별도 작업.

**결정 6: 빈 데이터 라벨 "거래 내역이 없습니다"로 통일**
- 차트 오버레이: "거래 내역이 없습니다" (기준 라벨, 유지)
- 당일 드릴다운: "매도 내역이 없습니다." → "거래 내역이 없습니다." / "보유 종목이 없습니다." → 유지 (다른 개념 — 보유종목은 거래내역이 아님)
- 5거래일/당월 드릴다운: "5거래일 거래 내역이 없습니다." / "당월 거래 내역이 없습니다." → "거래 내역이 없습니다."로 통일
- 누적 드릴다운: "거래 내역이 없습니다." (유지) / "입금 이력이 없습니다." (유지 — 별개 개념)

### 2.2 기각 방안

| 방안 | 기각 사유 |
|------|-----------|
| 백엔드 dailySummary 비거래일 생성 로직 수정 | 백엔드 의존 증가, 공휴일 캘린더 동기화 별도 작업 필요. 프론트 필터링이 P24 단순성 부합 |
| 계좌현황 평가 3행 제거 | 사용자 결정 — 계좌현황은 자산 구성 뷰이므로 평가 정보 유지가 실용적. 핵심 원칙의 예외 영역으로 명시 |
| 당일 드릴다운 평가 영역 유지 | 핵심 원칙 위반. 평가손익은 계좌현황/보유종목 페이지에서만 표시 |
| buildTodayDrilldown에서 positions/sectorStocks 매개변수 제거 | 타입 시그니처 변경 범위 최소화. 평가 영역 제거만으로 충분 (매개변수는 unused 경고만 발생 가능 → 제거 검토는 구현 단계에서 결정) |

## 3. 사용자 결정 항목

### 결정 A: 계좌현황 평가 3행 유지 여부
- **질문**: "계좌현황 섹션에 현재 유지중인 보유 종목 평가금액/평가손익/평가수익률 3행은 유지하는게 좋을까?"
- **사용자 답변**: (의견 요청)
- **에이전트 권고**: 유지 권장. 계좌현황은 잔고 중심 섹션이므로 평가 정보가 함께 있는 것이 자연스러움. 핵심 원칙의 예외 영역으로 명시.
- **최종 결정**: 계좌현황 평가 3행 유지 + 당일 카드/드릴다운에서만 평가손익 제거 (사용자 승인 "이대로 진행")

### 결정 B: 다단계 워크플로우 전환
- **질문**: "정량 기준(수정 파일 6개, 50줄 초과)을 초과합니다. 다단계 워크플로우로 전환할까요?"
- **사용자 답변**: "다단계로 진행"
- **최종 결정**: 다단계 워크플로우(설계→태스크→구현)로 진행

## 4. 아키텍처 원칙 부합 검토

| 원칙 | 부합 | 근거 |
|------|------|------|
| P10 (SSOT) | ✅ | 실현손익 계산 단일 소스 유지. 평가손익은 계좌현황/보유종목 페이지 SSOT로 분리 |
| P16 (살아있는 경로) | ✅ | 평가 영역 제거 후에도 buildTodayDrilldown 호출 경로 유지 (실현만 반환) |

| P21 (사용자 투명성) | ✅ | 당일 카드에 평가손익이 합산되어 사용자 혼란 발생 → 제거로 투명성 향상. "최근 체결 기준" 라벨 제거는 실현손익이 체결 완료값이므로 별도 라벨 불필요 |

| P23 (일관성) | ✅ | 빈 데이터 라벨 "거래 내역이 없습니다"로 통일. 핵심 원칙("실현손익만") 전 페이지 일관 적용 |
| P24 (단순성) | ✅ | buildTodayDrilldown 평가 영역 제거로 타입·렌더 단순화. 비거래일 필터링은 프론트 단독 처리 (백엔드 의존 최소화) |
| P25 (격리된 실패) | ✅ | 변경 범위가 수익 카드/드릴다운에 한정. 계좌현황·보유종목 페이지 영향 없음 |
