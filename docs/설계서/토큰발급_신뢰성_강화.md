## 1. 목표

1. **토큰 발급을 신뢰성 있는 선행 단계로 만든다** — 토큰은 잔고 조회·주문·확정 데이터 다운로드의 전제 조건이다. 토큰 발급 자체가 가장 약한 고리여서 후속 로직이 무용지물이 되는 구조를 끝낸다.
2. **일시적 네트워크 장애 후 자동 회복** — 수 초~수 분 내 회복되는 일시적 장애(DNS 해석 실패, 순간 단절 등) 시 앱 재시작 없이 백그라운드에서 자동으로 토큰을 재발급받아 정상 모드로 복귀한다.
3. **런타임 토큰 만료(401) 자동 복구** — API 호출 중 401 응답을 받으면 토큰을 자동 재발급 후 원 요청을 재시도한다. 현재는 만료 임박 사전 갱신만 있고 런타임 401 대응이 없다.
4. **두 증권사 재시도 패턴 일관성** — 키움·LS의 재시도 간격·횟수·지터 적용 방식을 통일한다. 현재 키움은 adaptive backoff, LS는 선형 증가로 패턴이 다르다.
5. **회복 시 사용자 투명성** — 토큰 회복 성공·실패를 화면에 반영한다. 현재 "연결 안됨 상태" 전환 후 회복되어도 화면에 자동 반영되지 않는다.
6. **일시 실패 vs 영구 실패 분기** — 토큰 발급 실패를 두 종류로 구분하여 대응을 다르게 한다. 일시적 장애(네트워크 단절·DNS·5xx·429·타임아웃)는 회복 루프로 자동 재시도하고, 영구 실패(키/시크릿 없음·인증 거부·invalid_client)는 연결 안됨 상태로 전환하여 사용자 액션을 유도한다. 현재는 실패 종류 구분 없이 3회 재시도 후 일괄 연결 안됨 상태 전환 — 일시 장애와 영구 장애가 같은 경로로 처리되어 일시 장애도 영구 전환되는 문제가 있다.

## 3. 문제 + 현재 구조

### 3.1 문제 상황 (2026-08-05 23:05 발생)

앱 시작 시 일시적 DNS 해석 실패(`nodename nor servname provided`)로 LS증권·키움증권 토큰 발급이 모두 실패. 두 증권사 모두 3회 5초 간격 재시도 후 포기 → "연결 안됨 상태"로 영구 전환. 이후 네트워크가 수 초 내에 회복되었음에도 앱 재시작 전까지 정상 모드로 복귀하지 못함.

동시에 확정 데이터 다운로드도 토큰 발급 실패로 중단 → 1,339종목 전부 오래된 데이터 상태로 유지 → 다음 날 저녁 예약 시간까지 재시도 없음.

### 3.2 현재 구조 — 토큰 발급 흐름

**시작 시 토큰 발급 (활성 broker 1개)**:
- `engine_loop.py`의 `_get_all_tokens_async`가 `settings["broker"]` 단일 증권사 토큰 발급
- 실패 시 `state.access_token = None` → 연결 안됨 상태 전환
- 이후 WS 연결 차단, AutoTradeManager 생성 생략, 잔고 조회 건너뜀

**확정 데이터 다운로드 시 토큰 발급 (Lazy Auth)**:
- `market_close_pipeline.py`의 `_run_confirmed_pipeline`이 `confirmed_data_broker`(빈 값이면 활성 broker) 토큰 발급
- 실패 시 파이프라인 계속 진행하나 토큰 필요 API는 실패

**토큰 발급 구현 (키움·LS 공통)**:
- 최대 3회 재시도, **5초 고정 선형 증가** (5s, 10s, 15s)
- 429 응답 시 추가 대기 (10초 기반)
- **지터(jitter) 없음** — 여러 인스턴스·재시도가 동시에 몰리면 재시도 폭주 위험
- **401 응답 감지 없음** — 429만 특별 처리, 401은 일반 HTTP 오류로 취급
- 예외 시 클라이언트 리셋(키움) 또는 단순 continue(LS)

**만료 임박 사전 갱신**:
- 키움: `is_expired_soon(buffer_seconds=3600)` — 만료 1시간 전 재발급
- LS: `is_expired(buffer_seconds=3600)` — 만료 1시간 전 재발급
- 이것만으로 런타임 401(서버가 토큰을 조기 무효화하는 경우)을 잡지 못함

### 3.3 왜 현재 구조가 잘못되었는가

1. **회복 경로 부재 (P16 위반)**: 시작 시 3회 재시도 후 포기하면 살아있는 회복 경로가 없다. 일시적 장애는 수 초~수 분 내 회복되는 경우가 대부분인데, 앱 재시작 전까지 정상 모드로 돌아갈 수 없다.
2. **401 자동 복구 부재**: API 호출 중 401을 받으면 (a) 토큰이 서버에 의해 조기 무효화, (b) 만료 임박 체크와 실제 만료 사이 창, (c) 서버 오류 — 이 경우 자동 재발급이 표준 패턴이나 현재 없다.
3. **재시도 패턴 불일치 (P23 위반)**: 키움은 adaptive backoff(`_api_delay` 자동 조정), LS는 고정 선형 증가. 같은 "토큰 발급" 기능이 두 증권사에서 다른 패턴으로 구현.
4. **지터 부재**: 고정 간격 재시도는 여러 재시도가 동시에 몰리는 retry storm 위험. 표준 패턴은 지수 백오프 + 지터.
5. **사용자 투명성 부분 위반 (P21)**: 연결 안됨 상태 전환은 화면에 반영되나, 회복 시 자동 반영 경로가 없다 (회복 자체가 없으므로).

### 3.4 표준 패턴 대비 진단 (웹 조사 기반)

키움·LS 공식 가이드 + 자동매매 커뮤니티 모범 사례 + 분산 시스템 표준(OAuth2/OIDC):

| 항목 | 표준 패턴 | 현재 상태 | 진단 |
|---|---|---|---|
| 토큰 캐싱 | 1회 발급 → 메모리 캐싱 → 만료 임박 갱신 | 충족 | ✅ |
| 재시도 간격 | 지수 백오프 + 지터 | 5초 고정 선형, 지터 없음 | ⚠️ |
| 401 자동 재발급 | 401 감지 시 재발급 후 원 요청 재시도 | 없음 | ❌ |
| 시작 실패 후 회복 | 백그라운드 회복 루프 (lazy init + retry) | 없음 | ❌ |
| 두 증권사 패턴 일관성 | 공통 상수·패턴 | 키움 adaptive / LS 선형 | ⚠️ |
| 실패 분류 (일시 vs 영구) | 일시 실패는 재시도, 영구 실패는 즉시 포기 + 사용자 액션 | 분류 없이 일괄 재시도 후 연결 안됨 상태 | ❌ |

> **실패 분류의 검증 근거**: Microsoft Entra(MSAL silent acquisition + 일시 실패 백오프), Spring WebClient OAuth2(토큰 서버 다운 시에만 서킷브레이커, 일시 실패는 백오프), Money Forward Split Session(일시 오류 자동 백오프, 영구 실패만 사용자 액션), Truto(영구 revoke 시 graceful degrade), Azure/Woyable(401은 재시도 금지, 재시도는 일시 실패 전용). 5개 출처가 "일시 실패 vs 영구 실패 구분"으로 수렴.

## 4. 채택안 + 이유

### 결정 1: 지수 백오프 + 지터 적용 (시작 시 재시도)

**채택**: 두 증권사의 토큰 발급 재시도를 **3회, 지수 백오프 + 풀 지터(1s→2s→4s 기반 + 랜덤)**로 통일. 재시도 상수는 `constants.py`에 공통 상수로 이동.

**왜**: 
- 고정 5초 선형 증가는 일시적 DNS 장애(수 초~수십 초 회복)를 잡기에 간격이 짧고, 동시에 retry storm을 유발할 수 있음.
- 지수 백오프(1→2→4초)는 짧은 장애는 1~2회 내에 잡고, 긴 장애는 점진적 대기로 서버 부하 완화.
- 풀 지터(full jitter)는 재시도 폭주 방지의 표준 기법 — 분산 시스템/OAuth2 커뮤니티 권장 패턴.
- 상수를 `constants.py`로 이동하면 두 증권사가 같은 상수를 참조하여 P10(SSOT)·P23(일관성) 부합.

### 결정 2: 시작 실패 후 백그라운드 회복 루프 (일시 실패 전용)

**채택**: 시작 시 3회 재시도 전부 실패 시, **실패 종류가 일시적일 때만** 백그라운드 회복 루프(30초 간격, 최대 10회)를 `schedule_engine_task`로 생성. 회복 성공 시 `state.access_token` 설정 + `broadcast_engine_status`로 화면에 정상 모드 전환 알림. 최대 10회(약 5분) 후에도 실패 시 회복 루프 종료 — 연결 안됨 상태 유지 + "수동 재시작 필요" 안내. **영구 실패(키 오류·인증 거부)는 회복 루프 진입 없이 즉시 연결 안됨 상태 전환** (결정 6 참조).

**왜**:
- 일시적 네트워크 장애는 수 초~수 분 내 회복이 대부분. 30초 간격 10회(약 5분)면 현실적 일시 장애의 대부분을 커버.
- 영구 실패(키 오류 등)를 회복 루프에 넣으면 의미 없는 재시도가 5분간 자원 소모 — 실패 분류(결정 6)로 사전 차단.
- `schedule_engine_task` + `engine_scheduled_tasks`는 기존 백그라운드 태스크 패턴 (P23 공통 자산 재사용).
- 회복 성공 시 `broadcast_engine_status`로 화면 반영 — P21(사용자 투명성).
- 무한 재시도가 아닌 10회 상한 — P24(단순성), 영구 장애 시 자원 낭비 방지.
- 회복 루프는 백그라운드이므로 다른 기능 차단하지 않음 — P25(격리된 실패).

### 결정 3: 401 자동 재발급 (런타임)

**채택**: 키움 `_call_api`·LS `_place_order` 등 REST 호출 래퍼에서 **401 응답 감지 시 토큰 재발급 후 원 요청 1회 재시도**. 재발급 실패 시 원 요청 실패 처리.

**왜**:
- 만료 임박 사전 갱신(`_ensure_token`)은 토큰이 정상적으로 만료되는 경우만 커버. 서버가 토큰을 조기 무효화하거나 만료 창을 놓친 경우 401이 발생.
- 401 감지 → 재발급 → 1회 재시도는 OAuth2 클라이언트 표준 패턴 (키움·LS 공식 가이드·커뮤니티 모범 사례).
- 1회만 재시도 — 무한 루프 방지 (P24). 재발급 실패면 진짜 인증 문제이므로 사용자 조치 필요.
- 기존 `_ensure_token` 호출 전에 401이 아니라 호출 후 401을 잡는 구조 — `_call_api` 래퍼 내부에 401 분기 추가.

### 결정 4: 공통 재시도 상수를 `constants.py`로 이동

**채택**: 토큰 발급 재시도 관련 상수(최대 재시도 횟수, 백오프 기준 간격, 지터 비율, 회복 루프 간격·최대 횟수)를 `constants.py`에 정의. 키움·LS 양쪽이 같은 상수를 참조.

**왜**:
- 현재 키움은 클래스 변수(`_API_MAX_RETRIES` 등), LS는 하드코딩(`max_retries = 3`)으로 분산 — P10(SSOT) 위반.
- `constants.py`는 이미 KST·수수료 등 공통 상수의 SSOT. 재시도 상수도 같은 위치에서 관리하여 P23(일관성) 부합.
- 사용자 설정이 아닌 시스템 내부값이므로 `settings_defaults.py`가 아닌 `constants.py` (P24 단순성 — 설정 노출하지 않음).

### 결정 5: 회복 시 화면 알림 (기존 이벤트 활용)

**채택**: 회복 루프 성공 시 기존 `broadcast_engine_status` 호출. 새 이벤트·새 UI 추가하지 않음.

**왜**:
- `broadcast_engine_status`는 이미 `broker_statuses[broker_id].token_valid`·`degraded_mode`를 포함. 프론트엔드는 이 값을 수신하여 연결 상태 표시에 활용 가능.
- 새 이벤트·새 UI는 비목표 (P24 단순성, 프론트 변경 최소화).
- 회복 성공·실패 로그도 백엔드 로그 창에 표시 — P21(사용자 투명성).

### 결정 6: 일시 실패 vs 영구 실패 분기 처리

**채택**: 토큰 발급 실패를 두 종류로 분류하여 대응을 분기한다.

| 실패 종류 | 판단 기준 | 동작 |
|---|---|---|
| **일시적 실패** | 네트워크 예외(DNS 해석 실패·연결 거부·타임아웃), HTTP 5xx, HTTP 429, 응답 파싱 실패 | 3회 지수 백오프+지터 재시도 → 전부 실패 시 회복 루프 진입(결정 2) |
| **영구 실패** | API 키/시크릿 없음, HTTP 401/403(인증 거부), 응답 내 인증 거부 코드(키움 8030 등), invalid_client | 재시도 없이 즉시 연결 안됨 상태 전환 + 사용자 액션 안내("API 키 확인 필요") |
| **회복 루프 최대 횟수 도달 후 실패** | 10회(약 5분) 후에도 일시 실패 지속 | 연결 안됨 상태 전환 + "수동 재시작 필요" 안내 |

**왜**:
- 현재는 실패 종류 구분 없이 3회 재시도 후 일괄 연결 안됨 상태 전환. 일시적 DNS 장애(수 초 회복)와 영구적 키 오류(사용자 조치 필요)가 같은 경로로 처리되어, 일시 장애도 영구 전환되는 문제가 있었다.
- 웹 조사 검증(5개 출처 — Microsoft Entra·Spring WebClient OAuth2·Money Forward·Truto·Azure/Woyable): "일시 실패는 백오프 재시도, 영구 실패는 즉시 포기 + 사용자 액션"이 분산 시스템/OAuth2 표준 패턴으로 수렴.
- 영구 실패(키 오류)를 5분간 재시도하는 것은 의미 없는 자원 소모 — 사용자가 API 키를 수정하지 않으면 절대 성공하지 않음.
- 분류 기준은 HTTP 상태 코드 + 예외 타입 + 응답 내 인증 거부 코드로 기계적 판정 가능 — 휴리스틱 아님.
- 401은 "토큰이 이미 발급된 후 런타임에 무효화된 경우"(결정 3)와 "발급 자체가 거부된 경우"(본 결정)를 구분 — 런타임 401은 재발급, 발급 단계 401은 영구 실패.

### 결정 7: 공통 함수 추출 및 클래스 구조 정리 (중복 로직 제거)

**채택**: 키움·LS 양쪽에 중복된 토큰 발급 재시도·백오프·실패 분류·401 재발급 로직을 공통 함수로 추출하여 신규 파일 `backend/app/core/auth_utils.py`에 배치. 두 증권사 클래스는 공통 함수를 호출하는 얇은 래퍼로 정리 — 함수명·동작을 통일하여 구조 일관성 확보.

**추출 대상 공통 로직** (중복 제거):
- 지수 백오프+풀 지터 대기 시간 계산 — 양쪽에 동일 공식이 하드코딩될 것을 공통 함수 `compute_backoff_delay(attempt, base, jitter_ratio) -> float`로 추출
- 실패 분류 판정 — HTTP 상태 코드·예외 타입·응답 키워드로 일시/영구 실패를 판정하는 공통 함수 `classify_token_failure(status_code, exception, response_keywords) -> str` 추출. 판정 기준은 결정 6의 상수 집합 참조
- 401 재발급 후 1회 재시도 패턴 — 공통 헬퍼 `retry_once_on_401(issue_token_fn, request_fn, ...) -> tuple` 추출. 키움 `_call_api`·LS `_place_order` 양쪽에 동일 패턴 적용
- 회복 루프 간격·상한 판정 — `should_continue_recovery(attempt, max_attempts) -> bool` 등 작은 헬퍼 (필요 시)

**증권사 고유 로직 (각 클래스에 잔류)**:
- 호출 주소·요청/응답 포맷 (키움 JSON / LS form 데이터)
- 인증 에러 응답 코드/키워드 (키움 "8030" / LS "invalid_client" 등) — 공통 분류 함수에 키워드 목록을 인자로 전달
- 토큰 정보 데이터클래스 (`TokenInfo` / `LsTokenInfo` — 만료 시각 계산 방식이 다름)
- 클라이언트 관리 (`_get_client` / `ensure_client` — 세부 구현 차이)

**왜**:
- 현재 두 증권사의 `_issue_token`은 재시도 루프 구조가 거의 동일하나 각자 하드코딩 — 결정 1·4·6을 양쪽에 개별 적용하면 중복이 2배로 늘어남 (P10 SSOT 위반, P23 일관성 위반).
- 공통 함수 추출로 "재시도 정책·실패 분류·401 처리"의 단일 진실 소스를 만들면, 향후 재시도 간격 변경·실패 분류 기준 추가 시 한 곳만 수정 — P10·P23 부합.
- 범용 라이브러리(전 프로젝트 공용)가 아닌 "토큰 발급 전용 공통 함수"로 한정 — 과잉 추상화 방지 (P24). 적용 범위는 토큰 발급·재발급·회복 루프로 명시적 제한.
- 두 클래스의 함수명 통일(`_issue_token` 반환값 구조·`_ensure_token`/`ensure_token` 이름·`get_access_token`/`get_token` 이름) — P23 일관성. 단, 기존 호출부 호환성을 위해 래퍼 유지 (한 번에 전면 개명이 아닌 점진 정리).
- `auth_utils.py`는 `core/` 디렉터리에 배치 — `constants.py`·`broker_urls.py` 등 기존 공통 모듈과 같은 위치 (P23 일관성).

## 5. 기각안 + 사유

| 방안 | 기각 사유 |
|---|---|
| 회로 차단기(Circuit Breaker) 도입 | 토큰 발급은 주문과 달리 연속 실패 확률이 낮음 (네트워크 장애·키 오류 정도). 10회 상한 회복 루프로 충분. 기존 주문용 서킷브레이커와 도메인이 다름. 과잉 추상화 (P24) |
| 설정 기반 재시도 파라미터 (`settings_defaults.py`) | 재시도 횟수·간격은 사용자가 조작할 필요 없는 시스템 내부값. 설정 노출하면 오히려 잘못된 값으로 장애 유발 가능 (P24 단순성) |
| 영구 백그라운드 토큰 갱신 루프 | 만료 임박 사전 갱신(`_ensure_token`)이 이미 있으므로 중복. 회복 루프는 시작 실패 후에만 동작하는 유한 루프로 충분 (P24) |
| 프론트엔드 "토큰 회복 중" 전용 UI | 기존 `broadcast_engine_status`의 `token_valid`·`degraded_mode`로 충분. 새 UI는 비목표 (P24, 프론트 변경 최소화) |
| 범용 재시도/백오프 라이브러리 (전 프로젝트 공용) | 토큰 발급 전용 공통 함수(`auth_utils.py`)는 채택(결정 7)하되, 모든 도메인에서 쓰는 범용 라이브러리는 과잉 추상화 (P24). 공통 함수 적용 범위를 토큰 발급·재발급·회복 루프로 한정 |
| 시작 시 토큰 발급을 블로킹 게이트로 변경 (토큰 없으면 앱 시작 안 함) | 현재 "연결 안됨 상태"로 기동하는 구조는 P25(격리된 실패)에 부합 — 토큰 없어도 시세·화면은 동작. 블로킹하면 일시 장애 시 앱 자체가 안 켜짐. 회복 루프가 더 나은 해결 |
| confirmed_data_broker Lazy Auth에도 회복 루프 적용 | 확정 데이터 다운로드는 장마감 1회성 배치. 시작 시 활성 broker 토큰 회복이 우선. Lazy Auth는 다음 날 예약 시간에 자연 재시도됨. 범위 확장은 과잉 (P24) |
| 모든 실패를 동일하게 재시도 (실패 분류 없음) | 현재 구조. 일시 장애와 영구 장애가 같은 경로로 처리되어 일시 장애도 영구 전환되는 문제. 검증된 표준 패턴(5개 출처)이 "일시 vs 영구 분류"를 권장. 분류 없는 재시도는 영구 실키 시 자원 낭비 (P24 위반) |

| P25 (격리된 실패) | ✅ | 회복 루프는 백그라운드. 다른 기능 차단하지 않음. 401 재발급 실패 시 해당 요청만 실패 |

## 8. 위험도 산정

**등급**: 중간

**근거**:
- 토큰은 주문·잔고 조회 경로에 직접 영향. 토큰 회복 시 자동으로 주문 가능 상태로 승격되므로 실전 모드에서 주문이 나갈 수 있음.
- 단, 매매 판단 로직 자체는 변경하지 않음 — 토큰이 회복되면 기존 주문 경로가 정상 동작하는 것뿐.
- 401 자동 재발급은 런타임 동작 변경 — 기존에 401 시 실패하던 요청이 성공으로 바뀜. 부작용 가능성 낮으나 검증 필요.
- 두 증권사 재시도 패턴 변경 — 기존 5초 고정에서 지수 백오프+지터로 변경. 타이밍 변화 있으나 동작 호환성 문제 없음.
- 공통 함수 추출(결정 7)로 두 증권사 클래스 구조 변경 — 기존 클래스 내부 로직을 `auth_utils.py` 공통 함수 호출로 교체. 래퍼 구조 유지로 외부 호출부 호환성 유지되나, 내부 경로 변경으로 회귀 가능성 존재. 테스트로 검증 필수.

**비개발자용 3줄 요약**:
- 일시적 인터넷 장애 후 앱을 껐다 켜지 않아도 자동으로 복구되도록 합니다.
- 토큰(증권사 로그인 증명)이 만료되거나 거부당했을 때 자동으로 다시 발급받도록 합니다.
- 일시적 장애(인터넷 단절)와 영구 장애(API 키 오류)를 구분하여, 일시 장애는 자동 재시도·영구 장애는 즉시 안내로 분리 대응합니다.
- 두 증권사(키움·LS)의 재시도 방식을 통일하고, 회복 시 화면에 상태가 반영되도록 합니다.

## 9. 완료 기준

### 사용자 관점 수용 조건

- [ ] 앱 시작 시 일시적 네트워크 장애(DNS 해석 실패 등)가 발생한 후, 네트워크가 회복되면 앱 재시작 없이 1~5분 내 자동으로 정상 모드(잔고 조회·주문 가능)로 전환된다.
- [ ] 정상 모드 전환 시 화면에 연결 상태가 "정상"으로 표시된다 (기존 연결 상태 표시 활용).
- [ ] API 호출 중 토큰 만료(401)가 발생하면 자동으로 토큰을 재발급받아 원 요청이 성공적으로 완료된다 (사용자가 체감하지 못함).
- [ ] 두 증권사 모두 동일한 재시도 패턴(횟수·간격·지터)으로 동작한다.
- [ ] 회복 루프가 10회(약 5분) 후에도 실패 시 종료되며, 백엔드 로그에 "수동 재시작 필요" 메시지가 표시된다.
- [ ] 영구 실패(API 키 오류·인증 거부) 시 회복 루프에 진입하지 않고 즉시 연결 안됨 상태로 전환되며, 사용자에게 "API 키 확인 필요" 안내가 표시된다.
- [ ] 일시 실패는 회복 루프로, 영구 실패는 즉시 연결 안됨 상태로 분기되어 두 경로가 명확히 구분된다.
- [ ] 기존 동작(정상 시작 시 즉시 토큰 발급·주문·잔고 조회)은 회귀 없이 유지된다.
- [ ] 키움/LS 토큰 발급 관련 중복 로직이 공통 함수로 추출되었다 (재시도 루프·백오프 계산·실패 분류·401 재발급 패턴이 `auth_utils.py` 단일 소스).
- [ ] 두 증권사 클래스가 일관된 구조를 갖게 되었다 (공통 함수 호출 구조 통일, 증권사 고유 로직만 각 클래스에 잔류).

### 검증 게이트
- 위험도 중간 → 3계층 검증 (기계적 검증 + 요청 의도 사후 확인 + 독립 검증자).
- 백엔드 수정 → pytest + 런타임 기동 검증.
- 401 처리·회복 루프·재시도 패턴 변경 → 신규 회귀 테스트 작성 (기존 테스트 없음).
- 실패 분류(일시/영구) 분기 → 일시 실패는 회복 루프 진입, 영구 실패는 즉시 연결 안됨 상태 전환을 각각 별도 테스트 케이스로 검증.
