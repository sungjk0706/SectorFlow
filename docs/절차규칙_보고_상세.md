### 사용자 보고서 표준 형식 (상황별 선택 가이드)

> **목적**: 사용자가 코딩 지식 없이도 한눈에 파악할 수 있도록, 보고는 표 형태를 우선한다. 본 형식은 `규칙 0-8`과 `세션 보고 포맷`(섹션4)의 구체적 표준(P10 SSOT)이다. 각 `SKILL.md`는 본 형식을 참조하고, 스킬별 추가 항목만 행(row)으로 추가한다. 보고는 추가 결정이 필요한 경우에만 승인 요청 역할을 한다. 작업 완료 보고는 종료 알림이다.
>
> **표 형식 강제 (완료 보고·단계 완료 보고·중단·보류 보고)**: 세션 종료 계열 보고는 반드시 표 형식으로만 작성. 이모지 요약 형식은 "1줄 질답·진행 중 간단 알림"에만 허용되며 완료 보고에는 사용 불가. 표 형식 강제 이유 3가지:
> 1. **항목 누락 기계적 방지** — 표 칸이 비어 있으면 한눈에 보여 누락 즉시 발견.
> 2. **한눈 상태 파악** — 사용자가 코딩 지식 없이도 표만 보고 전체 상태 파악 가능.
> 3. **봉인 규칙 명확 종결** — 세션 종료 체크리스트 표의 마지막 행(사용자 결정)으로 보고가 명확히 종결되어 완료 후 추가 질문·제안이 붙을 수 없음.
>
> **표 선택 가이드 (세션 종료 계열 보고 = 표 강제, 작업 성격에 따라 관련 표 선택)**: 아래 7개 표를 기본 메뉴로 제공하되, 세션 유형에 따라 관련 없는 표는 생략 가능. 단, 생략 시에도 "없음"이 아닌 "해당 없음"으로 명시하거나 해당 표를 아예 빼는 것을 허용. **세션 종료 체크리스트(7번)는 세션 종료 계열 보고 시 반드시 포함 — 생략 불가.**
>
> | 세션 유형 | 기본 선택 표 | 비고 |
> |---|---|---|
> | 코드 수정 완료 세션 | 7개 표 전부 기본 (작업 규모 작으면 검증 결과 표·커밋 표 등 관련 없는 표 생략 가능. 단, 세션 종료 체크리스트는 생략 불가) | 변경 내용·원칙·검증·최종 판별·커밋·설계 완료 기준(다단계 시)·세션 종료 체크리스트 |
> | 조사/의견 제시 세션 | 변경 내용 표(변경 전 컬럼만) + 최종 판별 표(진행 가능/중단·보류) + 세션 종료 체크리스트 | 분석 내용에 맞춰 추가 표 자유롭게 구성 |
> | 1줄 질답·진행 중 간단 알림 | 표 형식 생략, 이모지 요약 또는 간결 텍스트 허용 | 세션 종료 계열 보고가 아닌 경우만 해당 |
>
> **7개 표 (기본 메뉴)**: 변경 내용 표 · 아키텍처 원칙 판별 표 · 검증 결과 표 · 최종 판별 표 · 커밋 및 핸드오버 표 · 설계 완료 기준 충족 표(다단계 작업 시) · **세션 종료 체크리스트(필수)**.
>
> **추가 표 허용**: 작업 성격에 따라 기본 7표 외에 추가 표를 포함할 수 있다. 예: 조사 보고서의 '조사 범위 표'·'비교 분석 표', 다단계 작업의 '단계별 진행 표', 영향도 분석의 '영향 도메인 표' 등. 추가 표는 기본 표 뒤에 배치하되, 기본 표의 행을 중복 생성하지 않고 별도 관점을 다루는 경우에만 추가.
>
> **표 작성 공통 원칙**: `ARCHITECTURE.md` 부록 B 표준 용어 사전 준수 — "업종" not "섹터", "종목" not "주식", "매수 후보" not "바이 리스트", "보유 종목" not "홀딩/포지션", "매수" not "Buy/구매", "매도" not "Sell/판매".

> **다단계 작업 단계 표시 (강제 — 태스크 파일 있는 작업)**: 태스크 파일(`docs/태스크/*.md`)이 있는 다단계 작업의 보고 제목은 `전체 N단계 중 N단계 시작` / `전체 N단계 중 N단계 완료` 형식으로 작성. N(전체 단계 수)과 N(현재 단계)은 태스크 파일 기준. 단계가 추가·병합·삭제되면 **태스크 파일을 먼저 갱신**한 뒤 보고에 반영 — 태스크 파일과 보고의 단계 수가 항상 일치해야 함(P10 SSOT · P23 일관성). 태스크 파일 없는 단발 작업·조사 세션은 기존 형식(세션 한글명만) 유지.

> **이모지-표 관계 (중복 금지 — 규칙 0-8 3항 + 표 형식 강제)**: 세션 종료 계열 보고(완료·단계 완료·중단·보류)는 반드시 표 형식만 사용 — 이모지 요약 줄 사용 금지. 이모지 요약 줄은 "1줄 질답·진행 중 간단 알림"에만 허용. 표를 쓸 때 각 이모지가 담당하는 항목:
> - `💡 변경내용` → **변경 내용 표**
> - `✅ 원칙` → **아키텍처 원칙 판별 표**
> - `⚠️ 경고` → **최종 판별 표**의 '경고/특이사항' 행
> - `📦 커밋` / `🚀 푸시` / `📝 HANDOVER` → **커밋 및 핸드오버 표**
> - `검증 결과 표`는 `✅ 원칙` 표 다음 또는 별도로 배치(P21 사용자 투명성 강화).

#### 1. 변경 내용 표

| 항목 | 변경 전 (문제) | 변경 후 (해결) |
|---|---|---|
| 문제/필요성 | <기존 문제, 사용자가 겪은 화면 증상, 또는 이 작업이 필요해진 이유 — 일반 사용자 용어> | — |
| 근본 원인 | <실제 코드/설정 근본 원인, 내부 분석 시 파일:줄번호> | <해결된 근본 원인 요약> |
| 수정 방안 | — | <구체적 수정 내용, 화면에서 어떻게 달라지는지> |
| 개선 결과 | — | <이 작업으로 사용자가 얻는 이점 — 무엇이 어떻게 나아지는가> |
| 영향 범위 | — | <영향 받는 화면·기능·종목/업종 범위> |

> **작성 요령**: '변경 전'과 '변경 후'가 좌우로 바로 비교되도록 작성. 사용자가 확인할 수 있는 화면 변화를 먼저 기술.
> - **'문제/필요성' 행**: 버그 수정(사용자가 겪은 화면 증상)·사전 예방(잠재 위험)·개선 작업(왜 필요해졌는지) 모두 수용. 증상이 없는 작업에서 "없음"으로 비우지 말고 작업 필요성을 한 줄로 명시 — 사용자가 "왜 이 작업을 했는가"를 보고만 보고 이해하는 유일한 행.
> - **'개선 결과' 행**: '수정 방안(무엇을 바꿨는가)'과 구분되는 '사용자가 얻는 이점(무엇이 개선되는가)'. 화면 변화가 없는 내부 개선도 "화면 변화 없음(내부 개선: <이점>)" 형태로 명시.
> - **보고 단계별 자연 분리**: 사전조사 보고(규칙 0-8)에서는 '변경 전' 컬럼('문제/필요성'·'근본 원인')을 먼저 채우고, 세션 완료 보고에서 '변경 후' 컬럼('수정 방안'·'개선 결과'·'영향 범위')을 채운다 — 동일 표가 보고 단계 양쪽에 일관 적용.

#### 6. 설계 완료 기준 충족 표

> 다단계 작업(설계서 → 태스크 → 구현)에서만 해당. 단일 세션 수정·조사 세션은 "해당 없음". 작업 완료 체크리스트 1단계 의미적 검증 항목 4("설계서 완료 기준 모두 충족?")의 보고 단계 연결 — 0절 역할 원칙 "검증=설계 완료기준 따른다" + "사용자 보고는 결과·상태를 알리고 필요한 경우에만 결정받는다" 통합.

| 설계 완료 기준 | 충족 | 비고 |

| <설계서 완료 기준 항목 2> | ✅/⚠️ | <근거 1줄, 또는 미완료 사유> |
| ... | ... | ... |

> **작성 요령**: 설계서 "완료 기준" 섹션의 항목을 그대로 나열. ⚠️ 미완료 시 사유 명시 — 사용자가 승인 여부 판단하는 핵심 정보. 모두 ✅인 경우도 근거 1줄 필수 (형식적 체크 방지).

#### 7. 세션 종료 체크리스트 (종료 또는 필요한 결정)

> **보고서 마지막에 반드시 배치** — 작업 결과와 종료 상태를 사용자가 알 수 있게 하는 표. `작업 완료`와 `단계 완료·대기`에서는 승인 요청 없이 마무리하고, `중단·보류`에서만 재개에 필요한 결정을 적는다. 규칙 0-7(커밋/푸시/HANDOVER 독립 줄 명시)은 본 체크리스트 표의 행으로 충족 — 세션 종료 계열 보고는 표 형식 강제이므로 이모지 독립 줄은 1줄 질답·진행 중 간단 알림에만 적용.

| 항목 | 내용 |
|---|---|
| 검증 | ✅ 통과 / ❌ 실패(사유) — 기계적 + 의미적(작업 완료 체크리스트 1단계) |
| Git Commit | 완료(<사용자용 요약>) / 불필요(변경 없음) — 상세 식별자는 내부 인계 문서에만 기록 |
| HANDOVER 갱신 | 완료 / 보류(사유) / 갱신 없음(코드 수정 없음 — 규칙 0-6-2 예외) |
