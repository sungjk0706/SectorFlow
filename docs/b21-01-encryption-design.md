# B21-01 암호화 fail-closed 설계

- **상태**: 설계 완료, 구현 전
- **작성일**: 2026-07-26
- **대상**: Fernet 키 미설정·오류 시 민감정보 평문 저장/복호화를 허용하는 경로
- **관련 원칙**: P10(SSOT), P16(살아있는 경로), P20(폴백 금지), P21(사용자 투명성), P22(데이터 정합성), P23(일관성), P25(격리된 실패)
- **다음 단계**: 태스크 파일 작성 세션에서 이 설계를 실행 가능한 태스크로 분해

## 1. 목표와 범위

### 1.1 목표

1. 모든 민감정보 저장 경로가 동일한 암호화 검사를 통과하도록 한다.
2. Fernet 키가 없거나 유효하지 않으면 민감정보를 평문으로 저장하지 않는다.
3. 일반 설정은 암호화 상태 때문에 전체적으로 차단하지 않는다.
4. 키 없음, 키 오류, 암호화/복호화 실패를 `None`·빈 문자열·입력값 반환으로 뭉개지 않는다.
5. 사용자가 설정 화면에서 암호화 상태와 저장 차단 사유를 알 수 있게 한다.
6. 실전 브로커 연결·주문은 필요한 인증정보를 안전하게 읽을 수 있을 때만 허용한다.

### 1.2 범위

- 포함:
  - `backend/app/core/encryption.py`의 암호화·복호화 상태 모델
  - `backend/app/core/settings_file.py`의 전체 저장·증분 저장 경로
  - `backend/app/core/settings_store.py`와 설정 API의 오류·상태 전달
  - 일반설정 UI의 암호화 상태 표시와 저장 실패 안내
  - 관련 백엔드·프론트엔드 테스트
  - 기존 평문/손상 암호문 처리 정책
- 제외:
  - Fernet 알고리즘 자체 교체
  - 즉시 키 회전 기능
  - `stocks.db` 스키마 변경
  - DB 파일 자체의 암호화
  - 암호화 키를 DB에 저장하는 기능

## 2. 현재 실행 경로와 문제

### 2.1 민감 필드 SSOT

민감 필드 목록은 현재 `backend/app/core/settings_file.py`의 `_ENCRYPT_FIELDS`에 단일 정의되어 있다.

현재 대상:

- `kiwoom_app_key`
- `kiwoom_app_secret`
- `ls_app_key`
- `ls_app_secret`
- `telegram_bot_token_test`
- `telegram_bot_token_real`

계좌번호는 현재 암호화 대상이 아니며, 별도 정책 변경 없이는 이번 작업에서 암호화 대상에 추가하지 않는다.

### 2.2 저장 경로 불일치

- 전체 저장 경로에는 `_encrypt_field_or_raise()`가 있어 암호화 실패 시 평문 저장을 차단한다.
- 일반설정의 증분 저장 경로 `apply_settings_updates()` → `save_selected_settings()`는 `encrypt_value()`의 반환값이 있으면 저장할 수 있다.
- `encrypt_value()`는 Fernet이 없거나 암호화 중 예외가 발생하면 평문을 반환한다.

따라서 B21-01의 근본 원인은 암호화 함수의 폴백뿐 아니라 **저장 경로별 정책 불일치**다. 모든 저장 경로가 동일한 엄격한 저장 정책을 사용해야 한다.

### 2.3 복호화 경로 불일치

현재 `decrypt_value()`는 다음 상황에서 입력값을 그대로 반환할 수 있다.

- Fernet 키 없음
- Fernet `InvalidToken`

이 때문에 암호문, 평문 레거시 값, 키 부재, 잘못된 키를 호출부가 구분할 수 없다. 복호화 결과는 명시적인 상태를 가져야 한다.

## 3. 암호화 상태 내부 표현

상태는 **키 상태**와 **개별 민감값 상태**를 분리한다. 키 상태 하나만으로는 기존 데이터가 평문인지, 암호문이 손상됐는지 표현할 수 없기 때문이다.

### 3.1 키 상태

내부 열거형의 논리적 값은 다음으로 정의한다. 실제 Python 이름은 태스크 세션에서 기존 네이밍과 함께 확정한다.

| 논리값 | 의미 | 저장 허용 |
|---|---|---|
| `available` | 설정된 키로 Fernet 인스턴스를 만들 수 있음 | 허용 |
| `missing` | 키가 비어 있거나 설정되지 않음 | 민감정보 저장 금지 |
| `invalid` | 키가 있으나 형식·파생·Fernet 초기화에 실패함 | 민감정보 저장 금지 |

`missing`과 `invalid`는 UI에 별도로 표시한다. 사용자가 키를 새로 설정해야 하는지, 기존 설정이 잘못되었는지 구분할 수 있어야 한다.

키 원문, 파생 키, 예외 원문에 민감정보가 포함될 가능성이 있으므로 API 응답·로그·UI에 노출하지 않는다.

### 3.2 민감값 상태

개별 필드의 논리적 상태는 다음으로 정의한다.

| 논리값 | 의미 | UI/동작 |
|---|---|---|
| `empty` | 값이 없음 | 저장할 값 없음 |
| `encrypted` | 암호문을 정상 복호화할 수 있음 | 정상 |
| `plaintext_legacy` | DB에 기존 평문이 있음 | 새 평문 저장 금지, 명시적 재저장 때 암호화 |
| `key_unavailable` | 암호문이 있으나 키가 없음/유효하지 않음 | 복호화·사용·재저장 차단 |
| `decrypt_failed` | 키는 있으나 암호문이 손상됐거나 다른 키로 암호화됨 | 복호화·사용·재저장 차단, 재입력 필요 |

`plaintext_legacy`는 기존 데이터 호환을 위한 관찰 상태이지, 평문 저장을 허용하는 정책이 아니다.

### 3.3 암호화·복호화 결과 원칙

- 암호화 함수는 키가 없을 때 입력 평문을 반환하지 않는다.
- 복호화 함수는 키가 없을 때 입력 암호문을 반환하지 않는다.
- `None`과 빈 문자열은 "키 없음" 또는 "복호화 실패"를 의미하는 값으로 사용하지 않는다.
- 내부적으로는 상태와 선택적 값이 함께 있는 결과 모델 또는 동등한 명시적 결과 구조를 사용한다.
- 저장 계층은 결과 상태가 `encrypted`가 아니면 민감값을 DB에 기록하지 않는다.
- 호출부가 기존 `str | None` 계약에 의존하는 부분은 태스크 세션에서 전부 확인하고, 상태를 잃지 않는 방향으로 일괄 정리한다.

## 4. 민감정보 저장 정책

### 4.1 공통 저장 검사

`_ENCRYPT_FIELDS`에 포함된 필드는 전체 저장과 증분 저장 모두 동일한 공통 검사 경로를 사용한다.

검사 순서:

1. 빈 값은 기존 설정 삭제/미설정 의미를 유지하되, 호출부의 삭제 정책과 구분한다.
2. 이미 저장된 암호문을 그대로 재저장하는 경우에는 암호문 형식과 정책을 확인한다.
3. 평문 입력이면 현재 키 상태를 확인한다.
4. 키 상태가 `available`이 아니면 저장을 거부한다.
5. 암호화 결과가 정상 암호문이 아니면 저장을 거부한다.
6. 검사 실패 시 DB 쓰기와 성공 후 캐시 갱신을 수행하지 않는다.

기존 `_encrypt_field_or_raise()`의 fail-closed 의도를 재사용하고, 증분 저장 경로가 동일 정책을 통과하도록 연결한다. 별도의 저장 우회 함수나 평문 허용 옵션은 추가하지 않는다.

### 4.2 일반 설정의 정상 저장 범위

현재 설정 API는 필드 단위 PATCH 경로다. 이 구조를 기준으로 다음을 적용한다.

- 비민감 설정: 암호화 키 상태와 무관하게 정상 저장
- 민감 설정: 암호화 키가 없거나 오류이면 해당 필드 저장 거부
- 앱 전체 기동: 암호화 키가 없다는 이유만으로 전체 앱을 기동 불가로 만들지 않음
- 한 민감 필드의 저장 실패: 다른 비민감 설정의 저장을 차단하지 않음
- 향후 일괄 저장 API를 추가할 경우: 필드별 결과를 명시적으로 반환하고, 민감 필드의 실패를 성공으로 위장하지 않음

일반 설정이 민감정보와 하나의 요청으로 묶이는 새 경로를 만들지 않는다. 불가피한 일괄 저장에서는 민감 필드의 사전 검증과 결과별 상태 반환을 설계에 포함해야 한다.

## 5. 저장 실패 시 API 응답 형식

현재 라우터는 예외를 `422 Unprocessable Entity`로 변환하고 문자열 `detail`을 반환한다. 이번 작업에서는 기존 HTTP 상태 체계를 유지하되, UI가 원인을 안정적으로 판별할 수 있도록 구조화된 오류 내용을 추가한다.

권장 응답 형태:

```json
{
  "detail": {
    "code": "ENCRYPTION_KEY_MISSING",
    "message": "암호화 키가 설정되지 않아 인증정보를 저장할 수 없습니다.",
    "field": "kiwoom_app_key"
  }
}
```

권장 오류 코드:

| 코드 | 상황 |
|---|---|
| `ENCRYPTION_KEY_MISSING` | 키 미설정 |
| `ENCRYPTION_KEY_INVALID` | 키 형식·초기화 오류 |
| `ENCRYPTION_FAILED` | 암호화 처리 실패 |
| `DECRYPTION_UNAVAILABLE` | 키가 없어 기존 암호문 복호화 불가 |
| `DECRYPTION_FAILED` | 잘못된 키·손상 암호문 등 복호화 실패 |
| `PLAINTEXT_SECRET_REQUIRES_REENTRY` | 기존 평문 값이 감지되어 안전한 재입력이 필요 |

`field`는 민감값 자체가 아니라 필드 이름만 포함한다. 키 원문, 평문, 암호문 일부, 예외 traceback은 응답에 포함하지 않는다.

현재 프론트엔드 API 클라이언트는 FastAPI의 `detail` 문자열을 기준으로 오류를 읽고 있으므로, 구조화된 `detail`을 처리할 때 기존 문자열 오류도 계속 처리할 수 있도록 호환 전략을 태스크에 포함한다.

## 6. 기존 평문 데이터 처리

### 6.1 원칙

기존 DB에 평문 민감값이 있을 가능성을 고려하되, 읽기 시 자동으로 평문을 정상 암호문처럼 취급하지 않는다.

### 6.2 처리 규칙

- DB 로드 시 암호문 형식이 아니면 `plaintext_legacy` 상태로 분류한다.
- 키가 있으면 사용자가 해당 값을 명시적으로 다시 저장할 때 암호화한다.
- 키가 없으면 자동 마이그레이션·자동 재저장을 수행하지 않는다.
- `plaintext_legacy`를 새 저장 경로에서 그대로 복사하지 않는다.
- 평문 값을 UI 응답·로그·저널에 새로 노출하지 않는다. UI에는 "보안 재저장 필요" 상태만 표시한다.
- 기존 평문 값을 즉시 삭제하는 동작은 하지 않는다. 재입력·암호화 성공 전 삭제하면 인증정보가 유실될 수 있다.
- 사용자가 새 값을 입력해 암호화 저장에 성공한 후에만 기존 값을 암호문으로 교체한다.

### 6.3 복호화 실패 데이터

- 키 없음: `key_unavailable`
- 키는 있으나 다른 키/손상 암호문: `decrypt_failed`
- 자동으로 빈 문자열로 바꾸거나 입력값을 반환하지 않는다.
- 브로커 인증정보가 필요한 동작은 해당 필드가 복호화 불가이면 차단한다.
- 사용자가 설정 화면에서 다시 입력해 복구할 수 있도록 안내한다.

## 7. UI 상태 표시 위치와 표현

### 7.1 위치

기존 일반설정 화면을 유지하고, 다음 두 위치에 상태를 표시한다.

1. 일반설정 상단: 현재 앱 전체의 암호화 상태 요약 배너
2. `API 설정`·`텔레그램` 탭: 해당 민감정보 저장 영역의 구체적인 상태와 저장 제한 안내

기존 공통 UI 자산과 설정 화면의 표준 색상·토스트·설명 텍스트 패턴을 우선 재사용한다. 암호화 상태만을 위한 중복된 카드·색상 체계는 새로 만들지 않는다.

### 7.2 표시 상태

| 내부 상태 | 사용자 표시 |
|---|---|
| `available` | "민감정보 암호화 정상" |
| `missing` | "암호화 키가 설정되지 않았습니다. API 키와 토큰을 저장할 수 없습니다." |
| `invalid` | "암호화 키를 사용할 수 없습니다. 키 설정을 확인한 뒤 다시 저장하세요." |
| `plaintext_legacy` | "기존 인증정보가 안전하게 암호화되지 않았습니다. 인증정보를 다시 입력해 저장하세요." |
| `key_unavailable` | "암호화 키가 없어 저장된 인증정보를 읽을 수 없습니다." |
| `decrypt_failed` | "저장된 인증정보를 복호화할 수 없습니다. 인증정보를 다시 입력하세요." |

민감 필드 입력값은 계속 `***` 마스킹을 사용한다. 상태 표시는 비밀값을 표시하지 않는다.

### 7.3 저장 실패 UX

- 저장 버튼은 키가 없다는 상태를 알 수 있으면 미리 비활성화할 수 있다.
- 서버 검증이 최종 방어선이며, 버튼 비활성화만으로 저장 차단을 대체하지 않는다.
- 서버에서 거부되면 기존 설정값을 성공한 것처럼 store에 반영하지 않는다.
- 저장 실패 토스트 또는 인라인 메시지에는 구조화된 오류 코드에 대응하는 사용자용 메시지를 표시한다.

## 8. 거래 연결·주문 차단 연계

### 8.1 앱 전체 차단 여부

암호화 키 미설정만으로 앱 전체 기동을 차단하지 않는다. 일반 설정, 테스트 데이터 조회, 분석 화면 등 암호화된 인증정보가 필요 없는 기능은 계속 사용할 수 있어야 한다(P25).

### 8.2 브로커 연결

선택된 브로커에 필요한 인증정보가 다음 중 하나이면 브로커 연결을 시작하지 않는다.

- 값 없음
- 암호화 키 없음/오류로 복호화 불가
- 복호화 실패
- 재입력이 필요한 기존 평문 상태

연결 차단 상태와 사유는 UI의 브로커 연결 상태에 표시한다. 단순히 연결 실패로만 표시하지 않는다.

### 8.3 주문

주문 단일 경로인 `execute_buy()`/`execute_sell()`을 우회하지 않고, 주문 전에 이미 검증된 브로커 자격증명 상태를 사용한다. 인증정보가 안전하게 준비되지 않은 경우 주문을 차단하고 사유를 기록·표시한다.

테스트 모드는 현재 앱의 모의 거래 목적을 유지한다. 테스트 모드가 브로커 인증정보를 실제로 필요로 하지 않는 경로라면 암호화 키 상태만으로 테스트 매매를 차단하지 않는다. 반대로 외부 브로커 연결을 사용하는 테스트 경로는 필요한 인증정보 검증을 적용한다.

### 8.4 실전 안전성

이번 설계는 실전 거래를 활성화하는 변경이 아니다. 오히려 실전 브로커 인증정보가 안전하게 복호화되지 않으면 연결·주문을 차단하는 방향이다. 기존 실전/테스트 모드 판정 SSOT와 주문 단일 경로는 유지한다.

## 9. 키 백업·복구 안내

### 9.1 저장 원칙

- 암호화 키는 `stocks.db`에 저장하지 않는다.
- 암호화 키와 DB 백업은 같은 위치에 평문으로 함께 보관하지 않는다.
- 키는 로그·API 응답·UI·저널에 기록하지 않는다.
- DB 백업만으로는 암호화된 인증정보를 복구할 수 없음을 명시한다.
- 키를 잃으면 기존 암호화 데이터는 복구할 수 없을 수 있으므로, 키 백업 절차를 제공해야 한다.

### 9.2 사용자 안내 문구

설정 화면에 다음 안내를 사용한다.

> **암호화 키 백업 안내**
>
> API 키와 텔레그램 토큰은 암호화하여 저장합니다. 암호화 키를 잃어버리면 저장된 인증정보를 복구할 수 없습니다. 앱 데이터 백업과 암호화 키 백업을 서로 다른 안전한 장소에 보관하세요. 암호화 키를 화면이나 로그에 입력·기록하지 마세요.

키가 없을 때는 다음 문구를 사용한다.

> 암호화 키가 설정되지 않아 API 키와 비밀번호를 저장할 수 없습니다. 일반 설정은 계속 사용할 수 있지만, 인증정보가 필요한 브로커 연결과 주문은 사용할 수 없습니다.

복호화 실패 시에는 다음 문구를 사용한다.

> 저장된 인증정보를 복호화할 수 없습니다. 암호화 키를 확인하거나 인증정보를 다시 입력해 저장하세요. 기존 데이터는 복구 전까지 자동으로 삭제하지 않습니다.

## 10. 테스트·검증 설계

### 10.1 백엔드 단위 테스트

- 키 없음 → 암호화 결과가 평문이 되지 않고 명시적 `missing` 상태
- 잘못된/짧은 키 → `invalid` 상태
- 암호화 내부 예외 → `ENCRYPTION_FAILED`, 평문 저장 없음
- 키 없음 상태의 복호화 → 입력 암호문 반환 없음, `key_unavailable`
- 잘못된 키/손상 암호문 → `decrypt_failed`
- 정상 Fernet round-trip
- 기존 평문 값 → `plaintext_legacy`

### 10.2 저장 경로 테스트

- 전체 저장 경로에서 민감정보 평문 저장 차단
- 증분 저장 경로에서 민감정보 평문 저장 차단
- 비민감 설정은 키 없음 상태에서도 정상 저장
- 민감정보 저장 실패 후 DB 값·캐시·저널이 성공 상태로 바뀌지 않음
- 기존 민감 암호문을 키 없이 덮어쓰지 않음
- 구조화된 API 오류 코드·필드명 반환

### 10.3 프론트엔드 테스트

- 암호화 상태별 배너 표시
- API/텔레그램 탭의 저장 제한 표시
- 구조화된 오류 메시지 표시
- 민감정보 저장 실패 시 store에 평문 입력값을 성공 상태로 반영하지 않음
- 정상 상태에서 기존 저장·마스킹 동작 유지

### 10.4 검증 게이트

구현 세션 완료 시 다음을 실행한다.

- 백엔드 전체 테스트: `.venv/bin/python -m pytest backend/tests -q`
- 백엔드 런타임 기동: `.venv/bin/python main.py`
- RuntimeWarning 검증: `.venv/bin/python -W error::RuntimeWarning main.py`
- 프론트엔드 타입체크: `cd frontend && npm run typecheck`
- 프론트엔드 빌드: `cd frontend && npm run build`
- 프론트엔드 테스트: `cd frontend && npm run test`

실제 돈이 오가는 실전 거래는 검증 대상으로 실행하지 않는다. 거래 관련 검증은 테스트 모드와 연결·주문 차단 상태를 기준으로 한다.
