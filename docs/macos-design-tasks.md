# 태스크 파일: macOS 스타일 UI 전환

> 상태: 작성 완료 · 구현 승인 대기
> 작성일: 2026-07-27
> 기준 설계서: `docs/macos-design-plan.md`
> 범위: 프론트엔드 시각 스타일 전환
> 제외: 백엔드·매매 로직·DB 변경, 다크 모드 구현, CSS 파일 신설
> 진행 원칙: 한 세션에 한 단계만 진행하고, 각 세션의 검증 완료 후 다음 세션으로 인계한다.

## 0. 작업 목표와 공통 제약

### 0.1 목표

- `frontend/src/components/common/ui-styles.ts`를 스타일 토큰의 단일 진실 소스로 유지한다.
- 기존 TypeScript + Vanilla DOM 구조와 인라인 스타일 방식을 유지한다.
- macOS 계열의 시스템 폰트, 둥근 모서리, 은은한 그림자, 반투명 표면을 적용한다.
- 의미 색의 역할은 변경하지 않는다.
  - 빨강: 상승·양수·매수·위험·오류
  - 파랑: 하락·음수·매도·정보·활성
  - 초록: 성공·통과·연결·장중
  - 주황: 경고·주의
- UI 용어는 기존 표준을 유지한다.
  - 업종, 종목, 매수 후보, 보유 종목

### 0.2 공통 제약

- 매 세션 시작 전 해당 세션의 사용자 승인 여부를 확인한다.
- 매 세션은 해당 세션에 지정된 파일과 직접 의존하는 필수 연쇄 수정만 포함한다.
- 기존 공통 자산과 `ui-styles.ts`의 토큰을 우선 재사용한다. 동일한 색상·반경·그림자 상수를 파일별로 새로 만들지 않는다.
- 매 세션 종료 시 다음 세션에서 처리할 문제를 임의로 선행 수정하지 않는다.
- 스타일 변경으로 동작·상태·데이터 처리·주문 경로를 변경하지 않는다.
- `backdrop-filter`가 지원되지 않아도 내용과 기능을 사용할 수 있도록 불투명 또는 일반 배경이 남아 있어야 한다.
- 포커스 표시를 제거하지 않는다. `outline: none`이 있는 입력·버튼은 키보드 포커스가 식별 가능하도록 확인한다.
- 색상 변경은 색상 함수의 의미 로직을 변경하지 않고 토큰 값만 조정한다.

## 1. 설계 검토 보완사항

설계서의 방향은 유지하되, 구현 시 다음 기준을 추가 적용한다.

1. **하드코딩 기준선 재측정**
   - 설계서의 `borderRadius` 76곳이라는 수치를 구현 전 실제 검색 결과로 갱신한다.
   - 현재 확인된 `borderRadius:` 지정은 61건이며, 태스크 완료 여부는 고정 숫자가 아니라 토큰화 누락 목록이 0건인지로 판단한다.
   - 색상·반경·그림자 검색 결과는 세션 3 시작 시 기준선으로 기록한다.

2. **오버레이와 표면의 역할 분리**
   - `SURFACE_ALPHA.overlay`는 모달 뒤 배경을 어둡게 하는 오버레이 값이다.
   - 로딩 오버레이에 그대로 적용하지 말고, 로딩 화면의 가독성과 현재 동작을 먼저 확인한다.
   - 오버레이가 투명해지는 경우에도 로딩 문구와 진행 상태가 항상 읽혀야 한다.

3. **블러 적용 조건 명시**
   - 다이얼로그·토스트·툴팁에 블러를 적용하더라도 텍스트 대비와 배경 비침을 먼저 확인한다.
   - 가독성 기준을 충족하지 못하면 해당 표면은 불투명 배경으로 유지한다.
   - 표면 자체의 배경색과 뒤쪽 배경을 흐리는 `backdrop-filter`의 차이를 구분한다.

4. **색상 후보의 최종 확정 절차 추가**
   - `down`과 `warning`처럼 후보가 여러 개인 토큰은 구현 중 임의로 선택하지 않는다.
   - 대비 측정과 실제 화면 확인 후 최종값을 결정하고, 결정 전에는 제안값을 유지한다.
   - 상승=빨강, 하락=파랑 등 의미 매핑은 어떤 후보를 선택해도 변경하지 않는다.

5. **접근성·환경 검증 추가**
   - 일반 화면과 키보드 포커스 상태에서 텍스트, 입력, 버튼, 활성 상태가 식별되는지 확인한다.
   - 주요 의미 색은 색상만으로 상태를 전달하지 않는 기존 기호·라벨과 함께 확인한다.
   - `backdrop-filter` 미지원 환경에서 기능·가독성이 유지되는지 확인한다.
   - 기존 애니메이션의 동작을 바꾸지 않으며, 포커스 링이나 상태 표시를 희생하지 않는다.

### 세션 3 — 공통 디자인 토큰

**대상 파일**

- `frontend/src/components/common/ui-styles.ts`
- 직접 의존 테스트가 있는 경우 해당 테스트 파일만 필수 연쇄 수정

**수정 목록**

- `FONT_FAMILY`를 macOS 시스템 폰트 우선 스택으로 변경한다.
- `RADIUS`를 추가하고 칩·입력·버튼·카드·팝업·다이얼로그·필에 사용할 단계별 값을 정의한다.
- `SHADOW`를 추가하고 카드·호버·팝업·모달·사이드바 활성·없음 값을 정의한다.
- `BLUR`와 `SURFACE_ALPHA`를 추가한다.
- `COLOR`의 중성 색과 의미 색을 설계서 기준으로 조정한다.
- `rateColor()`, `pnlColor()`, `strengthColor()` 및 수익률 계산 로직은 변경하지 않는다.
- 모든 신규 토큰은 기존 상수와 같은 `as const` 패턴을 사용한다.

**검증 기준**

- `frontend/src/components/common/ui-styles.ts` 외에 동일 토큰의 별도 정의가 없다.
- TypeScript 타입체크, 프론트엔드 빌드, 프론트엔드 테스트가 통과한다.
- 상승·하락·성공·경고의 의미 색 계열이 보존된다.
- 주요 전경색과 배경색의 대비를 확인하고, 기준 미달 색상은 사용자 승인 없이 임의 확정하지 않는다.
- 기존 포맷 함수와 색상 함수의 테스트 결과가 변하지 않는다.

### 세션 4 — 레이아웃 뼈대

**대상 파일**

- `frontend/src/layout/shell.ts`
- `frontend/src/layout/sidebar.ts`
- `frontend/src/layout/header.ts`

**수정 목록**

- 루트·콘텐츠·패널 배경에 공통 토큰을 적용한다.
- 사이드바에 반투명 표면, 블러, 둥근 메뉴 항목, 활성 상태 그림자를 적용한다.
- 헤더에 툴바 표면, 블러, 보더, 헤더 칩 토큰을 적용한다.
- 기존 아이콘·라벨·활성 상태·로딩 상태의 동작은 유지한다.
- 사이드바 폭과 헤더 높이는 아래 미해결 항목의 사용자 결정을 받은 경우에만 변경한다.

**검증 기준**

- 타입체크와 빌드가 통과한다.
- 앱의 모든 기존 화면에서 사이드바와 헤더가 표시된다.
- 메뉴 선택, 화면 전환, 헤더 상태 칩, 로딩 오버레이가 기존과 동일하게 동작한다.
- 사이드바와 헤더의 텍스트가 배경에 비쳐 흐려지지 않는다.
- 블러 미지원 상태에서도 배경과 텍스트가 읽힌다.
- 사용자 결정 없이 사이드바 폭 120px→160px, 헤더 높이 40px→44px를 변경하지 않는다.

- 다이얼로그·토스트·툴팁에서 긴 문구도 읽을 수 있다.
- 블러 적용을 선택하지 않은 경우 불투명 배경으로 기능과 가독성이 유지된다.

- 차트 툴팁 블러는 미해결 항목의 결정과 실제 가독성 검증 후 적용하거나 불투명 배경으로 유지한다.
- 프론트엔드 전체에서 잔존하는 색상·반경·그림자 하드코딩을 검색한다.
- 기능상 특수값이어서 토큰화하지 않는 항목은 예외 사유를 태스크 결과에 기록한다.
- 신규 토큰이 실제 사용 경로에 연결되었는지 확인하고 사용되지 않는 토큰이나 dead code를 남기지 않는다.
- 전체 페이지를 최종 확인한다.

**검증 기준**

- 타입체크, 빌드, 프론트엔드 테스트가 통과한다.
- 차트 렌더링, 툴팁 위치, 데이터 표시, 페이지 전환이 정상이다.
- 잔존 하드코딩은 의도된 예외를 제외하고 없다.
- 업종순위, 매수 후보, 보유 종목, 수익현황, 수익상세, 종목분류, 종목상세, 일반설정 화면의 스타일이 일관된다.
- 상승=빨강, 하락=파랑, 성공=초록, 경고=주황 의미가 모든 화면에서 유지된다.
- 새로고침 후에도 스타일이 유지된다.
- 블러 지원 환경과 미지원 환경 모두에서 주요 텍스트·상태·버튼을 읽을 수 있다.
- 키보드 포커스와 비활성 상태가 식별 가능하다.

## 3. 미해결 6건 — 사용자 승인 항목

아래 항목은 구현자가 임의로 결정하지 않는다. 해당 구현 세션 전에 사용자의 결정을 기록한 뒤 진행한다.

| 번호 | 결정 항목 | 선택지 | 적용 세션 | 결정 상태 |
|---:|---|---|---:|---|
| 1 | 사이드바 폭 | 현재 120px 유지 / 160px로 변경 | 4 | 사용자 승인 필요 |
| 2 | 헤더 높이 | 현재 40px 유지 / 44px로 변경 | 4 | 사용자 승인 필요 |
| 3 | 다이얼로그 배경 | 불투명 흰색 유지 / 반투명 패널+블러 적용 | 5 | 사용자 승인 필요 |
| 4 | 차트 툴팁 배경 | 불투명 배경 유지 / 반투명 패널+블러 적용 | 8 | 사용자 승인 필요 |
| 5 | 다크 모드 | 이번 범위에서 제외 / 별도 설계 태스크로 분리 | 2 | 사용자 승인 필요 |
| 6 | 의미 색 최종값 | 설계서 제안값 채택 / 대비·실제 화면 확인 후 조정 | 3, 8 | 사용자 승인 필요 |

### 승인 처리 기준

- 사용자가 선택하기 전에는 기존 레이아웃 크기와 불투명 배경을 유지한다.
- 색상 후보는 대비 측정 결과와 실제 화면 확인 내용을 함께 제시한 뒤 확정한다.
- 다크 모드는 이번 8세션에 구현하지 않는다. 별도 설계로 분리하기로 결정하면 별도 태스크를 만든다.
- 결정 내용은 이 표의 `결정 상태`와 선택지에 반영한 후 해당 세션을 시작한다.

## 4. 공통 검증 게이트

각 구현 세션에서 다음 순서를 지킨다.

1. 변경 대상 파일이 해당 세션 범위 안인지 확인한다.
2. 프론트엔드 타입체크를 실행한다.
3. 프론트엔드 빌드를 실행한다.
4. 세션 표에 테스트가 지정된 경우 프론트엔드 테스트를 실행한다.
5. 브라우저에서 해당 세션의 화면과 상태를 확인한다.
6. 실패가 있으면 다음 세션으로 넘어가지 않고 해당 세션에서 원인을 해결한다.
7. 검증 결과와 미해결 사항을 인계 문서에 기록한다.

### 공통 정적 검증

- `cd frontend && npm run typecheck`
- `cd frontend && npm run build`
- `cd frontend && npm run test`

### 공통 브라우저 검증

- 새로고침 후 스타일이 정상 적용되는지 확인한다.
- 사이드바·헤더·카드·테이블·설정·차트의 텍스트가 읽히는지 확인한다.
- 상승·하락·성공·경고 상태의 색 의미가 유지되는지 확인한다.
- 버튼·입력·토글·팝업의 키보드 포커스가 보이는지 확인한다.
- 블러가 배경 텍스트를 과도하게 비치게 하지 않는지 확인한다.
- 블러가 지원되지 않아도 기능과 가독성이 유지되는지 확인한다.

## 5. 완료 조건

- 8세션의 각 검증 기준을 통과했다.
- 사용자 승인 항목 6건의 결정 상태가 기록되었다.
- `ui-styles.ts`가 모든 공통 토큰의 SSOT로 유지된다.
- 의미 색 함수의 로직과 매매·상태 데이터의 의미가 변경되지 않았다.
- 의도하지 않은 레이아웃·동작·용어 변경이 없다.
- 프론트엔드 타입체크·빌드·테스트가 최종 통과했다.
