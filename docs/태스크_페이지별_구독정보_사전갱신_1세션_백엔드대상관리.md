# 태스크: 페이지별 구독 대상 사전 갱신 — 1세션 백엔드 대상 관리

- **문서 역할**: 구현 방법과 완료 조건 정의
- **세션**: 1/4
- **상태**: 구현 대기
- **선행 조건**: 조사 완료, 사용자 구현 승인 완료
- **다음 세션**: 백엔드 전달·재연결·변경 통지 연결

## 1. 작업 목표

프론트엔드가 개별 종목 코드를 보내지 않아도, 백엔드가 화면 이름에 맞는 대상 자료를 관리하도록 한다.

이 세션에서는 **8개 화면의 대상 자료를 한 곳에서 관리하고 원본 변경 시 갱신**하는 것만 구현한다. WebSocket 전달과 프론트엔드 전환은 다음 세션에서 수행한다.

## 2. 대상 페이지와 대상 원본

| 페이지 | 자료 유형 | 대상 원본·규칙 |
|---|---|---|
| 업종 순위 | 종목 실시간 구독 | 기존 `all_filter_codes` 계약 유지. 유효한 시세·종목명 조건과 5일 평균 거래대금 기준을 동일하게 적용한다. |
| 매수 후보 | 종목 실시간 구독 | 현재 매수 후보 결과의 코드만 사용한다. |
| 보유 종목 | 종목 실시간 구독 | 현재 보유 목록에서 수량이 0보다 큰 코드만 사용한다. |
| 수익 현황 | 종목 실시간 구독 | 보유 종목과 같은 대상 집합을 공유한다. |
| 수익 상세 | 이력 스냅샷·변경 알림 | 매수·매도 이력 원본. 종목 실시간 구독 코드는 만들지 않는다. |
| 종목 분류 | 분류 스냅샷·변경 알림 | 사용자 업종 분류·전체 분류 대상 원본. 종목 실시간 구독 코드는 만들지 않는다. |
| 종목 상세 | 5일 일봉 스냅샷 | 5일 일봉 원본. 종목 실시간 구독 코드는 만들지 않는다. |
| 일반 설정 | 설정 스냅샷·변경 알림 | 설정 저장소. 민감한 값은 기존 마스킹 규칙을 유지한다. |

## 3. 저장소 원칙

- 실제 종목 자료와 실시간 값은 기존 마스터 캐시를 계속 원본으로 사용한다.
- 새 저장소에는 화면용 종목 전체 자료를 복사하지 않고 **페이지별 대상 코드 집합, 준비 상태, 변경 번호**만 저장한다.
- 보유 종목 대상은 보유 종목 원본 하나를 두 화면이 함께 사용한다.
- 페이지별 대상 집합은 파생 결과이며, 직접 수정하는 진실 소스로 만들지 않는다.
- 아직 계산되지 않은 상태와 대상이 실제로 없는 상태를 구분한다. 준비되지 않은 상태를 빈 목록으로 성공 처리하지 않는다.
- 기존 엔진의 증권사 실시간 구독 대상과 브라우저별 화면 구독 대상을 혼동하지 않는다. 이번 세션은 브라우저 화면 전달 대상 저장이 범위다.

## 3.1 원칙 준수 기준

- **P10 단일 소스**: 대상 코드는 기존 필터·후보·보유 원본에서만 파생하고, 페이지별 독립 목록을 직접 수정하지 않는다.
- **P11 폴링 금지**: 시간 간격으로 대상을 확인하지 않고 원본 변경 이벤트에서만 갱신한다.
- **P24 단순성**: 여덟 페이지에 같은 대상 계산을 복사하지 않고 공통 갱신 경로를 사용한다.

## 4. 구현 항목

### 4.1 대상 저장소 추가

- [ ] 기존 중앙 상태 관리 위치에 페이지 대상 상태를 추가한다.
- [ ] 대상 페이지 키는 `sector-ranking`, `buy-target`, `sell-position`, `profit-overview`, `profit-detail`, `stock-classification`, `stock-detail`, `settings` 여덟 개만 허용한다.
- [ ] 각 대상은 다음 정보를 가진다.
  - [ ] 종목 실시간 구독 화면: 정규화된 코드 집합 또는 중복 없는 안정된 코드 목록
  - [ ] 이력·분류·일봉·설정 화면: 화면 자료 준비 상태와 자료 변경 번호
  - [ ] 준비 완료 여부
  - [ ] 마지막 갱신 원인
  - [ ] 자료 유형(종목 구독 / 이력 / 분류 / 일봉 / 설정)
- [ ] 허용되지 않은 페이지 키가 들어오면 대상 저장소를 만들지 않는다.
- [ ] 코드 목록의 순서는 비교·테스트·전송 결과가 흔들리지 않도록 안정화한다.

### 4.2 공통 대상 갱신 처리

- [ ] 페이지별 대상·자료 계산을 한 곳에서 수행하는 공통 갱신 경로를 만든다.
- [ ] 업종 순위는 기존 업종 필터 계산 결과를 재사용한다. 같은 필터 조건을 새로 복사해 만들지 않는다.
- [ ] 매수 후보는 기존 매수 후보 조회 결과의 코드만 추출한다.
- [ ] 보유 종목은 기존 보유 목록 조회 결과에서 양의 수량만 추출한다.
- [ ] 수익 현황은 보유 종목 대상 집합을 재사용한다.
- [ ] 수익 상세는 매수·매도 이력 변경 번호만 갱신한다.
- [ ] 종목 분류는 분류 자료가 바뀔 때 분류 스냅샷 변경 번호를 갱신한다.
- [ ] 종목 상세는 5일 일봉 확정 자료가 바뀔 때 일봉 스냅샷 변경 번호를 갱신한다.
- [ ] 일반 설정은 설정 저장 결과가 바뀔 때 최신 마스킹 설정 스냅샷을 갱신한다.
- [ ] 이전 대상과 새 대상이 같으면 변경 번호를 올리지 않는다.
- [ ] 대상이 달라지면 변경 번호를 올리고, 추가·제거 코드를 계산할 수 있도록 이전 대상과 새 대상을 비교한다.
- [ ] 대상 계산 실패 시 이전 정상 대상에 조용히 빈 목록을 덮어쓰지 않는다. 실패 상태를 기록하고 호출자에게 실패를 알린다.
- [ ] 대상 계산은 요청이 들어올 때마다 반복하는 폴링으로 만들지 않는다.

### 4.3 초기 생성과 재기동

- [ ] 앱 준비·로그인 후 페이지 대상 저장소를 초기화한다.
- [ ] 초기 대상 계산 순서는 기존 필터·후보·보유 자료가 준비된 뒤로 보장한다.
- [ ] 재기동 시 이전 메모리 대상 목록을 신뢰하지 않고 현재 원본에서 다시 만든다.
- [ ] 계산 전에는 화면에 초기 스냅샷을 성공 전송하지 않도록 준비 상태를 사용한다.
- [ ] 초기 계산 실패가 전체 앱 기동을 불필요하게 중단하지 않도록 기존 실패 격리 패턴을 따른다. 단, 해당 페이지에는 실패 상태가 전달되어야 한다.

## 5. 원본 변경 시 갱신 연결 준비

이 세션에서는 아래 갱신 함수가 호출될 수 있도록 공통 진입점을 만든다. 실제 호출 지점 연결은 2세션에서 마무리한다.

- [ ] 설정 변경 후 업종 필터·업종 점수·매수 후보 재계산이 끝난 시점
- [ ] 장 마감 확정 데이터와 5일 평균 거래대금 반영이 끝난 시점
- [ ] 시장 시간대가 바뀌어 실시간 대상 정책이 바뀌는 시점
- [ ] 매수 후보가 다시 만들어진 시점
- [ ] 보유 목록이 체결 결과로 바뀐 시점
- [ ] WebSocket 재연결 후 현재 대상 재적용이 필요한 시점

## 6. 반드시 유지할 동작

- [ ] 매매 판단 공식과 매수 후보 선정 공식은 변경하지 않는다.
- [ ] 주문 실행 경로와 매도 조건은 변경하지 않는다.
- [ ] 5일 평균 거래대금의 단위와 화면 표시 규칙은 변경하지 않는다.
- [ ] 업종 점수 계산 대상과 필터 결과의 의미를 임의로 바꾸지 않는다.
- [ ] 기존 증권사 구독 한도·보유 종목 우선 정책을 변경하지 않는다.

## 7. 테스트 요구사항

- [ ] 종목 실시간 네 페이지의 대상 원본에서 코드가 정확히 추출되는지 테스트한다.
- [ ] 자료 중심 네 페이지의 자료 변경 번호가 정확히 갱신되는지 테스트한다.
- [ ] 동일한 대상 재갱신 시 변경 번호가 올라가지 않는지 테스트한다.
- [ ] 대상 추가·제거 시 이전·현재 집합 비교가 정확한지 테스트한다.
- [ ] 설정 변경으로 필터 대상이 바뀌는 경우 새 대상이 저장되는지 테스트한다.
- [ ] 매수 후보 변경으로 대상이 바뀌는 경우 새 대상이 저장되는지 테스트한다.
- [ ] 보유 종목 추가·부분 매도·전량 매도에서 보유 대상이 정확히 바뀌는지 테스트한다.
- [ ] 매수·매도 이력 변경이 이력 자료 변경 번호만 갱신하는지 테스트한다.
- [ ] 분류 변경이 분류 자료 변경 번호만 갱신하는지 테스트한다.
- [ ] 장 마감 일봉 갱신이 일봉 자료 변경 번호를 갱신하는지 테스트한다.
- [ ] 설정 변경이 마스킹 설정 스냅샷을 갱신하는지 테스트한다.
- [ ] 계산 실패 시 이전 정상 상태를 빈 목록으로 덮지 않는지 테스트한다.
- [ ] 페이지 대상 여덟 개 외의 키가 저장되지 않는지 테스트한다.

## 8. 완료 기준

- [ ] 여덟 페이지의 자료 유형과 원본이 한 곳에서 관리된다.
- [ ] 종목 실시간 구독 대상 코드는 한 곳에서 관리된다.
- [ ] 보유 종목 대상은 두 화면이 같은 원본 결과를 사용한다.
- [ ] 업종 필터 기준이 기존 화면·엔진 계산과 동일하다.
- [ ] 대상 변경이 없을 때 불필요한 갱신 번호·후속 작업이 발생하지 않는다.
- [ ] 폴링이나 주기적 전체 조회가 추가되지 않는다.
- [ ] 대상 계산 실패와 실제 빈 대상이 구분된다.
- [ ] 관련 백엔드 테스트와 린트가 통과한다.

## 9. 범위 밖

- WebSocket 수신 처리와 화면별 초기 스냅샷 전송
- 프론트엔드에서 종목 코드 전송 제거
- 일반 설정·이력·분류·일봉 화면의 화면 연결 처리
- 화면별 렌더링 변경
- 매매 전략·주문·리스크 변경
