## 0. 사전조사 결과 요약

### 0.1 구현 결정 항목

설계 세션의 사용자 요구와 현재 코드·표준 백분위 정의를 대조해 다음 구현 기준으로 확정했다. 구현 세션은 이 기준을 임의로 변경하지 않는다.

| 항목 | 확정 기준 | 사용자 영향 |
|---|---|---|
| 대표 데이터 폭 | 샘플 20개 이상이면 Nearest Rank P95, 1~19개는 기존 max | 작은 샘플에서 P95가 max와 같을 수 있다는 특성을 정직하게 반영 |
| 샘플 부족 기준 | 샘플 0개는 라벨 폭, 1~19개는 기존 `max` | 시작 직후 데이터가 적어도 헤더가 안정적으로 표시됨 |
| 절대 최대 폭 | `ABSOLUTE_MAX_WIDTH = 240` (폭 계산 가중치 상한) | 극단값이 비율 계산에서 과도한 비중을 차지하지 않음 |
| 기존 덮어쓰기 | type 캡과 `ColumnDef.minWidth/maxWidth`를 각 축별 교집합으로 병합 | 현재 페이지별 특수 폭과 공통 type 안전 범위를 함께 유지 |
| 폭 계산 준비 | 기존 수신율 임계값 게이트 통과 후 업종순위·업종별 종목만 1회 계산 | 미달 시 최종 폭을 고정하지 않고 대기 상태 유지 |

### 0.2 의존성 및 재사용 자산

| 파일 | 역할 | 태스크 적용 기준 |
|---|---|---|

| `frontend/src/components/common/table-config.ts` | `COLUMN_WIDTH` type별 캡, `CELL_PADDING` | type별 폭 상수와 셀 패딩을 변경하지 않고 재사용 |
| `frontend/src/components/common/data-table.ts` | type 캡과 페이지 min/max 병합, 준비 전 폭 계산 보류 | `widthReady` 조건을 받아 최종 폭을 1회만 계산 |
| `frontend/src/components/common/data-table-fixed.ts` | 고정 모드 준비 전·후 폭 적용 | 빈 rows에서 최종 폭을 고정하지 않음 |
| `frontend/src/components/common/data-table-virtual.ts` | 가상 스크롤 모드 준비 전·후 폭 적용 | 고정 모드와 동일한 초기화 계약 유지 |

| `frontend/src/pages/sector-ranking-list.ts`·`sector-stock.ts` | 실시간 대상 테이블에 `widthReady` 연결 | 업종순위 게이트 대상만 대기 |
| `frontend/tests/` 내 auto-width 관련 테스트 | 기존 계약 및 회귀 기준 | 준비 전 보류·준비 후 1회 고정 테스트 추가 |
| `docs/auto_width_data_driven_design.md` | 알고리즘·엣지케이스·검증 기준 SSOT | 본 태스크 파일과 불일치할 경우 사용자 결정 항목과 설계서 기준으로 확인 후 보고 |

### 0.3 영향 범위

- **직접 변경 대상**: `auto-width.ts`, `data-table.ts`, `data-table-fixed.ts`, `data-table-virtual.ts`, 기존 준비 상태 연결 경로, 업종순위·업종별 종목 페이지, 공통 테스트 파일.
- **자동 적용 대상**: 공통 함수 경유 8개 페이지, 11개 테이블. 폭 계산 알고리즘은 공통 적용하되, 수신율 준비 게이트는 업종 순위·업종별 종목 실시간 테이블에만 적용한다.
- **변경하지 않는 영역**: 백엔드 수신율 계산 공식, DB, 주문 경로, 업종 순위 계산 공식, CSS `table-layout`, 준비 완료 후 `createColumnWidthManager`의 1회 고정 동작.
- **장중 안정성**: 준비 완료 전에는 최종 폭을 고정하지 않고, 준비 완료 후 1회 계산한 폭은 장중 데이터·수신률 변화로 재계산하지 않는다.
- **표본 원칙**: 마스터 캐시 원본을 직접 측정하지 않고 각 테이블 `ColumnDef.render()` 결과를 샘플로 사용한다.
- **DB**: 스키마·데이터 변경 없음. DB 백업 불필요.

### 0.4 아키텍처 원칙 부합

| 원칙 | 판정 | 구현 기준 |
|---|---|---|
| P10 | ✅ | 수신율 준비 상태는 기존 서버 게이트·상태 경로, 폭 대표값은 `auto-width.ts`, 캡 조립은 `data-table.ts`의 단일 경로를 사용한다. |
| P16 | ✅ | `widthReady`를 실제 고정·가상 테이블 초기화 경로와 `computeColWidths`에 연결한다. 미사용 안전 코드를 남기지 않는다. |
| P20 | ✅ | 준비 전 rows는 최종 폭으로 고정하지 않고, 임계값 미도달 시에도 안전 폭과 대기 표시로 명시적으로 처리한다. |
| P21 | ✅ | 수신율 대기 상태를 사용자에게 표시하고, 준비 완료 후 실제 표시 문자열을 기준으로 폭을 계산한다. |
| P23 | ✅ | 기존 수신율 게이트·uiStore·DataTable 공통 경로와 type 상수를 재사용한다. |
| P24 | ✅ | Nearest Rank P95·축별 캡 병합·준비 게이트만 추가하고 페이지별 폭 계산을 중복하지 않는다. |
| P25 | ✅ | 컬럼별 계산을 독립적으로 수행하며, 기존 경고 로깅을 유지한다. |

## 1. 구현 세션 분할

> 규칙: 한 구현 세션은 아래 단계 중 하나만 수행한다. 각 단계 완료 후 검증·코드 커밋·`HANDOVER.md` 갱신·사용자 보고를 수행하고 다음 세션으로 넘긴다. 태스크 파일은 모든 단계가 완료될 때까지 삭제하지 않는다.

### 세션 3 — 준비 게이트·캡 병합·상수·백분위 함수·클램프 구현

**목표**: 수신율 임계값 통과 전 최종 폭 계산을 보류하고, 준비 완료 후 실제 표시 rows로 1회 계산하는 공통 경로를 만든다. 동시에 type/page 캡 병합과 P95 기반 폭 계산을 구현한다.

**수정 파일**:

- `frontend/src/components/common/data-table.ts`
- `frontend/src/components/common/data-table-fixed.ts`
- `frontend/src/components/common/data-table-virtual.ts`
- `frontend/src/components/common/auto-width.ts`
- 기존 수신율 준비 상태 SSOT 연결 파일(구현 전 실제 경로 확정)
- `frontend/src/pages/sector-ranking-list.ts`
- `frontend/src/pages/sector-stock.ts`

**작업 체크리스트**:

- [ ] 기존 백엔드 수신율 임계값 게이트와 프론트 `sectorDataReady` 전달 경로를 확인한다.
- [ ] 프론트에서 수신율을 재계산하거나 마스터 캐시 원본을 직접 읽는 새 경로를 만들지 않는다.
- [ ] `sectorDataReady`를 실제 정상 업종 데이터 이벤트 또는 비-WS 확정 스냅샷에 연결한다. 초기 `sectorScoresWaiting=false` 기본값만으로 준비 완료로 판단하지 않는다.
- [ ] `DataTableOptions` 또는 동일한 공통 경로에 `widthReady` 준비 조건을 추가한다.
- [ ] 업종순위·업종별 종목 테이블만 `widthReady` 게이트를 사용하고, 일반 테이블은 기존 즉시 계산을 유지한다.
- [ ] 준비 전 `rows=[]` 또는 부분 rows가 들어와도 최종 폭을 고정하지 않는다.
- [ ] 준비 완료 후 현재 `rows`의 각 `ColumnDef.render()` 결과를 샘플로 사용해 1회 계산한다.
- [ ] 준비 완료 후 계산이 끝나면 다시 계산하지 않으며, 준비 이벤트가 중복되어도 폭을 변경하지 않는다.
- [ ] 수신율 임계값에 도달하지 않아도 안전 폭·대기 UI를 유지하고 다른 테이블을 중단하지 않는다.
- [ ] `P95_MIN_SAMPLES = 20` 추가.
- [ ] `ABSOLUTE_MIN_WIDTH = 36` 추가.
- [ ] `ABSOLUTE_MAX_WIDTH = 240` 추가.
- [ ] 설계서의 Nearest Rank 방식으로 `percentile(values, p)` 구현.
  - [ ] 입력 배열을 복사한 뒤 오름차순 정렬하여 원본을 변경하지 않음.
  - [ ] 빈 배열은 `0` 반환.
  - [ ] `Math.ceil((p / 100) * length)` rank와 마지막 인덱스 보호 적용.
- [ ] `data-table.ts`에서 type 캡과 페이지 캡을 각 축별로 병합한다.
  - [ ] 최소 폭은 type 최소값과 페이지 최소값 중 큰 값을 사용한다.
  - [ ] 최대 폭은 type 최대값과 페이지 최대값 중 작은 값을 사용한다.
  - [ ] 한쪽만 페이지에 지정된 경우 반대쪽 type 캡을 유지한다.
- [ ] `clampColWidth`에서 병합된 캡과 절대 캡의 교집합을 산출한다.
  - [ ] 최소 폭: `max(ABSOLUTE_MIN_WIDTH, mergedMinWidth)` 또는 절대 최소값.
  - [ ] 최대 폭: `min(ABSOLUTE_MAX_WIDTH, mergedMaxWidth)` 또는 절대 최대값.
  - [ ] 유효 최소가 최대보다 큰 경우 기존 `console.warn` 후 최대값으로 최소값 보정.
- [ ] 기존 `DEFAULT_MIN_WIDTH` 및 무한대 최대값 처리와 새 절대 캡의 중복·불일치를 정리한다.
- [ ] 함수 시그니처와 `CELL_HORIZONTAL_PADDING` 계산은 유지한다.

**세션 3 완료 조건**:

- [ ] `percentile`이 실제 `computeColWidths` 경로에서 호출될 준비가 됨.
- [ ] type/page 캡이 각 축별로 병합되고, 기존 type/page 범위보다 넓은 폭을 허용하지 않으며 절대 범위 밖 폭을 차단함.
- [ ] 준비 전 최종 폭 고정 보류와 준비 완료 후 1회 고정이 고정·가상 스크롤 모드 모두에서 동작함.
- [ ] 수신율 임계값 미도달 시 전체 화면·다른 테이블이 차단되지 않고 대기 상태가 표시됨.
- [ ] `npm run typecheck` 통과.
- [ ] 해당 단계의 코드만 커밋하고 실제 커밋 해시를 `HANDOVER.md`에 기록.

### 세션 4 — `computeColWidths` P95 연결 및 단위 테스트

**목표**: 데이터 샘플 수에 따라 max/P95를 선택하고, 수신율 준비 전·후 1회 고정 계약과 캡 병합을 테스트로 고정한다.

**수정 파일 후보**:

- `frontend/src/components/common/auto-width.ts`
- `frontend/tests/`의 기존 auto-width 테스트 파일 또는 구현 전 조사에서 확인한 가장 가까운 공통 컴포넌트 테스트 파일

**작업 체크리스트**:

- [ ] 각 컬럼의 샘플을 텍스트 폭 배열로 변환한다.
- [ ] 샘플 0개는 데이터 폭 `0`으로 두고 라벨 폭만 사용한다.
- [ ] 샘플 1~19개는 기존과 같이 샘플 최대 폭을 사용한다.
- [ ] 샘플 20개 이상은 `percentile(sampleWidths, 95)`를 사용한다.
- [ ] 최종 대표 폭은 항상 `max(labelWidth, dataWidth)`로 산출한다.
- [ ] 컬럼 간 계산 결과가 섞이지 않도록 기존 배열 순서와 반환 배열 길이를 유지한다.
- [ ] 단위 테스트를 추가한다.
  - [ ] 샘플 10개에서 Nearest Rank P95가 max와 같은 결과를 허용한다.
  - [ ] 샘플 20개와 긴 이상치에서 P95 대표 폭을 사용한다.
  - [ ] 빈 샘플은 라벨 폭 이상으로 계산된다.
  - [ ] 샘플 19개는 max 방식으로 계산된다.
  - [ ] 라벨 폭이 대표 데이터 폭보다 길면 라벨 폭을 우선한다.
  - [ ] 절대 최소·최대 캡과 병합된 type/page 캡의 교집합을 검증한다.
  - [ ] type 캡과 페이지 min/max가 각 축별로 병합되는지 검증한다.
  - [ ] minWidth가 maxWidth보다 큰 설정에서 경고·보정 동작을 검증한다.
  - [ ] P95 계산이 입력 배열을 변경하지 않는지 검증한다.
- [ ] 준비 전 rows에서는 `computeColWidths` 또는 `applyWidths`가 최종 폭 경로로 호출되지 않는지 검증한다.
- [ ] 준비 완료 후 첫 rows에서만 `render()` 결과를 사용해 폭을 계산하는지 검증한다.
- [ ] 준비 완료 후 rows·수신률 이벤트를 추가해도 폭 계산·적용이 다시 실행되지 않는지 검증한다.
- [ ] 준비 완료 이벤트가 중복되어도 컬럼 폭이 변경되지 않는지 검증한다.
- [ ] `sectorDataReady`가 WS 구독 시작 시 false, 임계값 통과 후 정상 데이터 이벤트에서 true가 되는지 검증한다.
- [ ] 비-WS 확정 데이터 스냅샷에서는 `sectorDataReady`가 불필요하게 false로 남지 않는지 검증한다.
- [ ] 실제 마스터 캐시 원본을 직접 참조하는 프론트 폭 계산 경로가 없는지 확인한다.

**세션 4 완료 조건**:

- [ ] `computeColWidths`가 설계서의 샘플 수별 전략을 정확히 따른다.
- [ ] 기존 테스트와 신규 테스트가 통과한다.
- [ ] `npm run typecheck` 통과.
- [ ] 해당 단계의 코드·테스트만 커밋하고 `HANDOVER.md`에 기록.

## 2. 금지 범위 및 회귀 방지 기준

- [ ] 공통 폭 경로(`auto-width.ts`, `data-table*.ts`)와 준비 상태 연결 외에 페이지 컬럼 정의를 임의로 수동 조정하지 않는다.
- [ ] `COLUMN_WIDTH` type별 값, 기존 `ColumnDef.minWidth/maxWidth`, `widthsToPercentages`, `createColumnWidthManager` 계약을 변경하지 않는다.
- [ ] 장중 재계산, 타이머·폴링, CSS `table-layout: auto`, 페이지별 비율 프리셋을 추가하지 않는다.
- [ ] 백엔드 수신율 계산·DB·주문 경로·전략 및 리스크 로직을 수정하지 않는다. 기존 서버 게이트와 이벤트 계약만 재사용한다.
- [ ] 프론트에서 `master_stocks_cache` 원본을 직접 읽어 폭을 계산하지 않는다. 실제 테이블 `render()` 결과만 사용한다.
- [ ] P95 계산을 외부 라이브러리로 대체하거나 신규 의존성을 추가하지 않는다. 내부 함수는 export하지 않고 `computeColWidths` 결과를 통해 검증한다.
- [ ] `asyncio.run()`, 무분별한 `create_task`, silent `except: pass`, dead code를 추가하지 않는다.
- [ ] 이상치 잘림이 설계 범위를 넘어 사용자에게 숨겨지지 않도록 기존 ellipsis 스타일과 실제 표시를 확인한다.

## 3. 검증 및 롤백 기준

### 3.1 검증 게이트

1. 구현 단계별 관련 단위 테스트.
2. `cd frontend && npm run typecheck`.
3. `cd frontend && npm run test`.
4. `cd frontend && npm run build`.
5. 브라우저에서 주요 3개 화면(매수후보·보유 종목·업종 순위) 시각 확인.

검증 실패 시 통과 전까지 다음 세션으로 넘기지 않고 원인을 추적한다. 테스트 실패가 기존 실패인지 판단해야 하는 경우 수정 전 상태와 비교하여 기록한다.

### 3.2 즉시 롤백 트리거

다음 현상이 발생하면 해당 구현 커밋을 `git revert <커밋 해시>`로 되돌리고 원인을 조사한다.

- 컬럼 헤더 또는 데이터가 기존보다 광범위하게 잘림.
- 컬럼 폭이 장중 데이터 수신마다 변함.
- type별 또는 페이지별 폭 지정이 무시됨.
- 빈 데이터 화면에서 헤더가 사라지거나 테이블 레이아웃이 깨짐.
- 수신율 임계값 통과 전 폭이 영구 고정됨.
- 임계값 통과 후 데이터가 들어올 때마다 폭이 변함.
- 일반 테이블까지 수신율을 기다려 화면 표시가 불필요하게 지연됨.
- 프론트 테스트·빌드 실패가 해결되지 않음.
- 거래·백엔드·DB 경로에 의도하지 않은 변경이 확인됨.

### 3.3 최종 승인 기준

- [ ] P95·샘플 20개·절대 가중치 상한 240·type/page 캡 교집합이 모두 구현됨.
- [ ] 수신율 임계값 미통과 시 최종 폭 계산이 보류되고, 통과 후 실제 render 결과로 1회 계산됨.
- [ ] 라벨 우선 규칙과 샘플 부족 전략이 테스트로 고정됨.
- [ ] 장중 폭 고정이 유지됨.
- [ ] 프론트 검증 게이트 통과.
- [ ] 사용자 브라우저 확인 완료 또는 미확인 상태를 명시적으로 기록.
