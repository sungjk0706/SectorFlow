## 1. 배경 및 목표

### 1.1 현재 상태

사용자 요구: "ARCHITECTURE.md가 앞으로 모든 코드 수정의 유일한 기준이 되어야 한다. 코드가 문서를 따라야 하며, 문서가 코드를 따라가서는 안 된다."

그러나 현재 문서(1,930줄)는 기준 문서 역할에 4가지 장애가 있다.

1. **문서-코드 불일치 5건 확인** (2026-07-29 코드 대조):
   - "코어 큐 4개" 표기 vs 실제 3개 코어 큐 (`core_queues.py` 주석·코드 모두 3개, `db_write_queue`는 별도 쓰기 큐)
   - 안전장치 표 "틱 드롭 5000개" vs 실제 큐 크기 20000 (5000은 코드 어디에도 없음)
   - Compute Loop 의사코드(`asyncio.wait` 동시 대기) vs 실제 구현(`wait_for` 0.5초 + 배치 드레인, `pipeline_compute.py`)
   - RiskManager "단일 종목 비중 한도 (TODO)" 표기 vs 실제 구현 완료·매수 차단 경로에서 작동 중 (`risk_manager.py`)
   - 1차 필터 키를 `sector_min_trade_amt`(5.1절)와 `min_avg_amt_eok`(6.3절) 두 이름으로 표기 — 설정 SSOT은 `sector_min_trade_amt`, 다른 하나는 함수 인자명
2. **수치의 주인이 불분명**: 큐 크기 등이 문서와 코드 양쪽에 존재 → 어느 쪽을 고쳐도 다른 쪽이 낡음 (드리프트 구조적 원인)
3. **지켜지지 않는 규칙 생존**: mypy(표준 게이트에서 이미 제외), 커버리지 80/95% 수치, Conventional Commits, CI/CD 부록, CHANGELOG 부록 — 문서에만 살아있는 규칙
4. **기준이 3곳에 분산**: ARCHITECTURE.md + AGENTS.md + 스킬 6개가 세션 절차·금지 패턴 등을 중복 기재

### 1.2 목표

1. 문서를 3개 층(L1 불변 원칙 / L2 설계 결정+근거 / L3 수치 참조표)으로 재편하여 "판단 기준의 주인은 문서, 수치의 주인은 코드 상수"로 소유권 확정
2. 원칙 25개를 12개로 통합 (내용 손실 없이 교차 중복 제거)
3. 지켜지지 않는 규칙 제거 + 절차성 내용은 AGENTS.md로 단일화
4. 누락된 실전 필수 기준 추가: 주문 멱등성, 기동 시 미체결 주문 복구 절차, 실전 모드 재기동 잔고 동기화 절차, 단계별 지연 예산표 (3단계에서 기준 정의만 — 코드 구현은 별도 승인 과제)
5. 불일치 5건 정합성 회복 (4단계)
6. 최종 분량 약 700줄 (사용자 동의, 단 강제 규칙 전량 보존 조건)

### 1.3 비목표

- 매매 전략·로직 변경 (문서 재정비 작업이 아님)
- AGENTS.md·스킬 파일 내용 재작성 (중복 내용의 이동·단일화만)
- CircuitBreaker 복구 프로브 등 신규 코드 구현 (기준 정의 후 별도 승인 과제로 분리)

## 2. 설계 방향

### 2.1 핵심 설계 결정

**결정 1: 문서 3층 구조 (L1/L2/L3)**
- L1 불변 원칙: 돈·안전 관련 절대 규칙. "~해야 한다"/"~금지" 표현만 사용
- L2 설계 결정과 근거: 구조 선택 + "왜" 2~3줄. 바꾸려면 문서부터 수정
- L3 수치 참조표: 문서에 값을 적지 않고 `파일명:상수명`만 기재
- 왜: 불일치 5건 중 2건(큐 개수, 드롭 수치)이 수치 이중 관리에서 발생. 수치의 주인을 코드 상수 1곳으로 몰면 문서는 영구적으로 참조만 하므로 드리프트가 구조적으로 차단됨

**결정 2: 원칙 25개 → 12개 통합**
- 통합안: W1 단일 루프·논블로킹(P1,P2,P3,P7,P14+금지패턴1·2·4) / W2 파이프라인 분리(P8,P9) / W3 SSOT(P10,P12,P13,P17) / W4 단계 간 정합성(P22) / W5 단일 주문 경로(P15) / W6 살아있는 안전장치(P16+금지패턴5) / W7 테스트모드 동등성(P18) / W8 폴백 금지(P20+금지패턴3) / W9 격리된 실패(P25) / W10 사용자 투명성(P21) / W11 표현 통일(P23) / W12 중복·과잉 추상화 금지(P24). 구조 선택 성격(P4,P5,P6,P11,P19)은 L2로 이동
- 왜: P10/P22/P23/P24가 "중복 제거"를 서로 교차 강화하며 같은 말을 반복 — 에이전트의 규칙 충돌 판단 비용과 문서 유지비용의 근본 원인
- 검증: 2단계 완료 시 기존 원칙→새 원칙 매핑표로 누락 0건 확인

**결정 3: 수치 소유권 분리 기준**
- 전략·안전 수치(50ms 경고/200ms 중단, CircuitBreaker 5회·60초, 구독 한도, 일일 손실 한도 기본값): **문서가 주인** — 값 + 근거 명시
- 구현 세부 수치(큐 크기, 배치 주기 0.1/0.2/0.5초, 쓰로틀): **코드 상수가 주인** — 문서는 L3 참조표에 위치만 기재
- 왜: 사용자 돈에 직결되는 값은 근거를 알아야 판단 가능(문서 소유), 튜닝 값은 바뀌어도 설계 판단과 무관(코드 소유)

**결정 4: 지켜지지 않는 규칙 제거**
- 삭제: 부록 F(커밋 규칙), J(CI/CD), K(CHANGELOG), G의 커버리지 80/95% 수치, L(API 문서화)
- 왜: 죽은 규칙은 살아있는 규칙의 신뢰를 깎음 (문서판 P16 — "기준인 척하는 dead rule 금지")

**결정 5: 절차성 내용은 AGENTS.md로 단일화**
- 이동: 세션 절차, 응답 형식, 작업 프로세스, 금지 패턴 체크리스트
- 왜: 기준이 3곳이면 "유일한 기준"이 아님. ARCHITECTURE.md는 "시스템이 어떻게 동작해야 하는가", AGENTS.md는 "작업자(AI)가 어떻게 작업해야 하는가"로 역할 분리

**결정 6: 불일치 5건은 전부 "코드가 옳고 문서가 낡음"으로 판정**
- 근거: (a) 틱 드롭 — 사용자가 "드롭 다발로 용량을 늘렸다"고 확인 (20000이 최신 의도), (b) 나머지 4건은 코드가 실제 실행 경로에서 작동 중인 사실이고 문서만 구형 (P16 — 살아있는 경로가 기준)
- 처리: 4단계에서 문서 수정 (코드 변경 없음)

**결정 7: CircuitBreaker 복구 판정의 정의 명시**
- 코드 확인 사실: 별도의 가상 점검 주문(probe)은 존재하지 않음. OPEN → 60초 경과 → 다음 주문 1건을 허용(HALF_OPEN)하여 그 성공/실패로 복구 판정. 테스트 모드에서는 가상 체결(돈 안 나감), **실전 모드에서는 실제 돈이 나가는 주문이 복구 판정을 겸함**
- 문서 기준: 위 사실을 그대로 명시 ("테스트 주문"이라는 표현 대신 "복구 판정 주문"으로 용어 정확화)
- 후속 과제(별도 승인 필요): 실전 모드 복구 시 주문 대신 계좌 조회 등 무비용 요청으로 생존 확인하는 방식 도입 여부

### 2.2 기각 방안

| 방안 | 기각 사유 |
|---|---|
| 문서에 모든 수치 + 근거 명시 | 코드와 이중 관리 → 드리프트 재발 (불일치 5건의 근본 원인 재현) |
| 원칙 25개 유지 + 부연 추가 | 교차 중복 구조가 유지비용의 근본 원인. 늘리는 방향은 목표(700줄)와 정면 충돌 |
| 복구 프로브 주문 즉시 구현 | 이번 작업은 문서 재정비. 코드 변경은 기준 확정 후 별도 승인 과제 |

## 3. 사용자 결정 항목

**Q1. CircuitBreaker "테스트 주문"은 실제 돈이 나가는가?**
- 사용자 답변: 가상 체결이다. 테스트 주문에 돈이 나가지 않는다.
- 코드 확인 결과: 테스트 모드에서는 답변대로 가상 체결. 그러나 실전 모드에서는 별도의 가상 점검 주문이 없고, **다음 실제 주문 1건(실제 돈)이 복구 판정을 겸함** — 답변과 차이가 있어 사용자에게 보고 완료
- 확정 기준: 결정 7대로 문서에 사실을 명시. 실전용 무비용 복구 점검 도입은 후속 과제(별도 승인)

**Q2. 브라우저를 닫으면 프로그램 전체가 꺼지는가?**
- 사용자 답변: 현재는 백엔드·프론트엔드까지만 기동하고 브라우저는 사용자가 직접 연다. 브라우저를 닫아도 백엔드는 계속 실행된다. 문서를 현재 방식에 맞게 수정 지시
- 코드 확인 결과: 답변대로 변경 확인 (시작 스크립트에 브라우저 자동 열기 없음, 접속 안내 출력만 존재, WS 끊김 시 자동 종료 로직 없음)
- 처리: ARCHITECTURE.md 3곳(WS 관리 절, 안전장치 표, 시작 스크립트 절차) 현행화 — 1단계에서 적용 완료

**Q3. 구독 한도 200의 근거는?**
- 사용자 답변: 키움증권 기준. LS증권은 더 많은 세션 한도(약 300개 이상) 제공
- 확정 기준: 문서에 "기본 200 = 키움증권 세션 한도 기준 보수적 상한, LS는 여유 있음" 근거 기재 (2~3단계에서 반영)

**Q4. 불일치 5건 판단 위임**
- 사용자 답변: 틱 드롭은 과거 드롭 다발로 용량을 늘린 기억이 있음. 나머지는 에이전트 판단에 위임
- 확정 기준: 결정 6 (전부 코드 정합, 문서 갱신)

**Q5. 문서 분량 약 700줄 동의 여부**
- 사용자 답변: 작업 에이전트들이 인식하는 데 문제만 없다면 동의
- 확정 기준: 강제 규칙 전량 보존(통합이지 삭제가 아님) + 매핑표 검증으로 누락 0건 보장 조건으로 진행
