### 문서 표준 포맷 (역할 기반)

> 다단계 작업 산출물(설계서·태스크 파일), 인계 문서(HANDOVER.md), 세션 종료 보고서의 표준 포맷. P10(SSOT) · P23(일관성) · P24(단순성) 부합.
> **핵심 원칙: 문서의 역할(Role)이 SSOT다. 섹션 구조는 구현체다.** 역할이 지켜지면 섹션 이름·순서·개수는 설계 규모에 맞춰 자유롭게 재구성 가능. 역할이 깨지면 포맷이 맞아도 의미 없음.
>
> **문서 언어 규칙 (필수)**: 설계서·태스크 파일·조사 보고서 등 `docs/` 산출물은 **파일명과 내용 모두 한글**로 작성한다. 파일명은 제목만 봐도 무슨 내용인지 알 수 있도록 작성(예: `docs/설계서/실시간_지연_개선.md`, `docs/태스크/실시간_지연_개선.md`). 영어 파일명 패턴(`architecture_*_design.md`, `plan_*.md`)은 더 이상 사용하지 않는다. (P23 일관성 — 사용자가 파일명만 봐도 내용 파악 가능)

#### 0. 문서 역할 원칙 (최상위 SSOT — 모든 문서 작성 전 필수 확인)

> 이 원칙이 깨지면 설계서가 태스크를 침범하거나, 태스크가 설계서를 반복하거나, AI가 설계 범위를 벗어나 로직을 추가하거나, 보고가 정보 전달로 끝나 승인 단계가 누락됨. 아래 5항목은 절대 불가침.

| 문서 | 역할 (책임) | 답하는 질문 | 금지 |
|---|---|---|---|
| **설계서** | "왜"를 책임진다 | 무엇을 왜 이렇게 바꾸는가? 채택/기각 이유는? 영향 범위는? | 구현 순서·파일/라인 단위 변경 내역·검증 명령 (태스크 영역) |
| **태스크** | "어떻게"를 책임진다 | 어떤 파일의 어떤 함수를 어떤 순서로 바꾸는가? | 설계 배경·결정 사유·원칙 부합 검토 (설계서 영역) — 설계서 경로 참조만 |
| **구현** | 태스크를 따른다 | 태스크에 없는 로직/분기/상태를 추가하지 않는다 | 설계서·태스크에 없는 신규 로직 추가 (설계 이탈) |
| **검증** | 설계의 완료 기준을 따른다 | 설계서 "완료 기준"이 충족되었는가? | 태스크 체크박스만 채운다고 완료 아님 — 설계 완료 기준이 최종 판정 |
| **사용자 보고** | 결과와 상태를 알리고 필요한 경우에만 결정을 받는다 | 사용자가 무엇을 얻었는가? 추가 결정이 필요한가? | 작업 완료인데 승인 요청·다음 단계 질문을 붙임 — 완료 시 `없음(작업 종료)`으로 마침 |
| **HANDOVER** | 다음 세션 인계를 책임진다 | 다음 세션이 어디서부터, 어떤 승인 상태로 이어지는가? | 구현 상세 인라인 전개·설계/태스크 내용 반복·승인 없는 단계를 진행 가능으로 표시 |

**역할 분리의 핵심 경계 (P10 중복 방지)**:
| 항목 | 설계서가 담당 (추상화 상위) | 태스크가 담당 (추상화 하위) |
|---|---|---|
| 변경 | 개념 수준 — 모듈/데이터 흐름/인터페이스가 어떻게 바뀌는가 | 파일/함수/라인 수준 — 어디를 어떻게 바꾸는가 |
| 완료 | 사용자 관점 수용 조건 ("보유종목 현재가가 X 기준으로 표시된다") | 구현자 체크 조건 ("X.ts의 Y 참조를 Z로 변경", "typecheck 통과") |
| 검증 | 위험도 등급 + 적용 게이트 수준 (상위) | 단계별 구체적 검증 명령 |
| 비목표 | 설계가 다루지 않는 것 + 사유 | (설계서 비목표를 그대로 인용, 반복 서술 금지) |

**공통 헤더 (모든 문서)**: 제목(`# <종류>: <기능 한글명>`) + 인용 블록(상태 · 작성일 · 관련 원칙 P번호 · 관련 파일 경로). 설계서/태스크 파일에 적용. HANDOVER는 고정 헤더(`# SectorFlow HANDOVER`).

#### 1. 설계서 포맷 (`docs/설계서/*.md`)

**역할**: "무엇을 왜 이렇게 바꾸는가"를 확정. 2세션 태스크 파일의 입력. **전체 작업 완료 시 삭제(규칙 10) — 작업 완료 체크리스트 3단계에서 삭제**. 일부 단계만 완료 시 유지.

**파일명**: `docs/설계서/<기능명_한글>.md` (예: `docs/설계서/실시간_지연_개선.md`). 기능명은 제목만 봐도 내용을 알 수 있도록 한글로 작성. 단어 구분은 밑줄(`_`) 사용. 폴더명이 종류를 나타내므로 파일명에는 `설계서_` 접두어를 붙이지 않는다.

**역할별 필수 내용** (역할이 SSOT — 아래 내용은 반드시 포함되어야 하나, 섹션 구분/순서는 설계 규모에 맞춰 자유):

| 역할 | 내용 | 작성 가이드 |
|---|---|---|
| 목표 | 사용자 관점 달성 항목 | 번호 목록. "이 설계로 무엇이 달성되는가" |
| 비목표 (Not To Do) | 다루지 않는 것 + 사유 | 명시적 나열. 태스크에 그대로 인용됨 — 사유 포함 필수 |
| 문제 + 현재 구조 | 기존 구조/문제, 코드 위치 인용 | 통합 권장(작은 변경) 또는 분리(큰 변경). 코드 위치는 `<ref_file>`/라인 인용 |
| 채택안 + 이유 | 핵심 설계 결정, 각 결정마다 "왜" | 결정 N번 항목. "왜"가 빠지면 설계서 본질 상실 |
| 기각안 + 사유 | 고려했으나 기각한 방안 | 표: 방안 \| 기각 사유. "왜 안 됐는지"가 채택안 이유 보완 |
| 영향 범위 | 백엔드/프론트/DB/거래 로직 — 개념 수준 | "무엇이 어떻게 바뀌는가". 파일/라인 단위는 태스크 영역 — 침범 금지 |
| 아키텍처 원칙 부합 | P원칙별 ✅/위반 + 근거 1줄 | 헤더 "관련 원칙"과 교차 검증 |
| 위험도 산정 | 높음/중간/낮음 + 근거 | "검증 계층 게이트" 입력. 비개발자용 3줄 요약과 함께 승인 판단 근거 |
| 완료 기준 | 사용자 관점 수용 조건 체크리스트 | 검증의 최종 판정 기준 — 태스크 완료 조건은 여기서 파생 |

**조건부 포함** (위험도/복잡도 기반 — 역할 원칙 위에서 자율 판단):
- `사용자 결정 항목` — problem-solve 섹션 1-1 의무. 사용자 질문·답변 그대로 기록. 2세션 태스크에서 활용
- `동작 원리` — 데이터 흐름/상태 전이 복잡 시 (전이 2개+ 또는 상태 변수 3개+). 단순 시 채택안에 통합
- `사전 롤백 계획` — 위험도 '높음'/'중간' 시. "검증 계층 게이트" 연계 (safe-trade 스킬)

**다중 이슈 설계 대응**: 단일 기능이 아닌 다중 이슈를 다루는 설계(예: `docs/설계서/실전모드_불일치_조정.md`)는 문제/채택안/영향범위를 이슈별 그룹화 허용. 단, 목표/비목표/원칙 부합/위험도/완료 기준은 전역 단위로 유지 — 역할 원칙은 다중 이슈에서도 동일 적용.

**작성 완료 후 액션**: 사용자에게 설계 요약 보고(일반 사용자 용어, 규칙 0-4) → 승인 대기(규칙 0) → 승인 시 HANDOVER "다음 세션 진행 대기"에 설계서 경로 + 2세션 예정 명시.

#### 2. 태스크 파일 포맷 (`docs/태스크/*.md`)

**역할**: 설계서("무엇을 왜 바꾸는가")를 실행 가능한 체크리스트("어떤 파일을 어떤 순서로 바꾸는가")로 분해. 3세션~ 구현의 지시서. **전체 작업 완료 시 삭제(규칙 10) — 작업 완료 체크리스트 3단계에서 삭제**. 일부 단계만 완료 시 유지. **0절 "문서 역할 원칙" 준수 — 설계서 반복 금지, 설계서 경로는 헤더에 명시하고 참조만.**

**파일명**: `docs/태스크/<기능명_한글>.md` (설계서와 동일 기능명, 예: `docs/태스크/실시간_지연_개선.md`). 폴더명이 종류를 나타내므로 파일명에는 `태스크_` 접두어를 붙이지 않는다.

**필수 섹션**:
| 섹션 | 가이드라인 |
|---|---|
| 헤더 블록 | `# 태스크 파일: <기능 한글명> 구현` + 인용 블록(상태/작성일/설계서 경로/다단계 진행 상황 각 세션 ✅/**현재 단계**/**남은 단계**/**다음 세션 진행 단계**/관련 원칙) |
| 목표 | 1~2문장. 이 태스크가 달성할 핵심 결과. 설계서 요약 반복 금지 — 핵심 결과만. (예: "보유종목 현재가 표시 소스를 master_stocks_cache.cur_price로 변경. 계산은 positions.calc_cur_price를 그대로 사용.") |
| 변경 대상 파일 | 표: 파일 \| 수정 목적(1줄) \| 수정 포인트(함수명/라인) \| 수정 범위. 코드 스니펫 전문 대신 포인트 중심 — 상세 구현은 구현 세션에서 코드에 직접 반영 |
| 작업 순서 | 체크리스트 형태. 단계별 구분(1단계: … / 2단계: …). 각 단계마다 완료 체크박스(`- [ ]`). 세션당 1단계 원칙(규칙 0-1) — 다세션 시 각 세션별 단계 분리. 각 단계 끝에 검증 방법 명시(py_compile/ruff/pytest/런타임 기동/프론트 빌드 중 해당). **체크박스를 `[x]`로 바꾸기 전에 해당 단계 검증 출력(증거)을 먼저 확인·기록 (default-FAIL contract — 섹션2 "작업 완료 시 점검 체크리스트" 1단계와 동일 강제)** |
| 금지사항 (Not To Do) | 설계서 비목표와 동일하게 유지. 하지 말아야 할 것 명시. (예: "백엔드 변경 없음", "DB 변경 없음", "신규 플래그 없음", "신규 상태머신 없음") |
| 완료 조건 (Done Criteria) | 체크리스트(`- [ ]`). 구현자가 체크 가능한 조건 — **설계서 "완료 기준"(사용자 관점)에서 파생된 구현 수준 조건**. (예: "positions.ts의 cur_price 참조를 master_stocks_cache.cur_price로 변경", "computePositionValuation의 cur_price==null 분기 유지", "typecheck 통과", "pytest 해당 경로 통과"). 설계서 완료 기준을 그대로 복사하지 않음 — 구현자가 체크할 수 있는 단계로 전개 |

**선택 섹션** (필요시만):
- `사용자 결정 항목` — 설계서 "사용자 결정 항목" 섹션에서 이관. 구현 중 추가 결정 시 누적 기록
- `테스트 계획` — 신규 테스트 케이스 목록 (테스트 추가 세션)
- `런타임 검증 방법` — 기동 명령, 확인 API, 체크 포인트 (백엔드 변경 시)
- `바로잡음 로그` — 구현 중 태스크 기재 오류 발견 시 원인+수정 기록 (NWS/FIX-WS-04에서 실제 사용 패턴). 이견 조정 프로토콜 결정 사유도 여기에 기록 ("왜 이 결정을 택했는지")
- `사전 롤백 계획` — 위험도 '높음'/'중간' 시 필수. (a) 롤백 명령(`git revert <해시>`), (b) 즉시 롤백 트리거 증상(예: 주문 두 번, 손익 이상). "검증 계층 게이트" 참조

**작성 완료 후 액션**: 사용자에게 작업 순서 요약 보고(예상 세션 수 + 각 세션 범위) → 승인 대기(규칙 0) → 승인 시 HANDOVER "다음 세션 진행 대기"에 태스크 파일 경로 + 3세션 예정 명시.

#### 3. HANDOVER.md 포맷

**목적**: 다음 세션 인계 — 다음 세션이 어디서부터, 어떤 승인 상태로 이어지는가를 전달 (0절 역할 표). **인덱스 역할만** 수행(규칙 8-2). 삭제 금지 — 살아있는 문서.

**파일명**: 고정 `HANDOVER.md` (프로젝트 루트)

**필수 섹션**: **규칙 8-1 "HANDOVER.md 표준 섹션 구조" 참조** (P10 SSOT — 중복 정의 금지). 요약:
- `세션 개요` (최근 1건, 메타 담당) · `직전 완료 작업` (최근 1건, 본문 담당, 항목당 3~5줄) · `다음 세션 진행 대기` (완료 항목 즉시 제거, 항목당 3줄 이하, **승인 상태 필수** — "승인 완료—진행 가능" / "승인 대기—코드 수정 금지", **다음 안전 동작 필수** — 재검증 없이 안전하게 할 수 있는 가장 구체적인 한 동작, **이번 세션 검증 누락 필수** — 아직 검증하지 않은 것 1줄, 해당 없음 시 "없음", **이번 세션 가정·위험 필수** — 틀릴 수 있는 가정·위험 1줄, 해당 없음 시 "없음") · `미해결 문제` (규칙 9, 완료 항목 즉시 제거)

#### 4. 사용자 보고 포맷 (채팅 출력, 파일 아님)

**역할**: 0절 "문서 역할 원칙" 5번째 — 사용자 보고로 사용자가 결과와 현재 상태를 이해하고, 추가 결정이 필요한 경우에만 결정할 수 있게 한다. `작업 완료` 보고는 승인 요청이 아니라 종료 알림이다. 파일로 저장하지 않음(휘발 — 상세는 git 커밋 메시지에 영구 기록, HANDOVER는 세션 간 소통 인덱스). **일반 사용자 용어로 쉽게 설명**(규칙 0-8 1항 — 규칙 0-4 통합).

> **단일 템플릿 (누락 방지 — 강제)**: 완료 보고 작성 시 `docs/절차규칙/완료보고_템플릿.md`를 복사하여 빈 칸을 채우는 방식으로 작성. 본 섹션의 규정(자동 수행 순서·명시 의무·표 메뉴·종료 체크리스트)이 템플릿 한 곳에 통합되어 있어, 보고 작성 순간에 4곳을 각각 떠올리지 않아도 됨. 템플릿 사용 시에도 본 섹션의 규정을 위반해서는 안 됨 — 템플릿은 규정의 실행 보조이지 규정 자체를 대체하지 않음.

**핵심 원칙**: 보고 전에 종료 상태를 먼저 분류한다. `작업 완료`와 `단계 완료·대기`는 질문·승인 요청 없이 마무리하고, `중단·보류`에서만 재개에 필요한 결정을 요청한다.

**출력 구조 (한 줄 요약 → 표 → 종료 또는 필요한 결정)**:

1. **한 줄 요약** (보고서 제목 바로 아래, 모든 보고에 필수): 이번 작업으로 무엇이 달라졌는가 — 사용자 관점, 1문장.
2. **표 배치** (섹션3 "표 선택 가이드"에 따라 선택): 이모지 요약 줄은 생략(중복 방지). 작업 성격에 맞춰 선택한 표를 실제 내용으로 채워 출력.
3. **세션 종료 체크리스트** (정식 보고 시 필수 — 보고서 마지막): 검증·Git Commit·HANDOVER·Push·현재 상태·사용자 결정. `작업 완료`이면 사용자 결정은 `없음(작업 종료)`으로 표시한다.
4. **보고 봉인**: `작업 완료` 또는 `단계 완료·대기` 보고 뒤에 다음 단계 제안·질문·승인 요청·추가 작업 권유를 붙이지 않는다. **봉인은 체크리스트(7번) 생략을 의미하지 않는다 — 체크리스트는 보고의 필수 부분이고, 봉인은 체크리스트 이후의 추가 내용만 금지한다.**

**표 메뉴 (섹션3 "표 선택 가이드" 참조 — 7개 기본)**:
1. **변경 내용 표** — 사용자 관점 변경사항 (문제/필요성/근본 원인/수정 방안/개선 결과/영향 범위)
2. **아키텍처 원칙 판별 표** — P1~P25 전체 판정 결과와 근거 1줄씩. 시작 전 판정과 완료 판정을 대조하여 기록
3. **검증 결과 표** — 기계적 검증(typecheck/test/build) + 의미적 검증(설계 준수·원칙·완료기준)
4. **최종 판별 표** — 근본 원인 해결·원칙 부합·안전 규칙·검증 통과·사용자 승인·경고
5. **커밋 및 핸드오버 표** — git 커밋/푸시/HANDOVER/설계·태스크 문서 갱신/미해결/다음 세션/사용자 확인. **7번 "세션 종료 체크리스트" 사용 시 커밋/푸시/HANDOVER/사용자 확인 행은 중복 생략 — 본 표 고유 항목(설계·태스크 문서 갱신/미해결)만 표시 (P24)**
6. **설계 완료 기준 충족 표** (다단계 작업 시) — 설계서 완료 기준 항목별 ✅/⚠️ + 근거
7. **세션 종료 체크리스트** (정식 보고 시 필수) — 검증/Git Commit 완료 여부/HANDOVER 갱신/Push/현재 상태/사용자 결정. 상세 식별자는 내부 인계 문서에만 기록. 완료 시 `없음(작업 종료)`, 대기 시 필요한 결정만 표시

> **추가 표**: 작업 성격에 따라 기본 7표 뒤에 추가 표를 둘 수 있다(조사 보고서의 조사 범위 표·비교 분석 표, 다단계 작업의 단계별 진행 표 등). 기본 표의 행을 중복 생성하지 않고 별도 관점을 다루는 경우에만 추가.
