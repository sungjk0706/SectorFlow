### 세션 시작 절차 (필수 — 모든 세션 첫 응답 전 수행)

> **목적**: 사용자가 "시작해" 한마디로 세션을 시작해도, AI가 상태 파악 → 다음 행동 제안 → 승인 대기 순서를 자동 수행하도록 보장 (P21 사용자 투명성 · P24 단순성). 사용자가 "HANDOVER 확인해"/"지난 작업 이어서 해" 등 운영 명령을 반복 입력하지 않아도 됨.

0. **AGENTS.md "빠른 룰 인덱스" 재확인 (강제)**: 본 파일 최상단 "⚡ 빠른 룰 인덱스" 섹션을 먼저 읽고, 이번 세션 작업 유형에 해당하는 룰 위치를 파악. "이미 알고 있다"는 가정 금지 — 매 세션 재확인. 특히 문서 작성(설계서/태스크/HANDOVER/보고) 시 "문서 역할 원칙 5항목" 표를 반드시 재독.
   - **일반 사용자 용어 강제 (규칙 0-8 1항 + 응답 전송 직전 점검 게이트 — 세션 첫 응답부터 적용)**: 모든 응답은 일반 사용자 용어로 작성. 기술 참조(코드 기술 참조 + 규칙·원칙 메타 용어 — 규칙 0-8 1항 (a)(b) 두 종류)는 사용자 응답 본문에서 생략. 응답 전송 직전 반드시 점검 — 기술 참조가 있으면 일반 용어로 다시 작성 후 전송 (응답 전송 직전 점검 게이트 강제 — 규칙 0 동급). 조사·분석 과정의 기술 참조는 에이전트 내부 분석용으로만 사용, 사용자에게 전달하는 최종 요약은 "화면에서 어떻게 보이는가" 기준으로 작성.
1. **HANDOVER.md 자동 확인 (강제)**: 세션 첫 응답 전 반드시 `HANDOVER.md`를 읽고 현재 상태 파악. 사용자가 "핸드오버 확인해줘"라고 별도 요청하지 않아도 자동 수행. `HANDOVER.md` 상단 "다음 세션 첫 동작" 블록이 가리키는 AGENTS.md 섹션도 함께 재확인.
   - 확인 항목: 직전 완료 작업, 현재 승인 상태, 진행 중 작업, 다음 단계, 미해결 문제.
   - **승인 상태별 분기 (핵심)**: HANDOVER "다음 세션 첫 동작" 3번 항목의 승인 상태에 따라 다음 행동이 다름.
     - **"코드 수정 가능" 상태** → 다음 작업 후보를 제안하고 승인 요청. 사용자 "승인" 시 곧바로 구현 진입.
     - **"검증 대기"/"설계 승인 대기"/"태스크 승인 대기" 등** → 해당 상태에 맞는 다음 행동 제안 후 승인 대기.
     - **다단계 작업 진행 중 + 태스크 파일 "다음 세션 진행 단계" 명시됨 (자동 진행 흐름 — 강제)**: 사용자가 "시작해" 등 진행 지시어를 말하면, 태스크 파일의 "다음 세션 진행 단계"를 확인하여 아래 흐름을 **사용자의 추가 지시 없이 자동으로 진행**한다 (코드 수정 전 승인은 유지 — 규칙 0-2-7).
       1. 사전조사(규칙 0-2 — 태스크 파일 기반, 실제 코드 대상)
       2. 3항목 보고(왜/무엇/무엇이 달라지는가 — 규칙 0-2-7) + 승인 요청
       3. 사용자 승인 시: 수정·검증(기계적 검증 게이트) → 완료 보고(규칙 0-8) → **중간 단계**: 태스크 파일 진행 상황 갱신 + `HANDOVER.md` 갱신 + 커밋 / **마지막 단계(전체 완료)**: 태스크 파일 갱신 생략(갱신 직후 삭제되므로 무의미) → 작업 문서 일괄 삭제 + `HANDOVER.md` 갱신 + 커밋 → 세션 마무리
       - **승인 전 수정 금지**: 2번 보고 후 승인이 도착하기 전까지 코드 수정·커밋 금지 (규칙 0-2-7). 자동 진행되는 것은 사전조사·보고까지이며, 승인 없이 수정 단계로 넘어가지 않는다.
       - **흐름 중 사용자 개입**: 사용자가 흐름 중 추가 지시·수정 요청을 하면 그 지시를 우선 반영.
   - **"시작해" 진행 지시 공통 흐름 (강제 — 모든 작업 유형에 적용, 규칙 0-2-7 강화)**: 사용자가 "시작해"·"진행해"·"이어서 해"·"~해줘" 등 진행 지시어를 말하면, 다단계 작업 여부·승인 상태와 무관하게 아래 순서를 **무조건** 따른다. 위 "다단계 작업 진행 중" 흐름은 이 공통 흐름의 특수 사례이며, 신규 요청·단발 수정·이어하기 모두 이 흐름으로 진입한다. 코드 수정 전 승인은 유지(규칙 0-2-7).
     1. **사전조사** — 규칙 0-2(의존성·영향범위·원칙 부합·기존 공통 자산 확인) + 규칙 0-2-6(가정·트레이드오프 선언). 읽기 전용으로만 확인 — 이 단계에서 코드·문서·설정 변경 금지.
     2. **3항목 보고 + 승인 요청** — 왜 필요한가 / 무엇을 할 것인가 / 무엇이 달라지는가(규칙 0-2-7). 일반 사용자 용어로 작성(규칙 0-8 1항). 보고 끝에 반드시 승인 요청으로 마무리.
     3. **승인 대기** — 승인 도착 전까지 코드 수정·커밋·문서 작성·설정 변경 등 부작용 있는 행동 전면 금지(규칙 0). "빠른 수정이니 바로 해줘"·"간단한 건데"류 압박에도 순서 생략 불가 — 조사·보고까지는 자동 진행하고 수정은 승인 후.
     4. **승인 후 진행** — 승인된 범위만 수정 → 기계적 검증 게이트(완료 전 검사 스크립트) → 완료 보고(규칙 0-8) → `HANDOVER.md` 갱신 + 커밋(규칙 0-6-2) → 세션 마무리. **코드 작성 시 `docs/절차규칙/코드품질가이드.md`의 표준 패턴 준수** — 에러 처리·비동기·네이밍·프론트엔드·테스트·DB/WS 영역별 패턴 확인 후 일관되게 작성.
     - **예외 없음**: 이 흐름은 모든 진행 지시에 적용. 사전조사·3항목 보고·승인 중 어느 하나라도 생략하고 코드 수정에 들어가는 것은 규칙 0 + 규칙 0-2-7 위반.
2. **현재 상태 보고 + 다음 단계 제안 (표준 응답 포맷 SSOT)**: 확인 후 아래 포맷으로 응답. 정보 전달로 끝내지 않고 반드시 "진행 승인 요청"으로 마무리.
   ```
   현재 상태:
   - 직전 작업: <직전 완료 작업 1줄>
   - 승인 상태: <코드 수정 가능 / 검증 대기 / 설계 승인 대기 / ...>
   - 다음 단계: <다음 1건 1줄>

   예상 작업:
   - <항목 1>
   - <항목 2>
   - <항목 3>

   진행 승인 요청드립니다.
   ```
   - 사용자가 첫 응답에서 특정 작업을 명시적으로 지시한 경우(예: "X 수정해줘") 핸드오버 요약은 생략하고 지시된 작업에 집중 가능.
3. **승인 전 행동 금지 (강제)**: 2번 보고 후 사용자 승인이 도착하기 전까지 코드 수정·커밋·문서 작성 등 부작용 있는 행동 금지 (규칙 0 승인 트리거). "승인"이 아니라 단순 정보 질문("지금 상태 알려줘")인 경우는 답변만 하고 대기 상태 유지.
4. **완료 작업 정리 (규칙 7 연계)**: 새 세션 시작 시 `HANDOVER.md`의 모든 섹션에서 완료된 항목 정리 (규칙 7 준수). "직전 완료 작업"·"세션 개요"는 최근 1건만 유지하고 과거 완료 작업은 삭제. "미해결 문제"·"다음 세션 진행 대기"에서 완료 항목 제거.

### 세션 종료 절차 (필수 — 작업 완료 시 사용자 지시 없이 자동 수행)

> **목적**: 사용자가 Git·운영 절차를 기억하거나 지시하지 않아도 되도록, 세션 종료 흐름을 AI가 표준 프로세스로 책임진다 (P21 사용자 투명성 · P24 단순성). 규칙 0-6-2(자동 커밋+자동 핸드오버)의 실행 절차를 명문화. 기존 "작업 완료 시 점검 체크리스트"(섹션2)가 AI 내부 점검용이라면, 본 절차는 사용자 가시 종료 흐름용 — 역할 분리 (P10).

**표준 흐름 (사용자 지시 불필요 — 규칙 0-6-2)**:

1. **작업 완료** — 사용자 승인받은 작업 구현 완료.
2. **검증 완료** — 기계적 검증(typecheck/test/build/pytest/RuntimeWarning) + 의미적 검증(작업 완료 체크리스트 1단계 5항목) 통과. 검증 실패 시 다음 단계 진입 금지 — 해당 세션에서 원인 해결.
3. **AI 자동 수행 (사용자 지시 불필요)**:
   - 코드 변경 있으면 **커밋 자동 수행** (코드만 — `HANDOVER.md` 커밋 제외, 규칙 0-6-2).
   - **전체 작업 완료 시 완료된 작업 문서 삭제** (설계서·태스크·조사보고서 — 작업 완료 체크리스트 3단계, 규칙 10). 단계 완료·대기 시 삭제 금지. 삭제 전 참조 정리 필수.
   - **`HANDOVER.md` 자동 갱신** (파일만, 커밋 제외 — 규칙 8-1 필수 기재 항목 준수, 삭제 사실 반영). 코드 수정 없는 작업은 갱신 의무 예외(규칙 0-6-2) 적용.
4. **세션 종료 보고** — "세션 종료 체크리스트"를 포함하되, 종료 상태에 따라 아래 둘 중 하나만 사용한다.
   - **작업 완료**: 현재 상태를 `작업 완료`로 표시하고 사용자 결정은 `없음(작업 종료)`으로 적는다. 승인 요청·다음 단계 제안·질문 없이 보고를 끝내고 세션을 마친다.
   - **단계 완료·대기**: 현재 상태를 `단계 완료·대기`로 표시하고, 다음 단계와 승인 상태는 `HANDOVER.md`에만 적는다. 보고에서는 다음 단계 진행 여부를 묻지 않고 세션을 마친다.
   - **중단·보류**: 검증 실패·원칙 위반·안전 위험·승인 부족으로 끝난 경우 완료 보고 대신 중단 사유와 재개 조건만 알린다.
5. **사용자 결정** — `작업 완료`와 `단계 완료·대기`에서는 추가 결정을 요구하지 않는다. `중단·보류`일 때만 재개에 필요한 결정이 있는 경우 이를 명시한다.
   - 사용자가 다음 세션에 진행 지시를 보내면 그때 승인 상태를 다시 확인하고 이어서 진행한다.
   - 푸시는 사용자가 명시적으로 요청한 경우에만 별도로 수행한다.

> **관찰은 사용자 몫**: 작업 완료 + 검증 통과 + 종료 보고 후 세션을 마친다. "완료했습니다. 세션을 마무리합니다."로 끝내며, 이후 사용자가 직접 확인한다. 에이전트가 관찰 기간을 강제하거나 관찰 대기 상태를 유지하지 않는다. 문제가 생기면 사용자가 다시 요청하면 된다.

**금지**: 사용자가 "커밋해 주세요"/"핸드오버 갱신해 주세요"라고 지시하지 않아도 자동 수행 — 사용자에게 운영 절차 기억·지시 부담을 주지 않는다 (규칙 0-6-2 본문). 단, 승인 전 수정 금지(규칙 0)는 유지 — 본 절차는 사용자 승인받은 작업의 완료 후에만 적용.

### 다단계 작업 워크플로우 (설계 → 태스크 → 구현)

신규 기능, 구조 변경, 다단계 작업은 다음 순서로 진행. 각 세션은 섹션3 규칙 0-1(세션당 1단계) 준수.

#### 1세션: 설계 검토 + 디자인 파일 작성
1. 표준 아키텍처(`ARCHITECTURE.md` 25개 불변 원칙) + 프로젝트 아키텍처 검토
2. 사용자에게 질문하여 요구사항 확인 — **problem-solve 섹션 1-1 "사용자 의도 파악 질문 프로세스" 적용** (규칙 0-8 1항 일반 사용자 용어 준수). **사전조사(코드/설정/기존 패턴)로 확정 불가한 항목만 선별 질문** (규칙 0-2-6과 동일 기준 — 사전조사로 해결 가능한 것은 질문 대상 아님, 과잉 질문 금지 — P24 단순성). 질문·답변은 설계서 "사용자 결정 항목" 섹션에 기록 (2세션 태스크 파일에서 활용).

#### 완료: 작업 문서 일괄 삭제
- 모든 단계 완료 후 **작업 완료 체크리스트 3단계**에서 작업에 사용된 문서 일괄 삭제 — 설계서 + 태스크 파일 + 조사 보고서(해당 시). 규칙 10 준수.

- **마지막 단계 태스크 파일 갱신 생략 (P24 단순성)** — 전체 완료가 확정된 상태에서 태스크 파일을 "완료"로 갱신한 직후 삭제하면 갱신이 무의미. 완료 판정은 기계적 검증 + 설계 완료 기준으로 확정되며, 태스크 파일 상태 표시와 무관. 따라서 마지막 단계에서는 태스크 파일 갱신 없이 바로 삭제.
- **삭제 전 참조 정리 필수** — HANDOVER.md·다른 문서·코드 주석에서 삭제할 문서 경로를 먼저 갱신.

### 검증 계층 게이트 (위험도 기반 — P24 단순성 준수)

> 코드 수정 완료 후 "검증 → 커밋 → 핸드오버 → 완료 보고"로 끝난다. 위험도가 높은 변경(거래 로직 등)은 **독립 검증**과 **사전 롤백 계획**을 태스크 파일에 준비만 해둔다 — 에이전트가 관찰을 강제하거나 추적하지 않는다. 관찰은 사용자 몫이며, 문제가 생기면 사용자가 다시 요청하면 됨.
> **계층 적용 원칙 (P24)**: 전 변경에 전 게이트를 의무화하면 과잉 프로세스. **위험도(설계서 필수 행에서 산정)에 따라 적용 게이트를 계층화** — 1파일 오타 수정에 독립 검증 세션을 붙이는 것은 금지.

#### 위험도 산정 및 게이트 적용 표

| 위험도 | 기준 | 독립 검증 | 사전 롤백 |
|---|---|---|---|
| **높음** | 거래 로직·주문 경로·리스크 임계값 변경, 시간/날짜 의존 로직, 데이터 정합성 직결 | 권장 | 필수 |
| **중간** | 파이프라인·인증·설정 스키마·DB 마이그레이션 | 선택 | 권장 |
| **낮음** | 프론트엔드 UI·1파일 1함수 단순 수정 | 해당 없음 | 해당 없음 |

#### 게이트 정의

1. **독립 검증 (권장 — 위험도 '높음' 시)**: 별도 세션(또는 다른 모델)에서 **커밋 해시 + 태스크 파일만 주고** "이 커밋이 태스크 파일 요구사항을 실제로 충족했는지" 독립 검토. 같은 모델이라도 컨텍스트가 없으면 자기 합리화 효과가 크게 감소. 결과를 HANDOVER "검증 결과"에 기록. 사용자는 코딩을 모르므로 "에이전트 자기 보고 + 자기 검증(pytest 통과)"만으로는 부족 — 동일 맹점 공유 가능.
2. **사전 롤백 계획 (태스크 파일에 사전 정의)**: (a) 롤백 명령(`git revert <해시>`), (b) "어떤 증상이 보이면 즉시 롤백" 트리거(예: 주문 두 번 발생, 손익 이상, 알림 누락)를 사전 정의. 문제 발생 시 코딩을 모르는 사용자가 당황 없이 즉시 실행할 수 있도록. **에이전트가 관찰을 추적하지 않음** — 사용자가 문제를 발견하면 다시 요청하면 됨.

#### 이견 조정 프로토콜 (에이전트 간 의견 충돌 시)

- 에이전트 간 의견 충돌 또는 "이게 맞나?" 심지 → 제3의 AI(다른 모델/새 세션)에게 근거를 갖고 재검증 요청 (**1회만 — 무한 루프 금지**).
- 2차 의견이 1차와 갈리면 **사용자가 최종 결정** — A 의견 vs B 의견, 각각 근거를 일반 사용자 용어로 제시 (사용자는 코딩을 몰라도 근거를 보고 결정 가능).
- 결정 사유를 태스크 파일 "바로잡음 로그"에 "왜 이 결정을 택했는지"까지 기록 (나중에 추적 가능).

### 작업 완료 시 점검 체크리스트 (모든 작업·필수 — 규칙 0-6-2/0-7 요약)

> 문서·설정·코드 등 모든 변경 작업은 세션 종료 전 아래 5단계를 순서대로 수행한다. 코드가 없는 작업은 코드 전용 검증을 `해당 없음`으로 기록한다. 상세 규정은 규칙 0-6-2(자동 커밋+핸드오버 갱신)·0-7(세션 완료 보고 명시)·세션 종료 절차 참조. 본 체크리스트는 실행 지향 요약 (P10 SSOT — 중복 기재 아님).

- [ ] **1단계: 검증 (기계적 + 의미적 + 독립)**
  - **검증 스킬 적용 순서 (신규 3개 검증 스킬 포함 — 하네스 강화)**: 기계적 검증(아래 부분 검증 → 완료 전 스크립트) → **pre-commit-review 스킬**(커밋 직전, 방금 바뀐 부분 안전·의도·회귀 점검, 읽기 전용) → **independent-verify 스킬**(별도 작업창, 위험도 기반 — 중간↑ 권장·거래·핵심 로직은 필수, 설계 완료기준·의도·설계 이탈 독립 재검토) → 완료 보고(5단계). pre-commit-review는 커밋 직전(2단계 전·후 어디든 가능하나 변경분 확정 후가 적합), independent-verify는 완료 판정 전. 두 스킬 모두 읽기 전용이며, 위험도 낮음(1파일 오타 등)은 independent-verify 생략 가능(P24). **independent-verify 미충족 시 수정 후 재검증** (3회 반복 후에도 미해결 시 사용자 보고 후 대기 — 규칙 0-1-2 검증 자동화 루프와 동일). **독립 검증자 검토 상세는 independent-verify 스킬 파일이 SSOT** (중복 원장 #3 — 체크리스트 내 항목과 스킬 절차가 이중 정의되어 있었으므로 스킬 파일로 통합).
  - **기계적 검증 (부분 검증 → 완료 전 스크립트 — 섹션1 "검증 게이트 원칙" 참조, 중복 원장 #1 참조)**:
    - [ ] **부분 검증**: 변경한 파일만 먼저 테스트 → 실패 시 즉시 수정 (빠른 회수)
    - [ ] **완료 보고 전 기계적 검증 스크립트 실행 (강제 — 전체 검증 포함, 1회)**: `scripts/pre-complete-check.sh`를 이번 세션 작업 유형에 맞는 모드로 실행한다. **스크립트가 전체 테스트·린트·런타임 기동 검증을 수행하므로 수동 전체 검증은 별도로 실행하지 않는다** (중복 원장 #1 — 수동 전체 검증과 스크립트가 같은 실패 모드를 잡으므로 합침). 스크립트 출력(증거)을 먼저 확인·기록한 뒤에만 체크박스 표시 및 완료 보고로 진행한다. 모드 선택:
      - `auto` — **권장·Stop 훅 기본값**. 세션 시작 스냅샷과 비교하여 이번 세션에서 새로 바뀐 파일만 보고 알맞은 모드를 자동 판단. 백엔드 수정 시 런타임 기동 검증까지 자동 진입, 프론트엔드 수정 시 frontend 모드, 코드 변경 없으면 docs 모드. 이전 세션 잔재는 이번 세션 수정으로 잘못 인식되지 않음 (세션 시작 훅이 스냅샷 기록). 에이전트가 모드를 직접 고를 필요 없음 — 잘못된 모드 선택으로 인한 검증 누락 방지.
      - `docs` — 문서 전용 세션 (코드 검증 스킵, 백엔드 프로세스 절대 건드리지 않음). 단, 작업 창에 코드 변경이 감지되면 거부(실패) — 코드 변경이 있으면 `backend`/`frontend`/`all` 모드로 실행해야 함. 문서 자체 점검(깨진 참조·포맷·용어 일관성)은 에이전트가 별도 수행 후 보고.
      - `frontend` — 프론트엔드 수정 시 (백엔드 프로세스 건드리지 않음).
      - `backend` — **이번 세션에서 백엔드를 수정했을 때만**. 런타임 기동 검증을 위해 기존 백엔드 프로세스(사용자가 켜둔 것 포함)를 종료 후 새 코드로 기동 검증.
      - `all` — 백엔드 린트/테스트 + 프론트엔드 검증 (수동 지정 모드). 백엔드 프로세스를 건드리지 않음 — 런타임 기동 검증이 필요하면 `backend` 모드로 별도 실행.
      **핵심 원칙**: 백엔드 프로세스 종료·재기동은 `backend` 모드(또는 `auto`가 backend로 판정한 경우)에서만. 이전 세션 잔재가 작업 창에 남아 있어도, 이번 세션에서 백엔드를 수정하지 않았으면 백엔드 프로세스를 절대 종료하지 않는다 (사용자가 켜둔 백엔드 보호). `auto` 모드는 세션 시작 스냅샷으로 이를 자동 보장. 코드 검증 스크립트 실패 시 완료 보고 금지 — 규칙 0-1-2 검증 자동화 루프에 따라 통과까지 재시도 후 보고한다.
    - [ ] **완료 판정은 기계적 검증 결과로만** — 에이전트 자기 평가("다 된 것 같다")로 완료 판정 금지
    - [ ] **완료 표시 전 증거 먼저 확인·기록 (default-FAIL contract — 하네스 강화, 강제)**: 태스크 파일의 체크박스를 `[x]`로 바꾸기 전에, 해당 단계의 검증 출력(증거)을 먼저 확인하고 기록한다. 증거를 보기 전에 체크박스를 채우는 것은 금지 — "검증 결과를 보지 않고 완료했다고 표시"하는 자기 평가는 완료 판정 근거로 사용 불가 (섹션1 "검증 게이트 원칙"과 동일 정신).
  - **의미적 검증 (구현 완료 리뢰 — 0절 "문서 역할 원칙" 기반, 아래 4항목 순서대로)**:
    - [ ] **태스크 구현 항목 모두 완료?** (체크박스 전부 충족 — 구현 누락 확인)
    - [ ] **P1~P25 아키텍처 원칙 위반 없는가?** → 25개 전체 판정과 근거 1줄씩 필수. 하나라도 ❌ 또는 보류이면 완료 보고 금지, 원인·영향·대안을 사용자에게 알리고 중단한다. 기존 "작업 시작 전 아키텍처 적합성 판정 게이트"와 대조한다.
    - [ ] **설계를 벗어난 변경 없는가?** → 근거 1줄 필수 (예: "설계서에 없는 신규 필드/플래그/상태머신 추가 없음"). 역할 원칙 "구현=태스크 따른다" — 태스크에 없는 로직/분기/상태 추가 없었는지.
    - [ ] **설계서 완료 기준 모두 충족?** 역할 원칙 "검증=설계 완료기준 따른다" — 태스크 체크박스만 채운다고 완료 아님. 사용자가 승인한 목표 달성 여부 최종 판정.
    > **부작용·회귀 위험 점검은 pre-commit-review 스킬로 이동** (중복 원장 #5 — 의미적 검증 "부작용"과 pre-commit-review "회귀 위험"이 같은 질문이므로 합침). pre-commit-review는 완료 판정 전에도 실행 가능하므로 회귀 점검이 누락되지 않음.
  - **요청 의도 사후 확인 (Intent layer — 작성자 자기 점검, 하네스 강화, 강제)**:
    - [ ] **"내가 요청받은 대로 만들었나?" (자기 합리화 편향 점검)** — 코드가 문법적으로 맞고 기존 테스트가 통과하더라도, **원래 요청과 다른 기능을 구현했을 수 있음** (예: "매도 조건 변경" 요청에 매수 조건을 변경하는 경우, 모든 테스트 통과하지만 요청 미충족). 완료 전 반드시 "사용자 원래 요청 문장" vs "실제 구현된 변경"을 나란히 비교하여 일치하는지 확인. 불일치 시 완료 보고 금지 → 누락/오구현 수정 후 재검증. **역할 분리 (중복 원장 #2)**: 본 항목은 작성자 자기 점검. "요청 안 한 변경이 섞였나?"는 pre-commit-review 스킬(커밋 전 검토), "작성자가 놓친 요청-구현 불일치가 있나?"는 independent-verify 스킬(독립 검증)이 각각 담당 — 세 검사가 서로 다른 편향을 잡음.
    - [ ] **적용 범위**: 모든 코드 수정. 거래 로직·핵심 로직 변경 시 특히 엄격 (돈 직결).
  - **사용자 화면 확인 권유 (에이전트가 할 수 없는 검증만 사용자에게 위임)**:
    - [ ] 에이전트가 할 수 있는 검증(기계적·의미적·Intent·독립 검증자)을 모두 통과한 후, **화면에서 사용자가 직접 확인해야 할 항목**을 완료 보고에 권유 형태로 포함 (예: "화면에서 매수 후보 목록이 N개로 표시되는지 확인해 주세요"). 사용자는 코딩을 모르므로 화면 확인만 가능 — 에이전트는 화면을 볼 수 없으므로 이 항목은 사용자 영역. **강제 아님 — 권유** (사용자가 확인하지 않아도 완료 판정에 영향 없음, 단 권유 자체는 생략 금지 — P21 사용자 투명성).

- [ ] **2단계: 코드 커밋 (코드만)** — 코드 변경 사항 있으면 즉시 커밋. **커밋 대상은 코드 파일만** — `HANDOVER.md`는 커밋에 포함하지 않음. 변경 사항 없으면 커밋 생략.
- [ ] **3단계: 완료된 작업 문서 삭제 (전체 작업 완료 시만 — 강제)** — 이번 세션이 해당 작업의 **마지막 단계**이고 전체 작업이 완료된 경우, 작업에 사용된 문서를 삭제한다. **단계 완료·대기 상태(남은 단계 있음)에서는 삭제 금지 — 다음 세션이 문서를 필요로 함.**
  - **삭제 대상**: 설계서(`docs/설계서/*.md`) + 태스크 파일(`docs/태스크/*.md`) + 조사 보고서(`docs/조사보고서/*.md`) 중 **이번 작업에 사용된 것만**. 절차규칙 상세·완료보고 템플릿·참고자료·API 스펙·감사 문서는 삭제 금지(유지 문서).
  - **삭제 전 참조 정리 (강제)**: 삭제할 문서를 참조하는 모든 곳(HANDOVER.md·다른 문서·코드 주석 등)을 먼저 검색하여 참조 경로를 "삭제됨(작업 완료로 정리)"으로 갱신하거나 관련 항목을 제거한다. 참조를 갱신하지 않고 삭제하면 깨진 경로가 남음.
  - **삭제 후 확인**: 삭제한 파일 경로로 전체 검색하여 잔존 참조가 없는지 확인.
  - **코드 변경 없는 문서 전용 세션**: 코드 커밋이 없으므로 2단계 생략 후 이 단계부터 수행.
- [ ] **4단계: `HANDOVER.md` 갱신 (파일만, 커밋 제외)** — 세션 개요 최근 1건 유지 + 직전 완료 작업 섹션 교체. `HANDOVER.md`는 git 추적 대상 아님 (.gitignore) — 작업 디렉터리 파일로만 유지. 커밋 해시는 2단계 완료 후 실제 해시로 기재. **3단계에서 문서를 삭제했으면 삭제 사실을 인계 문서에 반영** (참조 경로를 "삭제됨"으로 표시하거나 완료 항목 제거).
- [ ] **5단계: 세션 완료 보고 (채팅 출력 — 마지막)** — 커밋·문서 삭제·핸드오버 갱신 완료 후 출력. 보고서에 커밋 완료 여부·문서 삭제 여부·핸드오버 갱신 여부를 각각 독립 줄로 명시 (상세 식별자는 내부 인계 문서에만 기록). 보고가 마지막 — 검증 통과 후 보고를 먼저 출력하면 안 됨. 위험도 '높음' 변경은 사전 롤백 계획을 태스크 파일에 준비만 해둠 (섹션4 "검증 계층 게이트" 참조) — 에이전트가 관찰을 추적하지 않음.

> **주의**: 1단계(검증) 통과 후 5단계(보고)로 점프 금지 — 2·3·4단계가 빠지면 작업 완료 아님. todo_write에 5단계를 명시적으로 분해하여 추적 권장. 3단계(문서 삭제)는 전체 작업 완료 시만, 단계 완료·대기 시 생략.

### 코드 제거 규칙

함수, 변수, 클래스, 모듈 등 코드를 제거할 때 다음을 반드시 함께 수행:

1. **참조 주석 정리**: 제거된 코드를 참조하는 모든 주석, docstring, 파일 헤더 설명을 함께 수정 또는 제거.
2. **불일치 금지**: 주석과 코드의 불일치는 원칙10(SSOT) 및 원칙21(사용자 투명성) 위반. 제거된 함수가 docstring에 남아 있으면 신규 코드에서 해당 함수를 찾는 오류 발생.
3. **검색 범위**: 제거된 코드의 이름으로 전체 코드베이스(backend + frontend + tests + docs)를 검색하여 잔존 참조 확인. 단, 완료된 감사·조사 문서 내 역사적 로그는 해당 문서가 규칙 10-(1)에 따라 삭제될 때 함께 정리되므로, 삭제 전까지는 잔존 참조로 간주하지 않음.
4. **테스트 파일 포함**: 테스트 파일의 docstring, 헤더 주석도 코드와 일치해야 함.

### 규칙·문서 수정 절차 (강제 — 내용 증발 방지)

> **목적**: 규칙·문서 수정 시 중복 정리·통합 과정에서 의도치 않게 내용이 증발하거나 의미가 변질되는 것을 방지. 과거 여러 차례 발생한 사고(중복 제거 중 한쪽 내용 누락, 참조 갱신 누락 등)의 재발 차단.

1. **수정 전 원본 확인 (강제)**: 규칙·문서 파일(`AGENTS.md`, `ARCHITECTURE.md`, `HANDOVER.md`, 스킬 파일 등)을 수정하기 전, 수정 대상 섹션의 **수정 전 원본을 먼저 읽고** 수정할 부분을 정확히 식별.
2. **수정 후 대조 (강제)**: 수정 완료 후 수정된 부분을 **수정 전 원본과 대조**하여 아래를 확인:
   - (a) **내용 증발 없음**: 통합·중복 제거 시 한쪽 내용이 누락되지 않았는가? 양쪽 모두의 의미가 보존되었는가?
   - (b) **의미 변질 없음**: 원래 의도가 바뀌지 않았는가? 단순 표현 정리인데 의미가 달라지지 않았는가?
   - (c) **참조 일치**: 수정으로 인해 다른 파일·섹션에서 가리키던 참조(섹션명·줄번호·파일 경로)가 깨지지 않았는가?
3. **중복 정리 시 양쪽 대조 (강제)**: 두 규칙/문단을 하나로 통합할 때는 **양쪽 원본 모두**를 나란히 읽고, 한쪽에만 있는 고유 내용이 통합본에 포함되었는지 확인. 한쪽만 읽고 다른 쪽을 버리면 안 됨.
4. **다단계 수정 시 단계별 대조**: 한 번에 여러 섹션을 수정할 때는 각 섹션 수정 직후 해당 섹션을 대조 — 한꺼번에 수정 후 마지막에만 대조하면 중간 증발을 놓침.

### 작업 시작 전 아키텍처 적합성 판정 게이트 (모든 작업·강제)

> 코드뿐 아니라 설계서·태스크·규칙 문서·설정·조사 결과를 수정하는 작업에도 적용한다. 읽기 전용으로 사실을 확인하는 것은 허용하지만, 변경안을 확정하거나 파일을 수정하거나 외부 영향을 만드는 행동은 이 판정을 먼저 통과해야 한다. P1~P25는 현재 아키텍처 문서의 W1~W12·D1~D17 매핑을 통해 판정하는 감사용 번호 체계다.
>
> **판정 절차**
> 1. 사용자의 요청을 한 문장으로 요약하고, 이번 세션의 작업 범위를 고정한다.
> 2. 아래 P1~P25를 모두 `✅`, `❌`, `보류` 중 하나로 판정한다. `해당 없음`으로 생략하지 말고, 해당되지 않는 이유를 적는다.
> 3. 하나라도 `❌` 또는 `보류`이면 작업을 즉시 멈춘다. 사용자에게 위반 또는 판단 불가 사유와 영향 범위를 알리고, 원칙에 맞는 대안만 제시한다. 일반 승인으로 위반을 감수하고 계속 진행하지 않는다.
> 4. 모두 `✅`인 경우 작업 실행과 검증으로 넘어간다. 네 가지 대상별 위험 작업에 해당할 때만 실행 전에 사용자에게 위험과 영향을 설명하고 승인을 받는다.
> 5. 작업 중 설계·범위·영향이 바뀌면 P1~P25를 다시 판정한다. 새로 `❌` 또는 `보류`가 나오면 즉시 멈춘다.
> 6. 완료 보고에는 이 표의 P1~P25 전체 판정 결과와 각 판정의 근거를 포함한다. 각 판정에는 연결된 현재 기준(W1~W12 또는 D1~D17)을 함께 적는다. 시작 판정과 완료 판정이 다르면 완료로 보고하지 않는다.
