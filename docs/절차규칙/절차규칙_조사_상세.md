### 조사 및 문제 해결 규칙

0. **승인 전 코드 수정 절대 금지 (최우선 규칙).** 어떤 작업이든 — 디버깅, 새 구현, 개선, 리팩토링, 1줄 변경 포함 — 사용자의 명시적 승인 없이는 절대 코드를 수정하지 않는다. 분석, 조사, 계획 제안, 추천까지만 수행하고 승인 전까지 수정 금지.
   - **승인 트리거 (강제 — "승인" 단어만)**: 사용자가 **"승인"**이라는 단어를 명시적으로 사용한 경우만 승인으로 간주. "진행해", "수정해", "구현해", "적용해", "go", "진행할게요", "시작하겠습니다", "시작해", "이어서 해", "해줘" 등 그 외 모든 표현은 승인으로 간주하지 않음 — 사전조사·3항목 보고까지만 자동 진행하고, 코드 수정은 "승인" 단어가 도착한 후에만 시작.
   - **미승인 상황 (수정 금지)**: 사용자가 "분석해", "분석해줘", "조사해", "조사해줘", "확인해", "확인해줘", "검토해", "검토해줘", "의견 줘", "추천해", "추천해줘", "어떻게 생각해", "계획 보여줘", "진행해", "시작해", "진행할게요", "시작하겠습니다" 등을 요청한 경우. 이 경우 분석/조사/제안/사전조사·3항목 보고까지만 하고 응답 종료. 사용자가 "승인"이라는 단어를 사용할 때까지 대기.
   - **추천 요청 시 주의**: 사용자가 "추천해줘", "너의 추천은?" 등을 물을 때, 추천을 제시한 후 사용자의 명시적 승인("승인" 단어) 없이 자동으로 수정에 들어가는 것은 절대 금지. 추천 제시 → 사용자 "승인" → 수정 순서 엄수.
   - **Plan 모드가 아닐 때도 동일**: Normal 모드라도 승인 전 수정 금지. 모드와 무관하게 항상 적용.
0-1. **세션당 1단계 원칙 (강제).** 각 세션은 1단계(Step)만 진행. 한 세션에서 여러 단계를 연속 진행 금지. **단, 단위가 작은 단계(예: 1파일 1함수 내 단순 수정, 라벨/색상/문구 변경 등)는 여러 개를 한 세션에 묶어 진행 가능** — 컨텍스트 관리 차원에서 큰 단계는 1세션 1단계, 작은 단계는 묶음 허용. 묶음 여부는 작업 순서 보고 시 사용자에게 명시.
   - 한 단계 내에서는 한 파일 또는 한 블록씩 수정하고 검증한다.
   - 검증 이상 없으면 완료 보고(규칙 0-8) → **중간 단계**: 태스크 파일 진행 상황 갱신 + `HANDOVER.md` 갱신 + 커밋 / **마지막 단계(전체 완료)**: 태스크 파일 갱신 생략(갱신 직후 삭제되므로 무의미) → 작업 문서 일괄 삭제 + `HANDOVER.md` 갱신 + 커밋 후 세션 종료. 검증 실패 시 다음 세션으로 넘기지 않고 해당 세션에서 원인 해결.
   - **완료 후 추가 질문·다음 단계 제안 금지 (강제)**: 할당된 단계 작업을 마치면 완료 보고를 한 뒤 즉시 세션을 마무리한다. 완료 보고의 마지막에는 질문, 선택지, 승인 요청, 다음 단계 제안을 붙이지 않는다.
   - **종료 상태를 구분한다**:
     - `작업 완료`: 사용자가 요청한 범위 전체가 끝난 상태. `사용자 결정: 없음(작업 종료)`로 표시하고 다음 단계 언급 없이 종료한다.
     - `단계 완료·대기`: 이번 세션의 한 단계만 끝난 상태. 다음 단계와 승인 상태는 `HANDOVER.md`에만 기록하고, 사용자에게 진행을 제안하거나 질문하지 않는다. 다음 세션은 사용자의 새 진행 지시가 있을 때만 시작한다.
     - `중단·보류`: 검증 실패·원칙 위반·승인 부족·위험 발견으로 끝난 상태. 완료라고 표현하지 말고, 재개에 필요한 결정만 알린다.
   - 다음 단계 시작 전 사용자 승인이 필요한 경우에도 완료 보고에서 질문하지 않는다. `HANDOVER.md`에 "승인 대기—코드 수정 금지"를 기록하고, 다음 세션에서 사용자의 진행 지시가 있을 때 승인 절차를 진행한다.
   - 작업량이 많은 경우 사전 분할 후 사용자에게 분할 계획 보고 (섹션4 컨텍스트 관리 규칙 1과 연계).
   - **다단계 작업 적용**: 본 규칙은 구현 단계뿐 아니라 설계·태스크 작성 단계에도 동일 적용. 다단계 워크플로우(설계→태스크→구현)는 섹션4 "다단계 작업 워크플로우" 참조.

0-1-1. **요청 범위 외 구현 금지 (강제).** 사용자가 명시적으로 요청하지 않은 기능·리팩토링·개선·정리는 본 작업에 포함시키지 않음. 발견한 아키텍처 위반·개선점·잠재 버그는 코드에 반영하지 말고 `HANDOVER.md` "미해결 문제" 섹션에만 기록(규칙 9). 예외: (a) 수정한 코드와 직접 의존하여 같이 바꾸지 않으면 빌드/테스트가 깨지는 필수 연쇄 수정, (b) 사용자가 명시적으로 승인한 추가 범위. P24·P21 부합.

0-1-2. **표준 검증 절차 (강제).** 모든 검증은 `.venv` 가상환경을 기준으로 실행. pyenv 글로벌 환경을 직접 사용하지 않음 (P10 SSOT · P22 정합성 — 실행 환경과 검증 환경 단일화).
   - **테스트 실패 추적 의무**: 테스트 실행 시 실패가 발생하면 "내 수정과 무관한 기존 실패"라고 단정하지 말고, 반드시 아래 절차를 수행:
      1) **연관성 조사**: 실패한 테스트가 수정한 코드/함수/모듈/설정 키를 직접 또는 간접적으로 참조하는지 확인.
      2) **수정 전 상태 비교**: `git stash`로 수정을 임시 되돌린 후 동일 테스트를 실행하여 수정 전에도 실패하는지 확인. 수정 전에도 실패하면 기존 실패로 판정, 수정 후에만 실패하면 내 수정이 원인.
      3) **기존 실패로 판정된 경우**: 사용자 보고에 "기존 실패 N건 (수정 전 동일 실패 확인)"으로 명시하고, `HANDOVER.md` "미해결 문제" 섹션에 기록.
      4) **내 수정이 원인인 경우**: 즉시 원인 추적 및 수정. "기존 실패"로 치부하고 넘어가는 것은 절대 금지.
      - 테스트 실패는 무언가 잘못됐다는 신호. 무시하지 말고 반드시 추적하는 것이 원칙.
   - **표준 검증 명령**:
      - 백엔드 테스트: `.venv/bin/python -m pytest backend/tests -q` (전체) 또는 `.venv/bin/python -m pytest backend/tests/<파일> -q` (개별)
      - 백엔드 타입체크: `.venv/bin/python -m mypy backend` (mypy.ini 설정 기준)
      - 백엔드 런타임 기동: `.venv/bin/python main.py` (10~30초 대기 후 종료, 잔존 프로세스 0건 확인)
      - 커버리지: `.venv/bin/python -m pytest backend/tests --cov=backend --cov-report=term-missing`
      - 의존성 재설치 시: `.venv/bin/python -m pip install -r requirements.txt`
   - **비실패 경고 등 미해결 문제 등록**: 테스트 실행 시 실패가 아니더라도, RuntimeWarning·coroutine 미-await·비동기 누수 등 원칙 19(런타임 검증 게이트)에 해당하는 경고가 발생하면 `HANDOVER.md` "미해결 문제" 섹션에 등록한다. 등록 필수 항목: 발견일, 발견 경위, 증상, 영향, 수정 방향, 상태(조사 예정/수정 예정). "한계/후속" 줄만으로는 부족. 근거: 0-1-2 테스트 실패 추적 의무는 "테스트 실패"에만 적용되므로, 비실패 경고 이슈는 본 항목으로 추적 의무화. P19(런타임 검증 게이트)·P21(사용자 투명성) 부합.
   - **검증 자동화 루프(하네스)**: 수정 후 표준 검증(0-1-2 표준 검증 절차) 실패 시 테스트 실패 추적 → 근본 원인 해결 → 재검증을 통과까지 자동 반복. 3회 반복 후에도 동일 실패 지속 시 근본 원인 파악 실패로 판단, 사용자 보고 후 대기. 루프 중 규칙 0-3(롤백)·0-5(사용자 설계 로직 변경)·0-6-1(원칙 위반 발견)·0-1-1(범위 외 구현) 해당 시 즉시 중단+보고. 검증 루프 내 수정 사이클은 본 규칙(0-1 세션당 1단계)의 1단계 내 허용. P19·P21 부합.
   - 백엔드 수정 시: pytest + 런타임 기동. 프론트엔드 수정 시: build + 브라우저 확인.

0-1-3. **세션 종료 전 잔존 프로세스 완전 종료 (강제).** 모든 작업 완료 후 세션 종료 전 반드시 다음 절차 수행:
   1) **잔존 프로세스 확인**: `ps aux | grep -E "python|main.py|pytest|vite" | grep -v grep`로 백엔드/테스트/프론트엔드 프로세스 잔존 여부 확인.
   2) **잔존 시 즉시 종료**: 1개라도 잔존하면 `kill <PID>`로 종료. 응답 없으면 `kill -9 <PID>`.
   3) **재확인으로 0건 확인**: 종료 후 재확인하여 잔존 0건까지가 세션 종료 조건.
   - **적용 범위**: 백엔드 런타임 기동(0-1-2 표준 검증 절차), pytest 실행, db-backup 앱 종료 등 프로세스를 띄운 모든 작업. 프론트엔드 전용 작업이라도 백엔드 기동을 동반한 경우 포함.
   - **세션 종료 조건**: 잔존 프로세스 0건 확인 전에는 세션 종료 불가. HANDOVER.md 갱신 + 사용자 보고 전에 반드시 수행.
0-2. **수정 전 사전조사 의무 (강제).** 코드 수정 착수 전 반드시 다음 4항목 조사:
   1) **의존성**: 이 수정이 다른 어떤 코드(함수/변수/모듈/타입/설정 키)에 영향을 주는지 전체 코드베이스 검색으로 식별. **표준 검색 범위: `app`, `src`, `tests`. `docs`는 설계 참조 시에만.**
   2) **영향범위**: 백엔드/프론트엔드/테스트 중 어디까지 바뀌는지 명시.
   3) **아키텍처 원칙 부합 여부**: P10(SSOT)/P16(살아있는 경로)/P20(폴백 금지)/P21(사용자 투명성)/P22(데이터 정합성)/P23(일관성)/P24(단순성)/P25(격리된 실패) 중 해당 원칙 확인.
   4) **기존 공통 자산 확인 (P23 사전 절차)**: 구현하려는 기능(함수/컴포넌트/상수/표준 색상/패턴)과 동일 또는 유사한 공통 자산이 프로젝트에 이미 있는지 먼저 검색. 있으면 반드시 그것을 활용하고, 같은 기능을 새로 만들지 않음. (백엔드: `core/constants.py`, 공통 유틸, 기존 함수 / 프론트엔드: `components/common/`, 공통 함수, 표준 색상)
   - 조사 결과를 수정 계획에 포함하여 사용자에게 제시.
   - 사용자 승인("승인" 단어, 규칙 0) 후에만 수정 시작.
   - 스킬(problem-solve/backend-fix/frontend-fix)의 사전조사 절차와 동일 기준 적용. 스킬 미호출 시에도 본 규칙 적용.
0-2-5. **사전조사 후 작업량 판명 시 워크플로우 전환 규칙 (강제).** 규칙 0-2 사전조사 완료 후, 작업량을 판단하여 아래 절차 적용. 처음부터 다단계로 명시된 요청은 섹션4 "다단계 작업 워크플로우" 그대로 적용.
   1) **작업량 판단**: 사전조사 결과(의존성·영향범위·수정 파일 수·검증 부담) 기준으로 단일 세션 완료 가능 vs 다단계 워크플로우(설계→태스크→구현) 필요 여부 판단. **정량 기준(강제 — P10 SSOT, 컨텍스트 관리 규칙 1과 동일 기준): 수정 파일 3개 초과 또는 수정 라인 50줄 초과 시 다단계 워크플로우 권장.** 기준 미달이더라도 의존성·영향범위가 복잡한 경우 다단계 전환 가능하되, 그 사유를 사용자에게 명시.
   2) **단일 세션 가능**: 사전조사 결과 + 수정 계획을 사용자에게 보고 후, 승인(규칙 0) 시 기존 단일 세션 절차로 진행.
   3) **다단계 필요 시 전환 제안 + 승인**: 사용자에게 "작업량이 커 다단계 워크플로우(설계→태스크→단계별 구현)로 진행을 권장"이라고 제안. 전환 승인("승인" 단어, 규칙 0)을 받은 후에만 섹션4 "다단계 작업 워크플로우" 1세션(설계)으로 진입. 승인 전까지 임의로 다단계로 전환하거나 임의로 단일 세션으로 진행 금지.
   4) **이미 다단계로 시작한 경우**: 섹션4 워크플로우 그대로 적용, 본 규칙 미적용.
   - **금지**: 사전조사 후 작업량이 큼이 판명되었는데도 사용자 승인 없이 다단계로 전환. 반대로 작업량이 큰데 임의로 단일 세션에서 진행하려는 것도 금지.
   - **사용자 소통**: 일반 사용자 용어로 작업량 근거(수정 범위, 예상 단계 수)를 간결히 설명. 기술 참조 노출 금지(규칙 0-8 1항).
0-2-6. **가정·트레이드오프 선언 의무 (강제).** 사전조사(규칙 0-2) 후 수정 계획 제시 시, 코드/설정/기존 패턴으로 확정 불가한 부분은 추측을 숨기지 말고 "가정: X로 간주(틀린 경우 Y 영향)" 형태로 명시. 사전조사로 해결 가능한 것은 가정으로 남기지 않음(P24). P21(사용자 투명성) 부합.
0-2-7. **코드 수정 전 의도 파악 및 사용자 확인 (강제).** 코드 수정 착수 전 반드시 아래 3항목을 사용자에게 보고 후 승인받아야 함. 승인 자체는 규칙 0 준용(중복 기재 회피 — P10), 본 항목은 승인 전 필수 보고 내용 명시. "어떻게 고칠까"보다 "왜 고쳐야 하는가"를 먼저(P21 사용자 투명성).
   1) **왜 이 로직이 존재하는가**: 설계 의도와 이 로직이 없으면 생기는 문제를 먼저 파악하여 보고. 표면 증상이 아닌 존재 이유부터 설명.
   2) **무엇을 수정하는가**: 변경 범위와 변경 방식을 일반 사용자 용어로 정리. 의존성·영향범위 상세는 규칙 0-2 준용, 본 항목은 "무엇을 어떻게 바꿀지" 요약.
   3) **무엇이 달라지는가**: 화면에서 사용자가 볼 수 있는 변화, 매매 판단에 미치는 영향, 성능 변화(빨라지는지/느려지는지)를 명시. 핵심 로직 변경 시 규칙 0-4 상세 기준 준용하되, 본 항목은 핵심 로직 여부와 무관하게 모든 코드 수정에 적용(0-4는 핵심 로직 한정, 본 항목은 전 수정 공통).
   - **목적**: 보고를 애매하게 해서 사용자가 오해하는 일이 없도록. "왜 고쳐야 하는가"를 먼저 명확히 하여 사용자가 정확히 이해한 상태에서 승인.
   - **적용 범위**: 모든 코드 수정(백엔드·프론트엔드·거래 로직). 스킬(problem-solve/backend-fix/frontend-fix/safe-trade) 사전조사 절차와 동일 기준 적용, 스킬 미호출 시에도 본 규칙 적용.
   - **모호 표현 재확인 (강제)**: 사용자가 "진행해", "시작해", "해줘", "go", "진행할게요", "시작하겠습니다" 등 구체적 수정 내역 없이 진행을 지시하는 어떤 단어를 사용하더라도, 그것이 코드 수정 작업으로 해석되면 반드시 본 규칙의 3항목 보고 후 **"승인" 단어**로 승인받아야 함. "진행해", "시작해" 등은 사전조사·3항목 보고까지만 자동 진행하고 코드 수정은 "승인" 단어 도착 후 시작(규칙 0 승인 트리거). 사용자 표현이 모호하다고 해서 재확인을 생략하면 안 됨 — "진행해" 한 단어로는 무엇을 어떻게 바꿀지 확정되지 않았으므로.
0-2-8. **불명확 시 질문 의무 (강제).** 사용자의 요구를 정확히 인지하지 못했을 경우 추측해서 진행하지 말고 반드시 질문한다. 사전조사(규칙 0-2) 후에도 요청 의도가 불명확한 부분이 남으면, 가정(규칙 0-2-6)으로 처리하지 말고 사용자에게 명확히 질문하여 확정한 후 진행한다.
   - **적용 기준**: "사용자가 무엇을 원하는지 확신할 수 없는 상태"에서 추측하여 코드 수정·설계·문서 작성에 들어가는 것은 금지. 사전조사로 해결 가능한 기술적 불확실성(의존성·영향범위 등)은 가정 선언(규칙 0-2-6)으로 처리 가능하되, **사용자 의도 자체가 불명확한 경우**는 반드시 질문.
   - **질문 형식**: 일반 사용자 용어로 작성(규칙 0-8 1항). 선택지가 있으면 선택지와 각각의 차이를 함께 제시.
   - **목적**: 잘못된 방향으로 작업이 진행되는 것을 사전에 방지 (P21 사용자 투명성 · P24 단순성 — 재작업 비용 회피).
0-3. **사용자 승인 없는 롤백 절대 금지 (강제).** 기존 코드를 이전 상태로 되돌리는 모든 행위(롤백, 되돌리기, 이전 커밋 상태로 복원, 함수/변수/로직 제거 후 이전 구조로 회귀)는 반드시 사용자 승인을 받아야 한다.
   - **금지**: "조용히 되돌리면 해결된다"는 판단으로 사용자 모르게 롤백. "dead code로 판단되어 제거" 등의 사유로 사용자가 설계한 로직을 승인 없이 되돌리는 행위.
   - **롤백 사유 명시**: 롤백이 필요한 경우 사유, 되돌릴 대상(파일/함수/커밋), 영향 범위를 사용자에게 일반 사용자 용어로 보고 후 승인받아 진행.
   - **적용 대상**: 코드 제거, 변수/함수 삭제, 이전 커밋으로 체크아웃, git revert/reset, 로직 구조를 이전 형태로 되돌리는 리팩토링 등 코드를 이전 상태로 회귀시키는 모든 행위.
   - **롤백 사유 기록 의무 (강제)**: 사용자 승인을 받아 롤백을 진행한 경우, 승인만으로 끝내지 않고 반드시 아래 2곳에 사유를 기록. 나중에 git log나 HANDOVER.md만 보는 사람(또는 다음 세션 에이전트)이 "왜 이전 상태로 되돌아갔지?" 오인하는 것을 방지.
     1. **git commit 메시지**: 롤백 커밋 메시지에 사유·되돌린 대상(파일/함수/커밋)·영향 범위를 상세 기록. "revert" 한 단어로 끝내지 않음.
     2. **HANDOVER.md**: "직전 완료 작업" 섹션에 롤백 내용과 사유 명시. 다음 세션이 롤백 맥락을 이어서 파악할 수 있도록.
0-4. **핵심 로직 변경 시 일반 사용자 용어 설명 + 승인 필수 (강제).** 수신률, 업종 점수, 매매 로직, 매수 후보 선정, 매도 조건 등 핵심 기능을 변경할 때는 사용자가 이해할 수 있도록 일반 사용자 용어로 변경 내용을 설명하고 승인을 받아야 한다. 승인 전까지 수정 금지 (규칙 0과 동일 적용).
   - **설명 의무**: 변경 전 동작(화면에서 어떻게 보였는가), 변경 후 동작(화면에서 어떻게 달라지는가), 사용자가 확인할 수 있는 영향(매수 후보 목록 변화, 업종 점수 표시 변화 등)을 일반 사용자 용어로 설명.
   - **금지**: 기술 참조(함수명, 변수명, FID 번호 등)만 나열하고 일반 사용자 용어 설명을 생략하는 행위(규칙 0-8 1항). 사용자가 "이게 화면에서 어떻게 달라지는지 모르겠다"고 느끼면 규칙 위반.
   - **교차 참조**: 규칙 0-8 1항(일반 사용자 용어)과 동일 기준 적용.
0-5. **사용자가 설계/승인한 로직은 더 엄격하게 (강제).** 사용자가 이전에 직접 설계하거나 명시적으로 승인한 로직(예: 누적 수신 세트, 업종 점수 계산식, 매수/매도 조건 등)을 변경 또는 제거할 때는 일반 변경보다 더 엄격한 절차를 따른다.
   - **변경 사유 상세 보고**: 왜 변경해야 하는지, 기존 로직이 어떤 문제를 일으키는지(또는 일으키지 않는지)를 구체적으로 보고.
   - **영향 범위 상세 보고**: 기존 로직이 연결된 모든 경로(화면, 매수 후보 선정, 업종 점수 등)에 미치는 영향을 명시.
   - **대안 제시**: 변경 외에 다른 해결 방법이 있는지, 변경하지 않고 유지하는 것이 가능한지 대안 포함.
   - **승인 없이 진행 금지**: 사유/영향/대안 보고 후 사용자 명시적 승인(규칙 0 승인 트리거)이 있어야만 수정. "dead code로 판단되어 제거" 등의 단독 사유로 사용자 설계 로직을 승인 없이 제거하는 것은 절대 금지.
0-6. **수정안 제시 원칙 (강제).** 수정안/구현안을 사용자에게 제시하기 전에 반드시 바로 앞의 작업 시작 전 아키텍처 적합성 판정 게이트에서 P1~P25 전체를 판정한다. 아키텍처 원칙에 부합하지 않는 임시방편·땜빵·우회 수정안과 "임시로/우선/나중에" 등 우회 표현은 제시하지 않음. 제시 방식은 작업 유형에 따라 아래 기준 적용:
   - **버그 수정**: 아키텍처 원칙에 가장 부합하는 근본 해결안 1개만 제시. 임시방편/땜빵/우회 수정안 제시 금지. 선택지 나열 금지.
   - **잘못된 로직 유지한 채 추가 금지 (강제)**: 기존 잘못된 로직(버그, 아키텍처 원칙 위반, 오작동 코드)을 제거·수정하지 않고 그대로 둔 채 그 위에 새 로직을 추가하는 우회 수정 금지. 반드시 잘못된 로직 자체를 먼저 제거·수정한 뒤, 새 로직을 동일 경로에 반영. 예: 잘못된 캐시 기반 delta 계산을 두고 news_boost만 별도 처리 추가 → 금지. 잘못된 delta 계산 자체를 수정 후 news_boost를 동일 경로에 반영. (근본 해결 — P10 SSOT · P16 살아있는 경로 · P24 단순성 교차 강화, 규칙 0-6 "임시방편/땜빵 금지" 구체화)
   - **신규 구현**: 사용자 요구사항이 `ARCHITECTURE.md`의 P1~P25 중 하나라도 위반하거나 판정할 수 없는 경우, 에이전트는 작업을 진행하지 않고 위반 또는 판단 불가 사유·영향·원칙에 맞는 대안을 사용자에게 알린다. 사용자가 위반 위험을 감수하겠다고 승인해도 현재 작업은 계속하지 않는다. 원칙 자체를 바꿔야 한다면 별도의 아키텍처 검토 작업으로 분리한다.
   - **예외 (기존 규칙 유지)**: (a) problem-solve 스킬 섹션 1-1 "사용자 의도 파악 질문" 시 선택지+트레이드오프 제시, (b) 규칙 0-5 "핵심 로직 변경 시 대안 제시"는 본 규칙과 별개로 그대로 적용 — **0-5는 "사용자가 설계/승인한 로직 변경" 시 적용, 0-6은 "일반 버그 수정" 시 적용. 전제가 다르므로 충돌 아님.**

0-6-1. **아키텍처 원칙 위반 발견/발생 시 즉시 중단 + 사용자 보고 (강제).** 작업 시작 전 또는 작업 중 P1~P25 위반이나 판단 불가 상태를 발견하면 즉시 작업을 중단하고 사용자에게 보고(위반 또는 판단 불가 원칙 + 사유 + 영향 범위 + 원칙에 맞는 대안). 위반 상태에서 일반 승인으로 작업을 계속하지 않는다. 원칙을 바꿔야 하는 경우에는 현재 작업과 분리된 아키텍처 검토 작업으로 다룬다.
0-6-2. **작업 완료 시 자동 커밋 + 자동 핸드오버 갱신 (강제).** 사용자가 "커밋해"/"핸드오버 갱신해"라고 별도 지시하지 않아도, 작업 완료(검증 통과) 시 **기본적으로** 아래를 자동 수행. 사용자가 매번 지시해야 하는 부담 제거 (P21 사용자 투명성 · P24 단순성).
   - **git 커밋 (자동 — 코드만)**: 코드 변경 사항이 있으면 즉시 커밋. **커밋 대상은 코드 파일만** — `HANDOVER.md`는 커밋에 포함하지 않음 (P21 사용자 투명성 — 코드 변경과 핸드오버 갱신이 단일 커밋에 묻혀 사용자가 분리 확인하기 어려운 문제 회피 · P24 단순성 — 단일 세션完結 작업에도 핸드오버를 매번 통합 커밋하는 절차 과잉 회피). 변경 사항이 없으면 커밋 생략.
   - **HANDOVER.md 갱신 (자동 — 커밋 제외)**: 작업 완료 즉시 **파일만 갱신** (read-before-write, 규칙 8). **`HANDOVER.md`는 git 추적 대상 아님 — 커밋에 포함하지 않고 작업 디렉터리 파일로만 유지** (다음 세션 인계 + 인덱스 역할 — 0절 역할 표, 규칙 8-1/8-2 참조). 필수 기재 항목은 규칙 8-1 "필수 기재 항목" 참조.
   - **수행 순서**: 검증 통과 → 코드 커밋(코드만) → `HANDOVER.md` 갱신(파일만, 커밋 제외) → 세션 완료 보고(채팅 출력 — '커밋 및 핸드오버 표'로 사용자가 갱신 여부·내용 확인).
   - **갱신 의무 예외 (코드 수정 없는 작업)**: 순수 문서 변경(AGENTS.md/SKILL.md/ARCHITECTURE.md 등)·설정 파일 변경·조사 보고서 작성 등 **코드 수정이 없는 작업**은 `HANDOVER.md` 갱신 의무 없음. 갱신할 실질 내용(다음 세션에 전달할 코드 작업 맥락)이 없으므로 (P24 단순성). 단, 아래 2가지는 예외에서 제외 — 코드 수정 없어도 `HANDOVER.md` 갱신 수행:
     1. **사전조사 중 미해결 문제(규칙 9) 발견 시** — "미해결 문제" 섹션에 기록 필요.
     2. **다단계 작업의 설계/태스크 단계 완료 시** — 설계 파일(`docs/설계서/*.md`)·태스크 파일(`docs/태스크/*.md`)을 작성한 경우, 다음 세션이 해당 파일 경로를 받아 이어서 진행해야 하므로 "다음 세션 진행 대기" 섹션에 파일 경로 + 다음 단계 명시 필요 (규칙 8-1 필수 기재 항목 2·3번 적용). 사용자가 일일이 말하지 않아도 다음 세션 에이전트가 핸드오버만 보고 다음 작업을 인지·시작할 수 있도록 (P21 사용자 투명성).
   - **승인 전 수정 금지 (규칙 0) 상태**: 사전조사·추천·제안 단계에서는 코드 수정이 없으므로 커밋 수행하지 않음. 핸드오버 갱신은 위 "갱신 의무 예외" 항 적용 (미해결 문제 발견 시 또는 다단계 작업 설계/태스크 단계 완료 시에만 갱신).
   - **푸시는 예외 (기존 유지)**: 푸시는 사용자가 명시적으로 요청한 경우에만 별도 수행 (Git 규칙 "DO NOT push unless explicitly asked").
0-7. **세션 완료 보고 명시 의무 (강제).** 세션 완료 보고는 커밋(변경 시)과 `HANDOVER.md` 갱신이 끝난 뒤 출력한다. 보고서 본문에 아래 3항목을 **각각 독립된 줄**로 명시한다.
   - **커밋**: 완료 여부와 사용자용 한 줄 요약 (상세 식별자는 내부 인계 문서에만 기록) 또는 "없음(변경 없음)"
   - **푸시**: "안 함(기본)" 또는 "완료(사용자가 명시 요청 시)"
   - **HANDOVER**: 아래 3가지 상태 중 하나로 명시
     - `완료(내용 요약)` — 핸드오버 갱신 완료. 내용 요약 1줄 포함 (예: "완료(직전 완료 작업 1건 갱신)").
     - `보류(사유)` — 갱신 보류. 사유 명시 (예: "보류(코드 수정 없는 문서 작업 — 규칙 0-6-2 갱신 의무 예외)").
     - `갱신 없음(코드 수정 없음)` — 코드 수정 없는 작업으로 갱신 의무 예외 적용 (규칙 0-6-2).
   - **독립 줄 표시 (강제)**: 위 3항목은 보고서 본문에서 **각각 독립된 줄**로 명시적 표시. 한 줄로 통합·병합 금지. "커밋에 포함"·"커밋과 함께" 등 간접·통합 표현 금지 — 반드시 "📝 HANDOVER: 완료(...)" / "📝 HANDOVER: 보류(...)" / "📝 HANDOVER: 갱신 없음(...)" 형태로 명시.
   - **상세 포맷**: 섹션4 "사용자 보고 포맷" 준수. 본 항목은 강제성 명시용이며 포맷 항목과의 중복 기재 금지 (P10 SSOT · P24 단순성 — "중복 금지"는 포맷 항목 간 중복을 의미, 3항목 독립 줄 표시와 충돌 아님).
0-8. **사용자 보고 의무 (강제).** 사용자에게 전달하는 **모든 보고**(사전조사 보고, 수정 계획 보고, 진행 중 알림, 세션 완료 보고 등)는 아래 4항목을 준수. 본 규칙은 기존 분산 규칙(섹션1 사용자 프로필, 사용자 의사소통 규칙, 규칙 0-4, 사용자 보고 포맷)의 **단일 강제 소스** 역할 (P10 SSOT — 기존 규칙과 중복 기재하지 않고 본 규칙이 통합 강제).
   - **1항 (일반 사용자 용어로 설명)**: 모든 보고는 **일반 사용자 용어**(코딩을 모르는 사용자가 이해할 수 있는 용어)로 설명. 아래 두 종류 모두 사용자 보고에서 금지.
     - **(a) 코드 기술 참조**: 파일 경로, 줄번호, 함수명, 변수명, 클래스명, 패키지명, 스택 트레이스, 명령어, 코드 인용 태그, 커밋 해시, 내부 상태값. 사용자에게 기술 명령어(`curl`, `npm`, `python`, `git` 등)를 직접 안내하지 않고 에이전트가 직접 실행. 사용자에게 API 직접 호출로 검증을 요청하지 않고, 에이전트가 내부적으로 API 호출 후 결과를 일반 사용자 용어로 보고.
     - **(b) 규칙·원칙 메타 용어**: 규칙 번호(0-8, 0-6 등), 원칙 번호(P10, P24 등), 메타 명칭("단일 진실 소소", "역할 원칙", "다단계 워크플로우", "룰 인덱스", "검증 게이트", "핵심 vs 부수 등급" 등). 사용자 보고에서 원칙을 언급할 때는 "원칙에 부합합니다"/"원칙에 어긋납니다" 정도로만 표현하고 번호 인용 금지.
     - UI 변화가 있는 보고에서는 화면에서 어떻게 달라지는지를 먼저 설명. UI 변화가 없는 내부 작업(조사·설치·설정 등) 보고에서는 작업의 목적·결과·영향을 일반 사용자 용어로 설명 (화면 변화 강제 아님). 단, 사용자가 명시적으로 기술 세부사항을 요구한 경우는 예외 (규칙 0-8 1항 예외 조항과 동일).
   - **2항 (P1~P25 부합 여부 명시)**: 보고의 모든 단계(사전조사·수정안 제시·세션 완료 보고)에서 아키텍처 원칙 P1~P25 전체의 판정 결과를 명시. 사전조사 단계는 작업 시작 전 아키텍처 적합성 판정 게이트와 규칙 0-2 3)항, 수정안 제시 단계는 규칙 0-6, 세션 완료 보고 단계는 섹션4 "사용자 보고 포맷"의 "아키텍처 원칙 부합" 항목을 따른다. 위반 또는 판단 보류 발견 시 규칙 0-6-1에 따라 즉시 중단한다.
   - **3항 (이모지 요약 vs 표 — 중복 금지, 상황별 택일)**: 보고는 **표를 쓰면 이모지 요약 줄을 생략**하고, **표를 안 쓰면(짧은 알림·1줄 답변) 이모지 한 줄 요약만** 사용. 같은 내용을 이모지 줄과 표에 중복 기재 금지 (P24 단순성, P10 SSOT — 중복 보고 차단).
     - 이모지는 섹션4 "사용자 보고 포맷"의 6개(📦 커밋 · 🚀 푸시 · 📝 HANDOVER · ✅ 원칙 · ⚠️ 경고 · 💡 변경내용)를 사용. 다른 이모지 임의 사용 금지 (P23 일관성).
     - 표를 쓰는 보고: 표가 모든 정보를 담으므로 이모지 요약 줄은 생략. 표 내부에 해당 항목(변경 내용·원칙·경고·커밋·푸시·HANDOVER)이 행/셀로 존재해야 함.
     - 표를 안 쓰는 보고(1줄 질답·진행 중 간단 알림 — 세션 종료 계열 보고는 표 형식 강제로 이모지 요약 사용 금지): 이모지 한 줄 요약만 사용. 각 이모지는 독립된 줄로 표시, 생략 시 "없음"으로 표시.
     - **"사용자 확인 항목" 표현 (표 없는 보고)**: 표를 안 쓰는 보고에서 사용자가 브라우저·UI에서 직접 확인할 항목이 있으면 💡 변경내용 이모지 줄에 "확인 요청: <UI에서 확인할 내용>" 형태로 포함. 별도 이모지 추가 금지 (P23 일관성 — 6개 이모지 외 임의 이모지 사용 금지). 확인 항목이 없으면 💡 줄에 포함하지 않음.

     | 보고 유형 | 형식 | 비고 |
     |-----------|------|------|
     | 사전조사 보고 | 표 사용 시 → 표만 / 표 없으면 💡 ✅ ⚠️ 이모지 줄 | 커밋/푸시/HANDOVER 제외 (코드 수정 전) |
     | 수정 계획 보고 | 표 사용 시 → 표만 / 표 없으면 💡 ✅ ⚠️ 이모지 줄 | 커밋/푸시/HANDOVER 제외 (코드 수정 전) |
     | 진행 중 알림 | ⚠️ 이모지 줄만 (표 없음) | 위험·경고 발생 시만 |
     | 세션 완료 보고 | 표 사용 시 → 표만 / 표 없으면 📦 🚀 📝 ✅ ⚠️ 💡 이모지 줄 | 섹션4 포맷 준수 |

     - 코드 수정 없는 세션의 세션 완료 보고: 표를 쓰면 커밋·푸시·HANDOVER 행을 "없음(변경 없음)"/"안 함(기본)"/"갱신 없음(코드 수정 없음)"으로 명시. 표를 안 쓰면 이모지 줄에 같은 내용 명시 (항목 자체를 생략하지 말고 명시 — 규칙 0-6-2 갱신 의무 예외).
   - **4항 (보고서 작성 전 규칙 재확인 — 강제)**: 보고서 작성 전 반드시 본 규칙(0-8)과 섹션3 "작업 완료 보고서 표준 형식 (상황별 선택 가이드)", 섹션4 "사용자 보고 포맷"을 재확인 후 작성. "중간 보고라서 형식이 적용되지 않는다"는 해석 금지 — 본 규칙 3항 표에 따라 모든 보고 유형에 표 또는 이모지 줄 중 하나 적용.
   - **강제성 (규칙 0-6 동일 등급)**: 본 규칙 위반(기술 용어 남용, P1~P25 부합 여부 누락, 이모지-표 중복 기재, 또는 재확인 절차 미수행) 시 규칙 0-6(근본 해결만 제시) 위반과 동일 수준으로 간주 — 임시방편/땜빵 보고 금지, 위반 시 해당 보고를 다시 작성하여 제출.
0-8-1. **완료 보고 봉인 규칙 (강제).** 종료 상태가 `작업 완료` 또는 `단계 완료·대기`로 판정되면 완료 보고 뒤에 다음 단계 제안·질문·선택지·승인 요청·추가 작업 권유를 붙이지 않는다.
   - **봉인 vs 종료 체크리스트 관계 (명확화 — 체크리스트 생략 금지)**: 봉인은 "다음 단계 제안·질문·승인 요청·추가 작업 권유"를 금지하는 것이지, "세션 종료 체크리스트(검증/저장/인계 갱신/푸시/현재 상태/사용자 결정)"를 생략하라는 뜻이 아니다. 체크리스트는 완료 보고의 필수 부분이며, 봉인은 체크리스트 이후에 추가 내용을 붙이지 말라는 의미이다. "봉인이니까 체크리스트도 빼야 한다"는 과잉 해석 금지 — 저장·인계 갱신 여부는 체크리스트의 필수 행이므로 반드시 포함.
   - `작업 완료`: 사용자가 요청한 범위 전체가 끝난 상태이므로, 보고서의 사용자 결정은 `없음(작업 종료)`으로 표시한다. 마지막 문장은 종료 사실만 알리고 즉시 세션을 마친다.
   - `단계 완료·대기`: 이번 세션의 작업만 끝난 상태이므로, 다음 단계와 승인 상태는 `HANDOVER.md`에만 남긴다. 사용자에게 다음 단계 진행 여부를 묻지 않고, 다음 세션의 새 진행 지시를 기다린다.
   - `중단·보류`: 완료 보고를 하지 않는다. 중단 사유, 영향, 재개에 필요한 사용자 결정만 알린다.
   - **예외**: 작업 중 원칙 위반·안전 위험·검증 실패·승인 부족으로 추가 결정이 없으면 진행할 수 없는 경우에는 완료가 아닌 `중단·보류` 보고를 한다. 이 경우에만 필요한 결정을 요청할 수 있다.
   - **금지 예시**: "다음 단계도 진행할까요?", "이어서 할까요?", "승인해 주시면 시작하겠습니다", "필요하면 말씀해 주세요" 등 완료 보고 뒤의 후속 유도 문구.
0-9. **대상별 위험 알림 의무 (강제).** 대부분의 작업은 바로 진행한다. 다만 실전 모드 전환, DB 파일 삭제·덮어쓰기, API 키·인증정보 변경, 매매·주문·실전 모드 관련 코드 수정은 실행 전에 사용자에게 쉽게 설명하고 승인을 받아야 한다.
   - **알림 내용**: 무엇을 왜 바꾸는지, 화면·매매 판단·실제 주문에 어떤 영향이 있는지, 무엇을 바꾸지 않는지를 일반 사용자 용어로 설명한다.
   - **승인 대기**: 네 가지 대상별 위험 작업은 차단 상태로 바꾸지 않고 설명과 사용자 승인을 기다린다. 사용자가 승인하면 승인된 범위 안에서 바로 진행한다.
   - **그 외 중단 대상**: 오류·예외, 범위 초과, 데이터 손상, 아키텍처 원칙 충돌, 비상 정지, 중복 실행은 실제 중단 사유로 처리한다.
   - **아키텍처 위반 예외 없음**: P1~P25 위반 또는 판정 보류는 사용자 승인을 받아도 현재 작업을 재개하지 않는다. 원칙에 맞는 대안이나 별도의 아키텍처 검토 작업으로만 전환한다.
0-10. **수치 변경 시 드리프트 방지 절차 (강제).** 코드 상수(큐 크기·배치 주기·쓰로틀 간격·임계치·타임아웃·기본값 등 수치)를 변경할 때, `ARCHITECTURE.md` "수치 소유권 분리 기준(W3 SSOT)"과 L3 참조표 규칙에 따라 아래 절차를 수행. 본 규칙은 문서-코드 불일치(드리프트)의 구조적 원인 — 수치가 문서·코드 양쪽에 존재하여 어느 쪽을 고쳐도 다른 쪽이 낡는 문제 — 를 차단하는 장치.
   1) **소유권 판별**: 변경 대상 수치가 어느 소유권인지 판별 (`ARCHITECTURE.md` L3 참조표 기준).
      - **코드 상수 소유(L3 참조표 항목)**: 큐 크기, 배치 주기(0.1/0.2/0.5초), 쓰로틀 간격, fake_fill 지연, 알림 쿨다운 등 구현 세부 수치. 주인은 코드 상수.
      - **문서 소유(L1/L2 전략·안전 수치)**: 50ms 경고/200ms 중단, CircuitBreaker 5회·60초, 구독 한도 기본값 200, 일일 손실 한도 기본값 등. 주인은 `ARCHITECTURE.md`(값+근거 명시).
   2) **코드 소유 수치 변경 시**: 코드 상수만 수정. **`ARCHITECTURE.md` L3 참조표는 값이 바뀌어도 갱신하지 않음** (L3 참조표는 위치만 참조). 단, 상수의 위치(파일명 또는 상수명)가 바뀐 경우에만 L3 참조표 갱신.
   3) **문서 소유 수치 변경 시**: **`ARCHITECTURE.md`(L1/L2)를 먼저 수정** — 값 + 근거를 함께 갱신. 값만 바꾸고 근거를 남기지 않는 것 금지(W10 사용자 투명성·W3 SSOT). 문서 갱신 후 코드 상수 수정.
   4) **드리프트 점검(수정 후)**: 변경된 상수명으로 코드베이스 전체(`app`, `src`, `tests`, `docs`, `ARCHITECTURE.md`, `AGENTS.md`) 검색하여, 코드 소유 수치인데 문서에 값이 직접 기재된 잔존 여부 확인. 잔존 시 위치 참조(`파일명:상수명`)로 교정.
   5) **커밋 메시지 명시**: 수치 변경 커밋 메시지에 (a) 변경된 상수명·위치, (b) 소유권(코드/문서), (c) 변경 사유를 명시.
   - **금지**: 코드 소유 수치를 바꾸면서 `ARCHITECTURE.md`에도 같은 값을 직접 기재(이중 관리 → 드리프트 재발). 문서 소유 수치를 코드만 바꾸고 문서 근거를 갱신하지 않는 행위.
