# 검증 중복 원장 (Redundancy Ledger)

> **상태**: 유지 문서 (작업 완료 시 삭제 금지)
> **작성일**: 2026-08-07
> **목적**: 작업 마무리 단계 검사 항목 간 겹침이 "의도적 다중계층"인지 "진짜 중복"인지 판정·기록. 판정 근거는 Belt-and-Suspenders 원칙("두 검사가 서로 다른 실패 모드를 잡는가?")과 V-Model 중복 식별 프레임워크("레벨 간 매핑·문서화 부재가 중복의 주원인")에 따름.
> **참고 자료**: Chalmers/Scania V-Model 중복·공백 식별 프레임워크 (Filipovikj et al.), Redundancy Ledger 패턴 (clockify-ts-sdk gate-tiers), Belt-and-Suspenders (AI Pattern Book)

---

## 판정 기준

| 판정 | 의미 | 후속 |
|---|---|---|
| **의도적 다중계층** | 두 검사가 서로 다른 편향·실패 모드를 잡음. 하나 제거 시 안전성 하락 | 유지하되 역할 명시 |
| **진짜 중복** | 같은 질문을 같은 도구·같은 시점에 반복. 둘 중 하나로 충분 | 합치기 |

## 판정 표

| # | 검사 A | 검사 B | 겹치는 내용 | 판정 | 근거 |
|---|---|---|---|---|---|
| 1 | 수동 전체 검증 (세션절차 상세 1단계 기계적 검증) | 완료 전 스크립트 (pre-complete-check.sh) | 전체 테스트·린트·런타임 기동 | **진짜 중복 → 합치기** | 스크립트가 수동 전체 검증을 완전히 덮음. 같은 도구로 같은 실패 모드(문법·회귀)를 잡음. 두 번째 실행은 새 실패 모드를 잡지 못함 |
| 2 | 요청 의도 사후 확인 (작성자 자기 점검) | 커밋 전 검토 의도 일치 (pre-commit-review) + 독립 검증 의도 일치 (independent-verify) | "요청한 대로 만들었나? 요청 안 한 변경 섞였나?" | **의도적 다중계층 → 문구 분리** | 작성자 자기 점검(자기 합리화 편향) / 커밋 전 검토(범위 초과 점검) / 독립 검증(작성자=검증자 편향 차단)이 각각 다른 편향을 잡음. Belt-and-Suspenders 조건 충족. 단, 세 곳 모두 같은 문구로 묻고 있어 역할이 안 보임 → 문구만 분리 |
| 3 | 독립 검증자 검토 (체크리스트 1단계 내 항목) | independent-verify 스킬 호출 (검증 스킬 적용 순서) | 별도 시선에서 완료 기준·의도 일치·설계 이탈 점검 | **진짜 중복 → 합치기** | 체크리스트 항목과 별도 스킬 절차가 사실상 동일. 둘 다 "별도 작업창에서 읽기 전용 검토"를 지시. 하나로 통합 |
| 4 | 의미적 검증 완료 기준·설계 이탈 (작성자 점검) | independent-verify 완료 기준·설계 이탈 (독립 검증) | "완료 기준 충족? 설계 벗어남 없음?" | **의도적 다중계층 → 문구 분리** | 작성자 점검과 독립 검증이 다른 편향을 잡음. 하지만 같은 체크리스트를 그대로 반복하는 건 진짜 중복에 가까움 → 독립 검증은 "작성자가 놓친 것"만 묻도록 문구 변경 |
| 5 | 의미적 검증 부작용 (작성자 점검) | 커밋 전 검토 회귀 위험 (pre-commit-review) | "다른 부분에 미치는 영향·회귀 없는가?" | **진짜 중복 → 합치기** | 커밋 전 검토의 회귀 점검이 의미적 검증의 부작용 점검과 동일. pre-commit-review는 완료 판정 전에도 실행 가능하므로(검증 스킬 적용 순서 명시) 하나로 통합 |

## 합치기 적용 결과 (진짜 중복 3건)

| # | 변경 전 | 변경 후 |
|---|---|---|
| 1 | 부분 검증 → 전체 검증(수동) → 완료 전 스크립트(전체 또 실행) | 부분 검증(빠른 회수) → 완료 전 스크립트(전체 검증 포함, 1회만) |
| 3 | 체크리스트 "독립 검증자 검토" 항목 + independent-verify 스킬 호출 (이중 정의) | independent-verify 스킬 호출만 유지, 체크리스트 내 항목 삭제 |
| 5 | 의미적 검증 "부작용" 항목 + pre-commit-review "회귀 위험" 항목 | pre-commit-review "회귀 위험"으로 통합, 의미적 검증 "부작용" 항목 삭제 |

## 문구 분리 적용 결과 (의도적 다중계층 2건)

| # | 검사 | 변경 전 문구 | 변경 후 문구 |
|---|---|---|---|
| 2 | 작성자 자기 점검 | "사용자가 요청한 기능을 실제로 구현했는가?" | "내가 요청받은 대로 만들었나?" (자기 합리화 점검) |
| 2 | 커밋 전 검토 | "사용자가 요청한 내용이 맞는가, 요청하지 않은 변경이 섞여 있지 않은가" | "요청 안 한 변경이 섞였나?" (범위 초과 점검) |
| 2 | 독립 검증 | "사용자 원래 요청 내용을 다시 읽고, 변경 내역이 그 요청을 해결하는가" | "작성자가 놓친 요청-구현 불일치가 있나?" (작성자 편향 차단) |
| 4 | 독립 검증 (완료 기준) | "설계서 완료 기준이 모두 충족되었는가" | "작성자가 스스로 충족했다고 본 기준이 정말 충족됐나?" (작성자 판정 재검) |
| 4 | 독립 검증 (설계 이탈) | "태스크에 없는 로직/분기/상태가 추가되지 않았는가" | "작성자가 '범위 내'라고 본 변경이 정말 범위 내인가?" (작성자 판정 재검) |

## 유지 근거 (의도적 다중계층 2건이 제거되지 않는 이유)

- **요청 의도 일치 3계층**: AI 출력은 비결정적이므로 작성자가 "요청대로 만들었다"고 판정해도 편향이 있을 수 있음. (a) 작성자 자기 점검 → (b) 커밋 전 검토 → (c) 독립 검증 순으로 각각 다른 편향을 잡음. 하나 제거 시 편향 차단 약화.
- **완료 기준·설계 이탈 2계층**: 작성자가 "완료 기준 충족"이라고 판정한 것을 독립 시선으로 재검. 작성자=검증자일 때 발생하는 확인 편향(자기 코드를 관대히 평가)을 차단하는 것이 independent-verify 스킬의 존재 이유.
