# 참고자료: 토큰 발급 분리 — 유사 앱 사례 조사

> **작성일**: 2026-08-07
> **목적**: "앱 기동과 증권사 토큰 발급의 의존성 제거" 작업의 설계 근거로 활용.
> **조사 배경**: 사용자 제안 — "앱 기동과 증권사 서버 연결이 의존성을 갖으면 안 되는 거 아닌가? 유사 앱들은 어떤 로직인지 비교해 보자."
> **성격**: 참고자료(유지). 설계서·태스크 아님. 설계 시 본 파일을 근거로 원칙 부합 여부 판단.

---

## 0. 핵심 질문

- 앱이 켜지는 순간 증권사 토큰을 발급받아야 하는가?
- 앱 기동과 증권사 연결을 분리하는 것이 정석인가?
- 토큰은 "필요할 때" 발급하는 구조가 더 나은가?
- 재연결 시 옛 토큰을 고정으로 써도 되는가?

## 1. 사례 정리

### 사례 A — openalgo (인도 개인용 자동매매, 20개 증권사 연동)

> 출처: https://github.com/marketcalls/openalgo

우리 프로젝트와 가장 유사한 구조. 개인 투자자용 로컬 자동매매 앱으로, 인도 증권사 20곳(zerotha, dhan, fyers, upstox 등)을 연동.

**토큰/연결 관리 방식**:
- 앱 기동 시 토큰을 발급하지 않음 — 필요할 때 발급
- 토큰은 별도 저장소(Auth 테이블)에 보관, 화면 메모리가 아닌 DB에서 조회
- **재연결 시마다 토큰을 새로 조회** (가장 중요한 교훈)
  - 인도 증권사 토큰이 매일 새벽에 갱신되는데, 처음 발급받은 토큰을 고정으로 쓰면 새벽 이후 실시간 화면이 죽어버림
  - 20개 증권사 어댑터 전부 "재연결 시 DB에서 최신 토큰 재조회"로 일괄 수정된 기록이 있음 (커밋 340010c)
- 장 시간 외에는 연결 유지 작업을 아예 하지 않음 (keepalive 서비스가 장 시간에만 동작)

**우리 프로젝트와의 비교**:
| 항목 | openalgo | 우리 현행 |
|---|---|---|
| 기동 시 토큰 | 발급 안 함 | 기동 즉시 발급 |
| 토큰 보관 | DB | 화면 메모리 |
| 재연결 시 토큰 | 매번 새로 조회 | 최초 토큰 고정 |
| 장 외 시간 | 연결 유지 안 함 | 시간구간 작업으로 해결됨 |

### 사례 B — IBKR(인터랙티브브로커스) 연동 자동매매 앱들

> 출처:
> - https://github.com/pedrobraiti/agentic-trading-mcp (ADR-002, ADR-003, ADR-004)
> - https://github.com/cquillen/ibkr-conduit

미국 IBKR을 연동하는 개인용 봇/에이전트 프로젝트들. 공통 패턴이 뚜렷함.

**공통 구조**:
- **세션 유지를 전담하는 부품을 별도로 둠** — 앱 본체와 분리
- 앱 기동 시 세션을 바로 맺지 않음 — 세션 부품이 "지금 연결해도 되나?"를 판정
- 세션이 끊기면 앱 전체가 멈추는 게 아니라 **세션 부품만 경고 전송, 앱은 계속 동작**
- 토큰/세션 만료 전 미리 갱신 (`ProactiveRefreshMargin` — 만료 1시간 전 갱신)
- 장 마감·정기 점검 시간(매일 ~01:00)에는 세션이 끊기는 것을 전제로 스케줄 설계

**설계 원칙(ADR 기록)**:
- "Auth = Gateway login only (OAuth discarded for retail)" — 인증은 세션 부품이 단독 담당
- "Robustness comes from the design, not from duplicating connections" — 견고함은 연결 중복이 아니라 설계에서 옴
- "One brokerage session per username" — 세션은 단일, 앱 기동과 분리

### 사례 C — 키움 REST API 파이썬 래퍼 프로젝트들

> 출처:
> - https://github.com/zln02/quant-agent (skills/kiwoom-api/kiwoom_api.py)
> - https://github.com/younghwan91/kiwoom-rest-api
> - https://brentlee.tistory.com/m/entry/키움-REST-API-명세서-정리
> - https://hyundonghwang.github.io/2026/06/15/키움증권-REST-Open-API-Python-리서치/

키움 REST API를 직접 다루는 파이썬 프로젝트들. 우리와 같은 증권사를 쓰는 사례.

**토큰 관리 패턴 (zln02/quant-agent)**:
- 토큰을 파일에 캐시 — 매번 발급하지 않고 캐시 재사용
- **만료 30분 전에 자동 갱신** — 만료 후에야 발급받는 게 아니라 미리 갱신
- 캐시 실패는 치명적이지 않음 — 다음 호출 시 새 발급
- 키움 응답에 만료 시간이 따로 없으면 1시간 유효로 가정

**토큰 관리 패턴 (younghwan91/kiwoom-rest-api)**:
- `login()` 한 번으로 토큰 발급 + 헤더 설정 자동 처리
- 토큰 만료 시 라이브러리가 내부적으로 재발급 — 사용자 별도 작업 불필요
- `logout()`으로 토큰 폐기(au10002) 명시적 지원

**키움 공식 명세의 권장 흐름**:
1. 토큰 발급(au10001) → Bearer 저장
2. 데이터 조회
3. 주문 실행
4. 실시간 구독(웹소켓)
5. **토큰 폐기(au10002)**로 마무리

→ "앱 기동 시 발급"이 아니라 "작업 시작 시 발급 → 작업 종료 시 폐기"가 공식 권장 흐름.

**다계정·배치 운영 관점 (황현동 블로그)**:
- 단순 조회는 `requests`로도 가능하지만 배치 운영까지 고려하면 `httpx.AsyncClient` + `async/await`가 적합
- 토큰·계좌별 권한·주문 중복·미체결 확인을 **별도로 설계**해야 함 — 한 덩어리로 묶으면 안 됨

### 사례 D — pocket-wallet (주식 토큰 거래 MCP 서버)

> 출처: https://github.com/hoodpocket-labs/pocket-wallet

주식 토큰을 24시간 거래하지만, **원본 주식은 장 시간에만 가격이 형성**되는 점을 다룬 사례.

**장 시간 인식 패턴**:
- NYSE 거래일 달력(주말·10개 공휴일·13:00 조기 마감)을 자체 산정
- 장 외 시간에는 가격이 떠다닐 수 있어 **경고 표시** 또는 **거래 차단**을 옵션으로 제공
- `get_token_info`, `quote`, `get_limits` 모든 조회에 실시간 장 상태 표시
- 장 시간 인식이 "별도 부품"이 아니라 모든 조회의 공통 전처리로 동작

→ 우리의 `is_realtime_reset_window()`와 같은 방향. 장 시간 판정을 단일 기준으로 두고 모든 경로가 참조.

### 사례 E — 멀티 페어 현물 거래 봇 (API 경계 설계)

> 출처: https://dev.to/weekendly/designing-safe-api-boundaries-for-a-multi-pair-spot-trading-bot-3cho

**핵심 설계 원칙**:
- "한 마켓 페어 = 하나의 런타임 프로세스 = 자체 API 자격 증명 컨텍스트"
- 한 마켓의 문제가 다른 마켓을 멈추게 하지 않음 (장애 격리)

→ 우리는 단일 증권사라 마켓 분리는 아니지만, "토큰 발급·회복·실시간 연결·다운로드"가 각각 독립적으로 실패해야 한다는 점은 동일. 한 부분의 실패가 앱 전체를 멈추게 하면 안 됨.

## 2. 공통 패턴 정리

5개 사례가 모두 가리키는 같은 방향:

1. **앱 기동 ≠ 증권사 연결** — 둘을 분리하는 것이 정석. 기동 시 토큰을 발급하는 프로젝트는 없었음.
2. **토큰은 "필요할 때" 발급** — 실시간 구간 진입·다운로드·주문 등 실제 통신이 필요한 순간에 발급.
3. **재연결 시 토큰을 새로 조회** — 옛 토큰을 고정으로 쓰면 안 됨. openalgo의 20개 증권사 일괄 수정 사례가 이를 증명.
4. **장 시간에만 연결 유지** — 장 외 시간에는 증권사와 대화하지 않음. 우리는 이미 시간구간 작업으로 해결.
5. **토큰 만료 전 미리 갱신** — 만료 후에야 발급받는 게 아니라 만료 임박 시 자동 갱신.
6. **세션/토큰 실패는 앱 전체를 멈추지 않음** — 해당 부품만 경고, 앱은 계속 동작.
7. **키움 공식 권장 흐름 = "작업 시작 시 발급 → 작업 종료 시 폐기"** — 기동 시 발급이 아님.

## 3. 우리 프로젝트에 주는 시사점

### 현재 상태
- 4번(장 시간에만 연결)은 지난 세션 실시간 시간구간 작업으로 해결됨
- 1·2·3·5·6번이 미해결 과제

### 설계 시 고려할 점 (본 참고자료 기반)
- 토큰 발급 시점을 "실시간 구간 진입 시"와 "다운로드 시작 시" 두 곳으로 분리 → 사례 A·C 지지
- 재연결 시 토큰을 새로 조회하는 구조 → 사례 A의 핵심 교훈 (옛 토큰 고정 금지)
- 토큰 만료 임박 시 자동 갱신 → 사례 B·C 지지 (현재 `_ensure_token()`이 부분 수행)
- 토큰 발급 실패 시 앱 전체 중단이 아니라 해당 기능만 대기 → 사례 B·E 지지
- 자동매매 관리자 생성 시점을 토큰 확보 시점으로 이동 → 현재는 기동 시 고정, 분리 필요
- 다운로드 완료 후 토큰 처리 — 키움 공식 권장(폐기) vs openalgo(기억에서만 제거, 다음 호출 시 재발급) 둘 다 사례 존재. 설계 시 결정 필요.

### 주의 (본 참고자료의 한계)
- 사례 A·B는 인도·미국 증권사로, 토큰 갱신 주기·세션 정책이 키움과 다를 수 있음
- 키움은 토큰 만료 시간이 응답에 명시되지 않는 경우가 있어(사례 C) 갱신 시점 산정이 다소 불확정
- 본 참고자료는 "방향성 근거"이지 "그대로 복사할 코드"가 아님 — 설계서에서 우리 제약(단일 증권사, 로컬 앱, 테스트/실전 모드 분리)에 맞춰 변형 필요

## 5. 에이전트 사용 가이드

본 파일은 "토큰 발급 분리" 관련 작업(설계서·태스크·구현) 시 참고 자료로 사용.
- 설계서 작성 시: 본 파일 "공통 패턴 정리"와 "시사점"을 설계 근거로 인용 가능
- 구현 시: 사례별 패턴을 그대로 복사하지 말고 우리 제약에 맞춰 변형
- 원칙 판정 시: 본 파일의 패턴이 원칙(단일 진실·사용자 투명성·데이터 정합성·단순성·격리된 실패)에 부합하는지 별도 확인 필요 — 본 파일은 참고일 뿐 원칙을 대체하지 않음
