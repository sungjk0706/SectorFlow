## 1. 배경 및 목표

### 1.1 현재 상태 (문제)

사용자 보고: 다른 페이지에서 수익상세 페이지로 이동했을 때 상단 요약 카드(당일 손익)가 즉시 갱신되지 않고, 당일 손익 카드를 클릭해야 갱신되는 간헐적 현상.

심층 조사 결과, 이 현상은 수익상세 페이지만의 문제가 아니라 **구조적 문제**:

- 현재 5개 페이지(수익상세·업종순위·매수후보·매도포지션·업종분류)는 페이지 진입 시 백엔드에 최신 데이터를 요청하지 않고, 앱 시작 시 WS로 받아 쌓아둔 메모리 캐시(hotStore)만 읽어서 화면을 그림.
- `notifyPageActive()`는 백엔드에 "이 페이지 켜짐" 필터만 설정할 뿐, 데이터를 밀어주지 않음.
- hotStore가 갱신되는 경로는 단 3가지: (1) WS (재)연결 시 initial-snapshot, (2) 체결 시 sell/buy-history-append, (3) 테스트 이력 초기화 시 broadcast_history. **정기적 갱신 없음**.
- 따라서 앱을 켜둔 지 오래되고 체결이 없으면 hotStore가 앱 시작 시점 데이터로 멈춰, 페이지 진입 시 옛날 데이터가 표시됨. 체결이 방금 일어났으면 정상. 이 차이가 "간헐적"으로 체감됨.

종목상세 페이지만 진입 시 항상 HTTP로 최신 데이터를 당겨오는 올바른 패턴을 사용 중. 수익현황 페이지는 차트만 부분적으로 HTTP 조회, 계좌 패널은 hotStore 캐시만 사용.

### 1.2 목표 (사용자 관점)

1. 페이지 이동 시 이동한 페이지가 즉시 최신 데이터를 표시 — 옛날 데이터가 보이지 않음.
2. 돈 관련 데이터(잔고·손익·보유·미체결)와 매매 판단 직결 데이터(매수후보·차단 상태)는 절대 옛날 값을 보여주지 않음.
3. 참고성 데이터(업종 분류)는 잠깐 옛날 값이 보여도 무해하므로, 즉시 표시 후 백그라운드 갱신으로 자연스럽게 교체.
4. 같은 페이지를 1초 만에 다시 가도 매번 백엔드 요청이 발생하지 않음 (불필요한 요청 차단).
5. 화면 깜빡임·로딩 스피너 최소화 — 옛날 캐시를 먼저 보여주되, 돈 관련 데이터는 즉시 최신으로 교체.

### 1.3 비목표 (다루지 않는 것)

- WS 실시간 스트림 구조 변경 없음 — 기존 WS 이벤트(delta/append)는 그대로 유지.
- 백엔드 데이터 소스·계산 로직 변경 없음 — 기존 조회 API 재사용.
- 페이지 간 상태 공유 구조(hotStore) 변경 없음 — hotStore는 그대로 두고, 진입 시 최신화만 추가.
- 장마감 고정 데이터(일별 통계)의 "기준일 표시" UI 추가 — 본 설계 범위 외 (별개 UX 개선).
- 새로운 페이지 추가 없음.

## 2. 설계 방향

### 2.1 핵심 설계 결정

**결정 1: 페이지 진입 시 화면이 직접 최신 데이터를 조회 (HTTP) — 기존 WS 실시간 갱신은 유지.**

- 근거: 실시간 트레이딩 앱 표준 패턴 "Query for State, Subscribe for Motion" (상태는 조회로, 변화는 구독으로). 종목상세 페이지가 이미 이 패턴 사용 — 일관성 확보.
- WS push 기반 진입 갱신(B 방식)도 유효한 아키텍처이나, SectorFlow 기존 구조(WS는 실시간 스트림 전용, 페이지별 조회 API 일부 존재)에서는 HTTP 조회가 구현 복잡도 낮고 책임 분리 명확.
- 백엔드 변경 최소화 — 기존 `/api/trade-history/*` · `/api/stock-classification` 등 조회 API 재사용.

**결정 2: 데이터 종류별 freshness 정책 차등 적용 (단일 정책 금지).**

- 근거: 돈 관련 데이터에 SWR(오래된 캐시 즉시 표시 후 백그라운드 갱신)을 적용하면 사용자가 옛날 잔고·손익을 보고 잘못된 매매 판단을 할 위험. AGENTS.md "돈 관련 수치는 확정값이 생명" 원칙과 정면 충돌.
- 4종 데이터 분류 (정책 그룹은 2개):

| 데이터 종류 | 예시 | 정책 | 화면 표시 |
|---|---|---|---|
| **돈 관련 확정** | 잔고, 체결, 손익, 수익률, 보유 수량, 미체결 | **항상 최신 조회** + WS 지속 갱신. 캐시 재사용 금지. | 즉시 최신 표시 (옛날 캐시 노출 금지) |
| **매매 판단 직결** | 매수후보, 차단 상태, 리스크 상태 | **항상 최신 조회** + WS 지속 갱신 (위와 동일 정책) | 즉시 최신 표시 |
| **시세성** | 현재가, 등락률 | WS로 이미 최신 유지 | 진입 시 WS 최신값 |
| **참고성** | 업종 분류, 종목 분류, 설정, 레이아웃 | **SWR** — 캐시 즉시 표시 + 백그라운드 갱신 | 잠깐 옛날 값 무해 |

- "돈 관련 확정"과 "매매 판단 직결"은 정책이 같으므로 같은 그룹으로 묶되, 설계서·코드 주석에 두 라벨을 명시해 정확성 확보 (P23 용어 통일 — "확정"과 "판단" 구분).

**결정 3: 공통 갱신 메커니즘을 먼저 구축, 각 페이지는 순차 적용.**

- 근거: 5개 페이지에 동일 패턴이 중복 구현되면 P24(단순성) 위반. 공통 유틸(예: `refreshPageData()`)을 먼저 만들고 각 페이지 mount에 1-2줄 추가.
- 공통 메커니즘은 데이터 종류별 정책을 인자로 받아 분기 — "항상 최신 조회" 그룹과 "SWR" 그룹을 한 유틸에서 처리.

**결정 4: 항상 최신 조회 그룹의 캐시 신선도 판단 기준 — "마지막 갱신 시각" + "페이지 진입 시점".**

- 돈 관련 확정·매매 판단 직결 데이터는 캐시 재사용 금지가 원칙이나, 같은 페이지를 1초 만에 다시 가는 경우까지 매번 요청하면 백엔드 부하·화면 깜빡임.
- 타협점: **직전 진입으로부터 N초 이내 재진입 시 캐시 재사용, N초 경과 시 최신 조회.** 단, N은 짧게 (예: 3초 — 페이지 간 빠른 왕복만 허용).
- N초 기준: 사용자가 페이지를 보고 있는 동안은 WS로 최신 유지되므로, 진입 직후 N초는 캐시가 사실상 최신. N초 이후 재진입은 "다른 페이지에서 오래 있다가 돌아온" 경우이므로 최신 조회 필요.
- N값은 코드 상수 소유 (AGENTS.md 규칙 0-10 — 코드 소유 수치). `core/constants.py` 또는 프론트엔드 상수 파일에 정의.

**결정 5: SWR 그룹(참고성 데이터)의 캐시 신선도 판단 기준 — 동일한 "마지막 갱신 시각" + 더 긴 N초.**

- 참고성 데이터는 느리게 변하므로 N초를 더 길게 (예: 60초). 60초 이내 재진입 시 캐시 즉시 표시, 60초 경과 시 백그라운드 갱신.
- 백그라운드 갱신 중에는 옛날 캐시를 그대로 표시 (사용자가 스피너를 보지 않음). 갱신 완료 시 조용히 교체.

**결정 6: HTTP 조회 응답과 WS 델타 사이의 순서 역전(race condition) 방지 가드.**

- 문제 시나리오: 페이지 진입 → HTTP 조회 요청 발사 (t=0) → 그 사이 실제 체결 발생, WS delta가 hotStore에 먼저 반영 (t=0.3) → 뒤늦게 도착한 HTTP 응답 (t=0.5, t=0 시점 기준 데이터)이 hotStore를 덮어씀 → 더 최신인 WS 데이터가 더 오래된 HTTP 응답으로 되돌아가는 역전 현상.
- 이 현상은 1.2절 목표 "돈 관련 데이터는 절대 옛날 값을 보여주지 않음"과 정면 충돌.
- 해결: HTTP 응답을 hotStore에 반영할 때 타임스탬프 또는 시퀀스 번호를 비교 — 응답이 그 사이 도착한 WS 델타보다 더 오래된 데이터면 덮어쓰지 않고 무시.
- 이 패턴은 실시간 시세 인프라들이 표준적으로 사용하는 방식 (클라이언트가 마지막 시퀀스 번호를 들고 있다가 재동기화 시 비교).
- 적용 대상: 돈 관련 확정 + 매매 판단 직결 그룹 (WS delta와 HTTP 응답이 동일 데이터를 동시에 다룰 수 있는 경우). 참고성 그룹은 WS delta가 거의 없으므로 미적용.

### 2.2 기각 방안

| 방안 | 기각 사유 |
|---|---|
| WS push 기반 진입 갱신 (B 방식) | 결정 1에서 "WS는 변화 전용, 조회는 HTTP" 원칙 채택. WS에 초기화 책임을 지우면 책임 분리가 무너지고 P16(살아있는 경로)·P23(일관성) 위반. 4종 핵심 데이터(돈 관련 확정·매매 판단 직결)를 이 방식으로 처리하면 결정 1의 원칙이 조용히 무너지므로, 설계 단계에서 A(HTTP API 신규 추가)로 확정 — 2세션 태스크 파일로 미루지 않음. |
| 모든 데이터에 SWR 단일 적용 | 돈 관련 데이터에 옛날 캐시 노출 → 사용자 오판 위험. AGENTS.md 원칙 위반. |
| 모든 데이터에 "항상 최신 조회" 단일 적용 | 같은 페이지 빠른 왕복 시 매번 요청 → 백엔드 부하·화면 깜빡임. 참고성 데이터까지 최신 조회는 과잉. |
| 페이지별 개별 구현 (공통 메커니즘 없음) | 5페이지 동일 패턴 중복 → P24 단순성 위반. |
| 정기적 폴링 (setInterval) | AGENTS.md P11(폴링 금지) 위반. |
| HTTP 응답을 hotStore에 무조건 덮어쓰기 | WS 델타보다 오래된 HTTP 응답이 더 최신 WS 데이터를 되돌리는 순서 역전 현상 발생 (결정 6). |

## 3. 사용자 결정 항목

> problem-solve 섹션 1-1 의무 — 사용자 질문·답변 기록.

| 질문 | 사용자 답변 | 설계 반영 |
|---|---|---|
| 수익상세 페이지에서 "클릭 시 갱신"을 보신 카드는? | 상단 요약 카드 | 상단 요약 카드값이 hotStore 캐시 기반 계산이므로, 진입 시 hotStore 최신화가 핵심. 하단 통계 카드는 선택 뷰 복원으로 인한 자연스러운 변화이므로 별도 처리 불필요. |
| 페이지 진입 시 최신 데이터를 가져오는 방식? | "B가 이벤트 기반 표준 아키텍처에 부합하는 것 같은데 인터넷 검색으로 검증해줘" → 검증 결과 A(화면 직접 조회)가 표준. 사용자 확인 후 A 채택. | 결정 1 반영. |
| 어느 범위까지 한 번에 적용할까요? | 공통 메커니즘 먼저 | 결정 3 반영 — 공통 유틸 먼저 구축, 각 페이지 순차 적용. |
| 페이지 진입 시 항상 최신 데이터를 가져올까요, 조건부로 할까요? | "인터넷 검색으로 표준 아키텍처 보고해줘" → 검증 후 "캐시 신선도 비교" 선택. 단, 두 AI 의견 수용하여 데이터 종류별 차등 적용으로 수정. | 결정 2·4·5 반영. |

**두 번째 AI 의견 수용 (라벨 정확성)**: 매수후보 페이지를 "돈 관련 확정"이 아닌 "매매 판단 직결"로 라벨링. 정책은 동일(항상 최신 조회 + WS)하나, 데이터 성격 구분을 위해 별도 라벨 사용.

## 4. 아키텍처 원칙 부합 검토

| 원칙 | 판별 | 근거 |
|---|---|---|
| P10 SSOT | ✅ | hotStore를 단일 진실 소스로 유지. 진입 시 조회 결과를 hotStore에 갱신 → 기존 WS 구독·파생 계산이 자동으로 최신 반영. 조회 결과를 별도 페이지 로컬 상태로 중복 저장하지 않음. |
| P16 살아있는 경로 | ✅ | 진입 시 갱신 로직이 실제 mount 경로에 연결. dead code 아님 — 모든 페이지 mount에 호출. |
| P20 폴백 금지 | ✅ | 조회 실패 시 빈 값/옛날 값으로 폴백하지 않음. 에러 표시 + 로깅 (P25 격리). 단, SWR 그룹은 옛날 캐시를 "폴백"이 아닌 "의도적 임시 표시"로 명시 — 정책의 일부이므로 P20 위반 아님. |
| P21 사용자 투명성 | ✅ | 돈 관련 데이터가 항상 최신 → 사용자가 "이 잔고가 맞나?" 의문 제거. 조회 실패 시 화면에 에러 표시. |
| P22 데이터 정합성 | ✅ | 진입 시 조회 결과를 hotStore에 갱신 → 파생 데이터(손익·수익률)가 원본(체결 이력)에서 파생. 중복 저장 없음. 결정 6 순서 역전 가드로 HTTP 응답이 WS 델타보다 오래된 경우 덮어쓰지 않아 정합성 유지. |
| P23 일관성 | ✅ | 공통 유틸로 5페이지 동일 패턴. "돈 관련 확정" vs "매매 판단 직결" 라벨 구분으로 용어 정확성. 기존 조회 API 재사용. 7절 A안 확정으로 종목상세·수익현황 차트와 동일한 HTTP 조회 패턴 일관. |
| P24 단순성 | ✅ | 공통 메커니즘으로 중복 제거. 각 페이지 mount에 1-2줄 추가. 데이터 종류별 정책 분기는 단일 유틸 내부에서 처리. |
| P25 격리된 실패 | ✅ | 한 페이지 진입 시 조회 실패가 다른 페이지에 영향 주지 않음. 페이지 mount 내부에서 try/catch + 로깅 + 에러 표시. |

## 7. 백엔드 조회 API 신규 추가 (확정 — A안)

결정 1에서 "WS는 변화 전용, 조회는 HTTP" 원칙을 채택했으므로, 현재 HTTP 조회 API가 없는 4종 데이터(계좌·보유종목·매수후보·업종점수·업종종목)는 **HTTP 조회 API를 신규 추가**하는 것으로 확정. 2세션 태스크 파일로 미루지 않음.

**근거**:
- 4종 중 3종(계좌·보유종목 = 돈 관련 확정, 매수후보 = 매매 판단 직결)이 본 설계의 핵심 목표(옛날 값 금지)에 직결. "구현 시 결정"으로 미루기엔 너무 중요.
- B안(WS 재요청)을 후보로 남기면 2세션에서 "API 만들기 복잡하니 B로 하자"는 판단이 결정 1의 원칙을 조용히 무너뜨릴 위험.
- 종목상세 페이지가 이미 HTTP 조회 패턴을 사용 중 — 일관성 확보.

**신규 API 목록 (2세션에서 상세 스펙 정의)**:
| API | 데이터 종류 | 기존 데이터 소스 |
|---|---|---|
| `GET /api/account/snapshot` | 돈 관련 확정 (잔고) | `engine_account.get_account_snapshot()` |
| `GET /api/account/positions` | 돈 관련 확정 (보유종목) | `engine_account.get_positions()` |
| `GET /api/market/buy-targets` | 매매 판단 직결 (매수후보) | `sector_data_provider.get_buy_targets_sector_stocks()` |
| `GET /api/market/sector-scores` | 참고성 (업종 점수) | `sector_data_provider.get_sector_scores_snapshot()` |
| `GET /api/market/sector-stocks` | 시세성 + 참고성 (업종별 종목) | `sector_data_provider.get_sector_stocks()` |

기존 WS initial-snapshot이 조립하는 동일 데이터 소스를 HTTP로 노출 — 데이터 소스 단일화 (P10 SSOT).

## 8. 리스크/롤백 기준

- **롤백 명령**: `git revert <해시>` (각 단계 커밋 해시는 태스크 파일에 기록)
- **즉시 롤백 트리거 증상**:
  - 페이지 진입 시 잔고·손익이 이전보다 더 옛날 값으로 표시되는 현상 (회귀)
  - 페이지 진입 시 화면이 멈추거나 빈 화면이 지속되는 현상
  - 백엔드 조회 API 호출 시 500 에러 빈발
- **관찰 기준**: 모의투자 모드에서 1-2세션 — 5개 페이지 간 이동 시 상단 카드·잔고·매수후보가 즉시 최신으로 표시되는지 확인.
