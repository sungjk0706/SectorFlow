## 사용자 전제 (필수)
> **공통 전제 (승인 전 수정 금지·사용자 소통·보고·오류 알림 의무·작업 시작 전 아키텍처 판정 필수·완료 보고 봉인)**: problem-solve 스킬 "사용자 전제" 섹션 (.devin/skills/problem-solve/SKILL.md) 참조. 단, 오류·위험 알림 의무는 거래 로직 특성상 매매 영향·잔고·주문 위험 시 즉시 알림으로 더 엄격 적용 (docs/절차규칙/절차규칙_조사_상세.md 규칙 0-9).
- **설계서·태스크 파일 작성 시 (다단계 1·2세션)**: 작성 전 반드시 docs/절차규칙/절차규칙_문서포맷_상세.md(특히 0절 "문서 역할 원칙" 5항목)을 재독. 기존 `docs/태스크/*.md`는 포맷 SSOT가 아니라 과거 산출물 — 베끼지 말 것.

## 안전한 거래 코드 수정 절차

### 1. 사전 조사 (필수 — docs/절차규칙/절차규칙_조사_상세.md 규칙 0-2 준수)
> **다단계 작업 안내**: 거래 로직 신규 기능/구조 변경/다단계 작업인 경우 docs/절차규칙/절차규칙_세션절차_상세.md "다단계 작업 워크플로우" 적용 (설계→태스크→구현 3세션). 본 스킬은 구현 단계(3세션~)의 거래 안전성 절차 담당.
> **사전조사 후 워크플로우 전환 (docs/절차규칙/절차규칙_조사_상세.md 규칙 0-2-5)**: 사전조사 완료 후 작업량이 크다고 판명된 경우, 사용자에게 다단계 워크플로우 전환을 제안하고 승인받아야 함 (승인 없이 임의 전환/임의 단일 세션 진행 금지). 거래 로직은 돈이 직결되므로 전환 제안 시 영향 범위를 더 상세히 설명.
> **사전조사 기본 흐름 (의존성 확인·영향 범위 3단계 분류·회귀 예상 지점 명시적 나열·근본 원인 분석·아키텍처 원칙 점검 P1~P25·기존 공통 자산 확인·네이밍 일관성 확인·롤백 여부 확인·사용자 의도 파악 질문·수정안 제시 원칙·코드 수정 전 의도 파악 3항목)**: problem-solve 스킬 "기본 틀" 섹션 (.devin/skills/problem-solve/SKILL.md) 참조. 본 스킬에는 거래 특화만 기재. 거래 로직은 돈이 직결되므로 기본 흐름 전 항목을 다른 스킬보다 더 엄격하게 적용 — 특히 전이 영향 필수 추적·회귀 지점 거래 특화 예시·롤백 시 규칙 0-4/0-5 최엄격·의도 파악 3항목 중 "매매 판단에 미치는 영향" 가장 상세히.

**거래 특화 사전조사 (기본 흐름 위에 추가)**:
- `TRADE_MODE`, `SIMULATION`, `TEST_MODE` 등의 설정값이 `test`/`simulation`/`true`인지 확인
- 브로커 API 키, 계좌 비밀번호, 토큰이 코드에 하드코딩되어 있지 않은지 `grep`으로 검색
- 실제 주문을 발생시키는 함수/엔드포인트가 `test_mode` 플래그로 보호되어 있는지 확인
- **영향 범위 3단계 중 전이 영향 필수 추적** (거래 로직은 돈이 직결되므로 problem-solve 기본 틀보다 더 엄격 — 2단계 이상 경로까지 필수)
- **회귀 예상 지점 거래 특화 예시**: "매수 조건 변경 시 기존 매도 조건과 충돌", "리스크 검사 순서 변경 시 CircuitBreaker 미작동 가능" 등 거래 동작 중심으로 나열
- **롤백 여부 최엄격 적용**: 거래 로직(매수/매도 조건, 주문 경로, 리스크 검사, 업종 점수 계산 등) 롤백 시 규칙 0-4(핵심 로직 변경 UI 기준 설명+승인)·규칙 0-5(사용자 설계/승인 로직 더 엄격)를 다른 스킬보다 더 엄격하게 적용 — "dead code로 판단되어 제거" 등의 단독 사유로 사용자가 설계한 매매 조건/주문 경로를 승인 없이 되돌리는 것은 절대 금지.
- **사용자 의도 파악 질문 거래 특화 추가 카테고리** (problem-solve 섹션 1-1 기본 카테고리 적용 후 추가): (1) 실전/테스트모드 전환 여부 및 전환 시점, (2) 주문 경로(`execute_buy()`/`execute_sell()`)에 미치는 영향 범위, (3) 리스크 임계값(최대 매수 금액, 종목당 비중, 일일 손실 한도 등) 사용자 결정 값. 거래 로직은 돈이 직결되므로 사전조사로 확정 가능하더라도 임계값/모드 전환 항목은 반드시 확인.
- **코드 수정 전 의도 파악 3항목 중 "매매 판단에 미치는 영향" 가장 상세히 명시** (본 스킬 1-1 Pre-mortem·정량 손실 시나리오와 연계)

### 1-1. Pre-mortem + 정량 손실 시나리오 (거래 로직 변경 시 필수 — 돈이 직결되므로 최우선)

> **적용 범위**: 거래 로직(매수/매도 조건, 주문 경로, 리스크 검사, 업종 점수 계산 등) 변경 시 필수. 로그/알림 개선 등 비거래 로직 변경 시 생략 가능.

변경 적용 전 실패 시나리오를 사전 상상하여, 최악의 경우 손실 규모를 정량화하고 사용자에게 보고 (P21 사용자 투명성 — 돈이 직결되므로 필수).

**Pre-mortem 질문**:
- "이 매수/매도 조건 변경이 잘못되면 어떤 일이 발생하는가?"
- "시장 극단 상황(상한가 연속, 하한가 연속, 거래중지, 장외 시간)에서 이 변경이 어떻게 동작하는가?"
- "RiskManager/CircuitBreaker가 이 변경을 올바르게 검사하는가? (P16 살아있는 경로)"

**정량 손실 시나리오 산출** (가능한 경우):
- 최대 손실 가능액 = (최대 매수 종목 수) × (종목당 최대 매수 금액) × (변경으로 인한 최악 시나리오 손실률)
- 예: "매수 조건 완화 시 최대 10종목 × 종목당 100만원 × 잘못된 조건으로 인한 전량 손실 가정 = 최대 1,000만원 손실 가능"
- 정량화 불가능한 경우: "정량 산출 불가 — <이유>" 명시 (P20 폴백 금지 — 암묵적 생략 금지)

**보고 의무**: Pre-mortem 결과와 정량 손실 시나리오를 사용자에게 보고 후 승인받아야 변경 진행 (규칙 0-4/0-5 — 거래 로직은 더 엄격). 사용자가 "이 정도 손실 가능성은 알겠다, 진행해" 명시적 승인 시에만 진행.

### 2. 아키텍처 원칙 준수 (필수 — 거래 로직은 돈이 직결되므로 최우선)

#### 2-0. 수정안 제시 원칙 (docs/절차규칙/절차규칙_조사_상세.md 규칙 0-6 준수 — 거래 로직은 최우선 엄격 적용)
- **버그 수정**: 아키텍처 원칙에 가장 부합하는 근본 해결안 1개만 제시. 임시방편/땜빵/우회 수정안 금지. 선택지 나열 금지.
- **잘못된 로직 유지한 채 추가 금지 (강제 — docs/절차규칙/절차규칙_조사_상세.md 규칙 0-6)**: 기존 잘못된 로직(버그, 원칙 위반, 오작동 코드)을 제거·수정하지 않고 그대로 둔 채 그 위에 새 로직을 추가하는 우회 수정 금지. 반드시 잘못된 로직 자체를 먼저 제거·수정한 뒤 새 로직을 동일 경로에 반영. 거래 로직은 돈이 직결되므로 특히 엄격 적용 — 잘못된 매수/매도 조건·주문 경로·리스크 검사를 그대로 둔 채 우회 로직 추가하면 잔고 손실 위험. (P10/P15/P16/P24 교차 강화)
- **신규 구현**: 사용자 요구사항이 원칙 위반(예: 주문 경로 분기 요청, RiskManager/CircuitBreaker 우회 요청, 테스트모드 안전장치 생략 요청 등)인 경우, 위반 사실(위반 원칙 번호 P15/P16/P18 + 사유)을 사용자에게 경고하고 원칙 부합 대안 제시. 거래 로직은 돈이 직결되므로 사용자가 원칙 위반 영향을 정확히 이해한 후에만 결정하도록 에이전트 경고·대안 제시 의무 필수 (사용자는 코딩 지식 없어 자가 판단 불가).

#### 2-1. 단일 주문 경로 (원칙 15)
- 주문은 `trading.py` → `execute_buy()` / `execute_sell()` 단일 경로만 사용
- **금지**: 주문 로직 분기 (예: 새로운 매수 함수 별도 생성, 라우터 우회 경로 추가)
- **금지**: 병렬/죽은 주문 경로 생성 (실행되지 않는 주문 코드 방치)
- 테스트모드: `dry_run.fake_send_order()` / 실전: `router.order.send_order()` — 이 2개만 허용

#### 2-2. 살아있는 경로 배선 (원칙 16)
- `RiskManager`는 `execute_buy()`/`execute_sell()` 내부에서 호출 — 외부에서 사전 체크만 하고 실제 주문 함수 내부 검사를 생략하는 것 금지
- `CircuitBreaker`는 주문 전후에 호출 — 주문 후 체크 생략 금지
- **금지**: 호출되지 않는 안전코드 작성 (예: RiskManager 체크 함수를 만들었으나 주문 경로에서 호출 안 함)
- **검증**: 수정 후 런타임 기동 시 RiskManager/CircuitBreaker 호출 로그 확인

#### 2-3. 테스트모드 동등성 (원칙 18)
- 테스트모드와 실전모드는 **돈 I/O와 데이터·계산 SSOT만 다르고 그 외 모든 과정은 동일** (자세한 역할 차이는 `AGENTS.md` 섹션1 "실전 모드 vs 테스트 모드" 참조)
- **금지**: 테스트모드에서만 안전장치 생략 (예: "테스트니까 RiskManager 스킵")
- **금지**: 모드 분기를 돈 I/O·데이터·계산 SSOT의 최소 지점(`dry_run.fake_send_order()`) 외에 추가
- 업종 점수 계산, 필터링, 타이밍 로직은 테스트모드/실전모드 동일하게 동작
- **검증**: 테스트모드에서 RiskManager/CircuitBreaker/필터링이 실제로 실행되는지 로그 확인

### 3. 허용되는 변경
- 테스트모드 매수/매도 로직 추가 (단, `execute_buy()`/`execute_sell()` 경로 내에서)
- 조건/임계값 수정
- 로그/알림 개선
- 주문 집계/필터링 로직 추가 (단, 단일 주문 경로 유지)

### 4. 금지되는 변경
- 실제 브로커 API 키 직접 입력
- `test_mode=False` 또는 `simulate=False` 등으로 강제 변경
- "테스트모드"가 아닌 "실전모드"로 설정 변경
- 사용자 승인 없이 주문 코드 실행
- 실제 돈이 들어가는 계좌로 테스트
- **주문 경로 분기 또는 우회 경로 생성 (원칙 15 위반)**
- **RiskManager/CircuitBreaker를 주문 함수 외부로 분리 (원칙 16 위반)**
- **테스트모드에서 안전장치 생략 (원칙 18 위반)**

### 5. 사용자가 실거래를 요청한 경우
- 반드시 경고: "실제 돈이 손실될 수 있습니다"
- 테스트모드로 먼저 테스트할 것을 권유
- 사용자가 명확하게 "실제 계좌로 진행"이라고 승인한 경우에만 진행

### 5-1. 검증 자동화 루프(하네스) — docs/절차규칙/절차규칙_조사_상세.md 0-1-2 검증 자동화 루프 준수
거래 로직 수정 후 검증 실패 시 통과까지 자동 반복. 상세 절차는 docs/절차규칙/절차규칙_조사_상세.md 0-1-2 검증 자동화 루프 본문 참조. 거래 로직은 돈이 직결되므로 루프 중 P15/P16/P18 위반 발견 시 0-6-1 즉시 중단+보고, 규칙 0-5(사용자 설계 로직 변경) 해당 시 중단 + 승인받아야 재개.

### 5-2. 3계층 검증 (하네스 강화 — 거래 로직은 최우선 엄격 — docs/절차규칙/절차규칙_세션절차_상세.md "작업 완료 시 점검 체크리스트" 1단계 준수)
검증 자동화 루프(5-1) 통과 후, 완료 보고 전 아래 3계층 추가 검증 수행. 거래 로직은 돈이 직결되므로 **독립 검증자 생략 불가 — 항상 필수**.

- **완료 보고 전 기계적 검증 스크립트 (강제)**: 거래 로직은 백엔드에 있으므로 `bash scripts/pre-complete-check.sh backend` 실행 — 런타임 기동 검증 포함, 실패 시 완료 보고 금지. 프론트엔드도 같이 수정했으면 `frontend` 모드도 별도 실행.
- **요청 의도 사후 확인 (Intent layer — 강제, 거래 로직은 최엄격)**: "사용자 원래 요청(매수/매도 조건 변경 등)" vs "실제 수정된 거래 코드" 나란히 비교 → 매매 판단에 영향을 주는 변경이 요청과 정확히 일치하는지 확인. 거래 로직은 돈이 직결되므로 사소한 불일치도 완료 보고 금지 → 수정 후 재검증.
- **독립 검증자 검토 (거래 로직은 항상 필수 — 생략 불가)**: `run_subagent`(profile `subagent_explore`)에게 (1) 사용자 원래 요청, (2) 커밋 해시, (3) 변경된 거래 로직 요약, (4) 섹션 1-1 Pre-mortem 정량 손실 시나리오, (5) "요청대로 구현되었는지 + P15 주문 경로 단일성 + P16 살아있는 경로 + P18 테스트모드 동등성 위반 없는지 + Pre-mortem 시나리오 대비 안전한지" 질문. 검증자가 "문제 발견" 시 해당 문제 수정 후 재검증 — 3회 반복 후에도 미해결 시 사용자 보고 후 대기.
- **사용자 화면 확인 권유**: 거래 로직은 배포 후 모니터링(6-1)이 별도 필수이므로, 여기서는 완료 보고에 "테스트모드에서 N일 관찰 권장"을 권유 형태로 포함. 강제 아님 — 권유, 단 생략 금지(P21).

### 6-1. 검증·관찰 계층 게이트 (거래 로직 — 전 게이트 필수 — docs/절차규칙/절차규칙_세션절차_상세.md "검증·관찰 계층 게이트" 준수)
거래 로직 변경은 위험도 '높음' — 독립 검증·사전 롤백·테스트 관찰·배포 후 모니터링 **전 게이트 필수** (P24 계층 적용에서 유일하게 전부 필수인 등급).
- **독립 검증**: 완료 보고 전에 별도 세션에서 커밋 해시 + 태스크 파일만 주고 독립 검토. 결과를 HANDOVER "검증 결과"에 기록. 문제가 나오면 완료 보고를 하지 않고 수정 후 다시 검증한다.
- **사전 롤백 계획**: 태스크 파일에 롤백 명령 + 즉시 롤백 트리거 증상(주문 두 번, 손익 이상, 알림 누락 등) 사전 정의. 섹션 1-1의 Pre-mortem 정량 손실 시나리오와 연결 — "손실이 <정량 시나리오>에 도달하거나 트리거 증상 발생 시 즉시 롤백"으로 명시. 변경 전 git 커밋 해를 롤백 지점으로 기록.
- **테스트 관찰(dry-run)**: 실계좌 적용 전 테스트모드(dry-run)로 N일/N세션 관찰. 시간 의존 로직 버그(개장 전, 월초 등)는 시간이 흘러야 검증됨 — pytest/코드 리뷰로는 잡히지 않음.
- **배포 후 모니터링**: 실계좌 반영 후 N회 텔레그램 알림과 프론트 화면을 사용자가 직접 비교 (숫자 두 개 눈으로 비교 — 비개발자가 가장 잘할 수 있는 검증). 이상 시 사전 정의된 롤백 즉시 실행.
- **이견 조정**: 에이전트 간 의견 충돌 시 제3의 AI에게 재검증(1회만) → 2차 갈림 시 사용자 최종 결정 → 태스크 파일 "바로잡음 로그"에 결정 사유 기록.

⚠️ 사용자가 "실제 돈으로 테스트"라고 해도 한 번 더 경고하고 테스트모드를 권장하라.
